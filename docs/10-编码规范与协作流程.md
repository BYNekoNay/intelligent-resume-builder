# 编码规范与协作流程

## 1. 文档目标

本文件用于统一项目开发期间的代码风格、分支管理、提交规范、评审流程和文档维护要求，降低返工和沟通成本。

## 2. 开发协作原则

- 先统一规范，再开始批量开发
- 小步提交，避免大块混乱修改
- 文档、代码、数据库设计同步维护
- 所有修改都应服务于当前阶段目标

## 3. 分支管理建议

推荐分支模型：

- `main`：稳定主分支
- `dev`：开发主分支
- `feature/*`：功能分支
- `fix/*`：问题修复分支

命名示例：

- `feature/auth-login`
- `feature/resume-editor`
- `fix/pdf-export-timeout`

## 4. 提交规范

推荐提交前缀：

- `feat:` 新功能
- `fix:` 问题修复
- `refactor:` 重构
- `docs:` 文档更新
- `test:` 测试相关
- `chore:` 杂项调整

示例：

- `feat: 完成简历 CRUD 接口`
- `fix: 修复导出任务状态更新问题`
- `docs: 补充数据库设计说明书`

## 5. Java 编码规范建议

### 5.1 包结构

按模块拆分，不按技术层全局堆积。

推荐：

```text
resume/
  controller/
  service/
  domain/
  repository/
  dto/
```

### 5.2 命名规范

- 类名：大驼峰
- 方法名：小驼峰
- 常量名：全大写加下划线
- 数据表名：小写下划线

### 5.3 代码要求

- Controller 只做参数接收和响应封装
- Service 承载业务逻辑
- Repository/Mapper 负责数据访问
- 不在 Controller 中写复杂逻辑
- 不在一个方法中堆积过多职责

## 6. 前端编码规范建议

- 页面按业务模块拆分
- 接口请求集中封装
- 表单字段与接口字段命名保持一致
- 状态管理只保存真正共享的数据
- 组件职责尽量单一

## 7. 接口协作规范

- 所有接口变更必须同步更新接口文档
- 响应字段名称保持稳定
- 错误码语义保持统一
- 联调前先确认请求体和响应体结构

## 8. 数据库协作规范

- 表结构变更前先更新数据库设计文档
- 避免直接在线上手工改表
- 所有字段新增都要说明用途
- JSON 字段结构变更需同步前后端
- 资料引用关系和用户覆盖规则变更需同步更新需求、接口和测试文档
- ATS 规则、投递状态枚举和 AI 建议采纳逻辑变更需同步更新需求、接口和测试文档

## 9. 代码评审建议

评审重点：

- 是否符合当前阶段目标
- 是否引入不必要复杂度
- 是否影响主流程
- 是否破坏已有接口和数据结构
- 是否遗漏异常处理和权限校验
- AI 是否只引用当前用户允许使用的职业资料，且资料不足时未虚构事实
- 成果量化和求职沟通文案是否仅使用用户确认事实，且没有隐式自动投递行为

## 10. 文档维护规范

文档权威顺序：

1. `01-项目开发总计划.md`：范围、阶段、里程碑和 MVP 边界
2. `02` 至 `05`：需求、架构、数据和接口契约
3. `06`、`07`：任务拆解与验收标准
4. `08`、`09`、`10`：运维、安全、质量和协作门禁
5. `11`：仅对明确标注的增量能力作补充；与上述文档冲突时必须先同步主文档
6. `12-面向AI代理的开发流程与交付规范.md`：代码代理的任务输入、执行步骤和交付格式

以下情况必须更新文档：

- 新增模块
- 修改数据库结构
- 修改接口字段
- 修改部署方式
- 修改验收标准
- 修改 AI 可引用资料范围、资料选择规则或岗位定制生成行为
- 修改 ATS 规则、成果量化确认规则、投递状态或面试答案资产行为
- 修改 AI 数据出站字段、同意、配额、删除保留或私有文件访问规则

优先更新的文档：

- 需求说明书
- 架构设计说明书
- 数据库设计说明书
- 接口设计说明书

## 11. 开发节奏建议

建议每完成一个功能块，就同步做三件事：

1. 自测
2. 更新文档
3. 提交代码

## 12. 禁止事项

- 未经确认直接扩大需求范围
- 将实验性代码直接混入主流程
- 不更新文档就修改关键结构
- 在主流程未稳定时做大量非必要重构
- 未读取任务涉及的需求、数据、接口和验收条目就开始实现
- 让代码代理根据缺失细节自行扩展接口、表结构、权限或产品范围

## 13. 结语

规范的意义不是让开发变慢，而是让项目在后期不崩。  
这类项目做到后面最值钱的，不只是功能本身，而是“你能证明自己是按工程化方式完成它的”。
