## 一、版本范围

本版是**增量版本**，不改变 v0.3.0 已闭环的能力边界（个人档案 / 职业资料库 / JD 解析 / 两阶段 AI 生成 / 简历版本 / ATS 分析 / PDF 导出 / 沟通草稿 / 模拟面试 / 账号与隐私 / 留存分级清扫），只推进三条线：

**1. 投递业务流（主线）**

- **状态机 6 → 9 态**：新增 `SCREENING`（简历筛选中）、`HIRED`（已入职）、`NO_RESPONSE`（投递无回音）。
- **补一条收尾边** `NO_RESPONSE → REJECTED`：现实中最常见的收尾是「投出去没回音、最终确认被拒」，
  此前只能经 `APPLIED` 中转，而那会在审计时间线里留下一条**从未发生**的状态迁移。
- **投递状态历史**（V36 `application_status_history`）：创建写首条（`fromStatus=null`），
  每次实际变化写一条（`from`/`to`/`note`/`changedAt`）。存量数据回填以 `COALESCE(stage_entered_at, created_at)`
  作为首个可观测时刻，`from` 留空表示更早的状态不可知。
- **导出接口 `GET` → `POST` + 当前密码复验**：access token 不等于「全量数据副本」的授权；
  `formatVersion` 1 → 2，payload 增 `applications[].statusHistory`。

**1.5 Windows 桌面本地工作区（ADR-012）**

- **免登录的本地工作区**：桌面端不要求账号，认证过滤器在本地模式下**注入恒定本地用户**
  （`local-desktop`，启动时幂等创建），既有 27 处 `currentUserId` 取用点零改动；
  `/api/auth/refresh` 在桌面模式直接签发本地令牌，前端沿用在线版启动流程即可进入工作区。
- **本地文件数据库**：H2 **file** 模式落在本机数据目录，Flyway 全量迁移在本地跑通；
  **MySQL 8.4 仍是 schema 权威**（`MySql84FreshMigrationIT` 已把 V1→V36 在 8.4 上跑通并断言字符集）。
- **前端由本地服务直接托管**：静态资源 + SPA 路由回落（history 模式的 22 个懒加载路由），
  不再需要 nginx。
- **纯 Java PDF 渲染**：用 PDFBox 直接绘制，**不打包约 292MB 的 Chromium 与 Node 运行时**；
  字体不随包分发（商业字体不可再分发），直接引用 Windows 自带字体。
- **安全护栏**：桌面模式只允许绑定回环地址，绑定 `0.0.0.0` 会**拒绝启动并退出**——
  桌面模式不做令牌校验，非回环绑定等同于开一个无认证的远程接口。
- **删号被禁用**：在线版的删号是「7 天撤销窗口 → 级联硬删该用户全部数据」，
  在桌面语境下等于清空整个本地工作区，故桌面模式返回 409 并引导使用备份恢复。

**2. AI 草稿确认的引用口径（ADR-011）**

`resume_material_reference` 只记录**真实被使用**的关系：REJECT 的素材不写引用；EDIT 改为引用新建的
`USER_EDITED` 副本；未列入 items 的 selected 素材静默跳过。该表是留存 A/B 分档的**唯一判据**，
改它等于改 `docs/04 §7.1` 的覆盖范围，因此独立成提交。

**3. 方向与基线（不写实现）**

`docs/decisions/DESKTOP-OFFLINE-DIRECTION.md` 确认桌面重建的业务方向（首发 Windows、本地数据、
无需登录、AI 可选且用户自配），`docs/plans/2026-10-20-001` 落需求基线 R1-R39 / 主流程 F1-F7 /
验收样例 AE1-AE9（`artifact_readiness = requirements-only`，**桌面重建未启动**）。

## 四、已知限制

1. **AI 全链路本版未在 CI 验证**：`suite_ai_full` 因无真实密钥而跳过（需 `workflow_dispatch` 勾选 `run_ai_live`）。
   AI 相关的**降级路径**有黑盒覆盖（`H3` 已断言 `aiFailure` 非空且可见），但**成功路径**未验证。
2. **版本号有 11 处独立副本，仍无机器门禁**：本版靠人工同步（`pom.xml`、`SystemController` 及其测试、
   两个 `package.json` + lock、`pdf-service/src/server.js`、systemd 的 jar 名、`deploy-direct.remote.sh` 的
   `JAR_NAME`、部署手册）。只改一处会得到「看起来是新的、实际不是」的静默不一致。
3. **`ApplicationService` 288 → 352 行，越过 300 行规范**（+62 在本版前期、+2 在收口阶段），仓内**无行数判据**，CI 不会红。
4. **持久化门禁按需手动跑**，不在 GitHub Actions 常驻（用户决策：真库验证在云服务器做，不占 CI）。
   代价是「5.7 升级可用」这条承诺在常规流水线上为空。
5. **MySQL 5.7 不支持全新安装**：门禁只证明「停在 V19 的 5.7 老库能升到 V36」。V18 用了 8.0+ 的窗口函数，
   5.7 从未、也不打算执行 V1~V19。
6. **服务器 `app/api` 目录堆积旧 jar**（0.1.0-SNAPSHOT 系列 7 个 + 0.3.0），不影响运行但应清理；
   当前只保留 0.3.0 与 0.4.0 作为回滚点。

## 七、回滚

- **代码**：`git revert` 本版提交，或回到标签 `v0.3.0`（`git checkout v0.3.0`）。
- **数据库**：V36 只**新增** `application_status_history` 表并回填存量，**无破坏性变更**；
  回滚到 v0.3.0 的代码时该表会被闲置但不影响运行（v0.3.0 的 `AccountPurge` 不涉及它）。
  如需彻底清理：`DROP TABLE application_status_history;` 并同步删 `flyway_schema_history` 中的 V36 行（**不建议**，会破坏 Flyway 校验和）。
- **部署产物**：保留 `intelligent-resume-server-0.3.0.jar` 与 `0.4.0.jar`；
  回滚时 `cp` 旧 jar 到 `app/api/` 并改回 systemd `ExecStart`，再 `systemctl restart intelligent-resume-api`。
  注意 **jar 名必须与 `ExecStart` 一致**（本版即因此同步了 11 处版本号副本）。
