## 一、版本范围

智历是面向求职者的**岗位定制简历平台**。核心不是"改一份现有简历"，而是让用户维护一套长期可复用的职业资料库，再针对每份 JD 选材、人工确认、生成独立的岗位简历。

本版已闭环的能力：

- **个人档案与职业目标**：联系方式、个人简介、目标职位/职级/行业/城市与工作方式、定位摘要。
- **可复用职业资料库**：工作、项目、教育、技能、证书、语言等基础资料，以及量化成果、管理/协作经历、单技能证据等深化资料；支持 `PREFERRED` / `EXCLUDED` 使用偏好。
- **JD 管理与解析**：增删改、关键词解析、从 JD 发起生成。
- **两阶段 AI 生成**：先 `JOB_MATERIAL_SELECTION`（规则预筛 + AI 选材）并由用户确认快照，再 `JOB_GENERATION` 产出结构化草稿；草稿逐项审核后才写入版本。
- **简历与版本**：当前版本、归档、恢复为新版本（`RESTORED`）、草稿隔离与恢复确认、编辑器 14 个栏目、模板预览。
- **JD 覆盖度与 ATS 分析**：规则分 + 可选 AI 分析，AI 失败时降级为规则分并暴露失败原因。
- **PDF 导出**：独立 Node + Puppeteer 服务、7 套模板、私有下载、过期清理与重试。
- **投递管理**：乐观锁与有限状态迁移。
- **沟通草稿**：基于简历/JD 事实生成，**只落草稿、绝不自动发送**。
- **模拟面试**：有限轮次、确定性反馈与报告、答案资产 CRUD；答题评估已异步化。
- **账号与隐私**：AI 授权（`v1.2.0`）与撤销、当日配额、失败重试；删除账号为**7 天可撤销窗口**，窗口结束后按外键拓扑级联硬删。
- **数据保留分级清扫**：无引用资源按期硬删（A 档）；被引用者转最小不可变快照（B 档，`{"__purged":true}`）。

本版**不做**的事（有意为之的设计边界）：

- AI 输出不直接写入简历 —— 生成、内联润色、资料补全都需人工确认。
- 不提供岗位简历的永久删除（只做归档与恢复）。
- 不把联系方式、用户 ID、Token、密钥、Prompt 或模型原文写入日志、指标标签或 Git。
- 保留清扫默认**关闭**（`app.retention.purge.enabled=false` / `app.retention.account-purge.enabled=false`），需显式开启。

## 二、本版包含的质量线

门禁不以"数量"论价值，而以"是否真的会失败"论价值。本版的门禁全部经过**双向抽查**（坏样本必须变红、好样本必须保持绿），抽查记录见 `docs/07` §5.11、`docs/decisions/` 与各批报告。

| 层 | 资产 | 数量（实测清点） |
| --- | --- | --- |
| 后端契约门禁 | `server/src/test/java/com/intelligentresume/contract/*ContractTest.java` | **24** |
| 前端构建链门禁 | `check:i18n`、`check:draft-fields`（均含自测用例） | **2** |
| 部署探针 | `scripts/probe-deployment.sh`（行为断言 + 生效配置一致性） | **17** 项 |

其中部署探针专治一类**单测与 CI 都看不见**的失败：仓库改了 `deploy/`（nginx / systemd）但部署链路没带上它。本版已把 `deploy/` 纳入打包范围，并把 `systemd` 单元与 nginx 站点配置**随部署同步**（幂等 + 先校验后 reload）。

> 通用原则（多次踩坑换来的）：**永远返回"通过"的检查最危险。** 任何门禁的可信度来自"用已知坏样本验证过它会失败"，而不是来自它当前是绿的。

## 四、已知限制

### 1. 本机进程沙箱导致 PDF 服务 7 项用例必然红（非代码缺陷）

`pdf-service` 的 7 项「非法配置启动即失败」用例（`test/bind-host.test.js` 1 项 + `test/production-config.test.js` 6 项）通过 `spawnSync(process.execPath, ...)` 拉起子进程并断言 `status === 1`。在**本机**沙箱内该子进程无法创建，`status` 恒为 `null`，因此报 `null !== 1`。

本版已用**等价手工直跑**逐项证伪"代码缺陷"：7 个用例逐个直接执行 → **全部 `exit=1`，且 stderr 命中约定文案**（校验脚本 `.local-validation/pdf-config-manual.ps1`，属不入库的本地验证产物）。CI 上这 7 项通过，是这条结论的最终依据。

> 判定此类红时先看**失败文本**：`null` 说明"根本没跑起来"，与"断言失败"是两回事。

### 2. 版本号存在 6 处独立副本，无机器门禁守护

承载版本号的位置（实测）：

1. `server/pom.xml`（决定产物 jar 名）
2. `server/.../SystemController.java` 的版本字面量
3. `SystemControllerTest.java` 的断言
4. `web/package.json`
5. `pdf-service/package.json` 与 `pdf-service/src/server.js`
6. `deploy/systemd/intelligent-resume-api.service` 与 `scripts/deploy-direct.remote.sh` 的 `JAR_NAME`

**这六处没有一致性门禁**，只能靠人工同步；本次封档即为一次 11 文件的协同改动。若将来只改其中一处，会得到"版本号看起来是新的、实际不是"的静默不一致（同类失败形态在本项目已出现多次）。

**建议**：后续补一条契约测试，断言以上各处版本号一致、且 systemd 单元 / 部署脚本引用的 jar 名等于 `${artifactId}-${version}.jar`。按项目纪律，该门禁必须先用坏样本验证会变红再入库。

### 3. 容器（Docker）路线未用于生产

本版生产/测试环境均为**直连部署**（非 Docker）。容器路径的安全头由最外层 edge 下发，与 `web/nginx.conf` 存在有意保留的不对称（见 `docs/08`），已用 `SecurityHeaderDeliveryContractTest` 固定住该口径。

## 六、验收与复现

前置：Java 17、Maven、Node.js、运行中的 MySQL。

```powershell
# 根目录；.env 放 MySQL 配置，.env.live-ai 放 BAILIAN_API_KEY
.\scripts\Start-LocalValidation.ps1     # Web 5173 / API 8080 / PDF 3001
.\scripts\Test-LocalFullFlow.ps1        # 全链路验收
.\scripts\Stop-LocalValidation.ps1
```

已知工具链坑（2026-10-03 实测）：若宿主环境注入了 `SERVER__PORT`（**双下划线**），Spring Boot 的宽松绑定会把它解析为 `server.port` 并**静默覆盖** `application.yml` 的 `${SERVER_PORT:8080}`，表现为"配置写 8080、实际去抢别的端口"。启动前清除该变量，或显式设置 `SERVER_PORT=8080`。

云端复现：`bash scripts/deploy-direct.sh`（默认指向当前测试环境；构建在服务器侧完成）。

## 七、回滚

- **代码**：`git revert` 相应提交，或 `git checkout v0.3.0` 取该版本源码后重走部署。
- **运行产物**：本次封档前已留回滚点 `/opt/intelligent-resume/app/api/rollback-20261003-145819-intelligent-resume-server-0.1.0-SNAPSHOT.jar`；启用方式是把它复制为 systemd 单元 `ExecStart` 指向的 jar 名并重启 API。注意**单元与 jar 名必须同时回退**，否则 API 会因找不到 jar 而起不来。
- **数据库**：V35 为**新增表**（`account_deletion_job`，无外键），回滚应用不会影响既有数据；Flyway 不做自动 down 迁移。
