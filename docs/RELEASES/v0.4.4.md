> 本版只做一件事：把 v0.4.3 引入的「发送前预览」从**通用端点**推广到**全部 5 个领域端点**，

> 补 v0.4.3 §四·1 的欠账 —— 那条「五个领域端点可绕过预览」的已知边界，本版关闭。

## 一、版本范围

### 1. 五个领域端点全部纳入预览协议（P5）

| 领域 | 端点 | 预览端点 |
| --- | --- | --- |
| JOB_MATERIAL_SELECTION | `POST /api/ai/select-materials-for-job` | `…/preview` |
| JOB_GENERATION | `POST /api/ai/tasks/{id}/confirm-materials` | `…/preview` |
| COMMUNICATION_GENERATE | `POST /api/communications/ai-generate` | `…/preview` |
| ATS_ANALYSIS | `POST /api/ats/checks/{id}/ai-retry` | `…/preview` |
| INTERVIEW_COACH | `POST /api/interviews/{id}/follow-up` | `…/preview` |

统一协议（与前版通用端点一致）：

- 令牌走请求头 **`X-AI-Preview-Token`**，不侵入 DTO；
- 服务端用**自己组装**的 input 重算 SHA-256 比对 —— 客户端伪造不了"预览过"；
- 缺令牌 → `40001`，载荷不符 → `40901`，**两者都不落库**；
- `/preview` 只读：不写库、不调 provider、不消耗配额、不要求 `Idempotency-Key`。

**关键实现约束**：预览与 worker 执行必须调用**同一个**组装函数。两处各拼一遍必然漂移，
而漂移比没有预览更糟——用户看到的内容和实际发出去的不一致，且没有任何提示。
为此新增/抽取：

- `AtsAiInputAssembler`、`AtsAiStarter`（ATS）
- `JobGenerationInputAssembler`、`JobGenerationPreviewService`（生成）
- `InterviewFollowUpPromptAssembler`（追问；这段 prompt 原本**只在 worker 执行时现场拼**，
  任务创建时根本不存在"将要发送的内容"）
- 沟通片纠正了勘察结论：沟通**不走** `PromptTemplates` 回落，
  而是 worker 现场 `promptBuilder.build(input)`，故 dry-run 必须复用同一个 builder。

**守卫位置**：`AiTaskService#create` 的 `beforeCreate`（幂等重放之后、配额与写入之前）。
即：同一 `Idempotency-Key` 的客户端重试不需要重复带令牌；被拒绝的请求不消耗配额、
不产生 `ai_task` 行。

### 2. ATS 的两段式启动（D-AI-11）

ATS 的 prompt 正文含 `atsCheckResultId`（worker 靠它写回结论），
导致「预览必须先有 check，而首次检查没有 check」的死锁。

**否决方案**：改 prompt 剔除 id —— 会改动 AI 实际输入，动摇既有 ATS 评估基线与历史可比性，
代价与收益不成比例。

**采纳方案**：不动 prompt，收敛 AI 启动入口，拆两段：

| 段 | 端点 | 行为 |
| --- | --- | --- |
| 检查 | `POST /api/ats/check` | **总是**落库；带令牌 → 启动 AI；不带 → **不创建** ai_task，返回 `RULES_FALLBACK` + `fallback.code=PREVIEW_REQUIRED`（`retryable=true`，`consentRequired=false`） |
| 启动 AI | `/preview` → `/ai-retry` | 带令牌才真正创建 `ai_task` |

`useAi=false` 的纯规则检查**完全不受影响**（仍返回 `RULES_ONLY`，无 `fallback` 字段）——
只有「启动 AI」才需要预览确认。

**已知代价**：客户端多一步「预览 → 启动」。这是 R32 的必然代价，不是退化；
规则分与既有返回结构均未改变。

### 3. 前端 4 个入口接线

`MaterialSelectionConfirmView`（生成确认）、`CommunicationView`（AI 文案）、
`InterviewView`（薄弱项追问）三个入口接入 `useAiTaskPreview` + `AiPreviewDialog`
（选材入口此前已就位）。

统一语义：**取消 = 明确不发** —— 既不创建任务，也不弹错误提示（取消不是错误）。
e2e 新增三条取消路径用例守住这条底线。

各领域 `/preview` 的 fetcher 与创建请求共用**同一个 payload 对象**，
避免字段漂移 → 40901。

## 二、升级须知

1. **五个领域的创建端点现在强制预览**：必须带 `X-AI-Preview-Token`
   （先调对应 `/preview` 拿）。不带 → `40001`，载荷变了 → `40901`，都不落库。
2. **ATS 的 `/check` 语义变了**：不带令牌时不再自动启动 AI，而是落成
   `RULES_FALLBACK` + `PREVIEW_REQUIRED`。检查记录**照常落库**，规则分不受影响。
   需要 AI 洞察的客户端要补一步「预览 → `ai-retry`」。
3. **数据库**：本版**无新增迁移**（仍是 V38）。
4. **无密钥环境不受影响**：可用性检查在令牌校验之前，仍落成 `AI_DISABLED`。

## 四、已知边界（诚实清单）

1. **未验证：真实后端联调**。前端 e2e 全部走 `page.route` mock；令牌能否真对上
   （尤其是 40901 场景）只能靠后端 IT 与真机验证 —— 前端算不出也伪造不了令牌。
2. **`toggle-contact` 在三个领域端点无实际效果**：服务端把 `includeContact` 固定为
   `false`，故勾选后会重新拉一次预览但内容不变。与已验收的 `GenerationWorkbenchView`
   行为一致。若后端后续给领域端点开放 includeContact，需回 `api/*.ts` 补 body 字段。
3. **重试系列端点未纳入**：`POST /api/ai/tasks/{id}/retry`、`/ai-retry`（面试/沟通的
   ai-retry）等"重跑已确认任务"的入口本版未加令牌强制。语义上用户已确认过一次内容，
   是否也要二次确认属产品决策，未定。
   *（2026-10-28 追记，不改上文结论：决策已定 —— **不纳入**，见 `docs/decisions/DECISION-BRIEF.md` D8。
   另：原文把 ATS 的 `ai-retry` 一并算作「未纳入」不准确 —— `AtsAiStarter` 的 `ai-retry` 本就要求先 preview。）*
4. **无告警通道**：备份/服务失败只能靠 `systemctl --failed` 或部署探针发现（承前版）。
5. 测试侧行数欠债未清（最大 `InterviewControllerIT` 已从 708 降到 648）。
