## 一、版本范围

### 1. 告警链路真正接通（P3）

此前的事实是「规则写对了、门禁绿了、真实环境从未评估」—— 直连路线运行的
`deploy/prometheus/prometheus.yml` **没有 `rule_files`**，15 条规则空转。

- `rule_files` 指向 `/opt/intelligent-resume/monitoring/prometheus/rules/*.yml`（绝对路径；
  服务器路径与仓库布局同构，门禁可机械映射回仓库）；
- 部署脚本幂等同步规则目录（**唯一源仍是仓库 `monitoring/prometheus/rules/`**，不在 `deploy/` 下复制副本）；
- 告警出口：`deploy/check-alerts.sh` + `intelligent-resume-alertcheck.timer`（每 5 分钟；
  critical firing → 退出码 2 → journald / `systemctl --failed` / 探针第 11 节可见）。
  **刻意不上 Alertmanager**：宿主机 3.6G、swap 已吃 979M（内存账见部署手册）；
- systemd 硬化：api `MemoryMax=1200M`、pdf `512M`、`TasksMax=512`，三个单元加 `OnFailure=alertcheck`；
- 部署回滚点：jar / 备份脚本 / prometheus 配置覆盖前先留 `.bak`（此前 jar 是唯一没有回滚点的产物）。

**验收（实测，非推断）**：停 API → `ApiTargetDown` critical firing → `check-alerts` 退出码 **2** →
启动 API → **2 分钟内**回到无告警 → 退出码 **0**。

### 2. 备份保底份数（P3）

原清理是裸 `find -mtime +14 -delete`：**连续失败 15 天会把最后一份好备份也删光**。

- 改为「新→旧排序 → 跳过最新 `MIN_KEEP`（默认 3）份 → 其余中超过保留期的才删」；
- `MIN_KEEP < 1` 显式拒绝；
- 新增 `--self-test`：临时目录造 5 份假备份（1/5/10/20/30 天前）反向验证清理逻辑，不连库、不碰真备份；
- `BackupRetentionContractTest` 用**禁止形态**（出现裸 `-mtime … -delete` 即红）守护，不依赖具体写法。

### 3. 部署探针扩到 33 项（P3）

- `SSH_HOST` 默认改为空（作者本机 ssh 别名不再写死；此前换机器跑 33 项里只有 11 项真的执行）；
- 汇总处强校验 `PASS+FAIL == EXPECTED_ITEMS`：注释掉任一检查项 → 探针自红；
- 新增：最近一次备份是否**成功过**（Result=success 且 36h 内）、备份份数/新鲜度/权限、
  `/api/v1/rules` 条数 ≥15 且 `health=ok`（带 60s 重试）、critical firing=0、alertcheck 出口可用。

### 4. 确认草稿：显式拒绝「客户端少提交」（P4，ADR-013）

`selected` 有、`items` 无 → `40904 SELECTION_ITEM_UNKNOWN`，且在**任何写库之前**失败。
历史上静默跳过，后果是「版本已落地但少了溯源引用」，而引用表同时是留存分档判据
（少引用会让素材提前进入物理删除档），**代码回滚救不回已删数据**。

前置调查结论：前端 `items` 是 `draftItems` 全量映射，不存在合法的部分提交路径。
`decision != ACCEPT`（用户明确拒绝）仍是合法的静默跳过 —— 两者由成对用例钉住。

### 5. `selection_reason` 取值域封闭（P4，D5）

新增 `SelectionReason`（`AI_REFERENCED` / `USER_EDITED`），写入前归一化，未知值抛 `40001`。
溯源字段出现无法解释的值等于伪造证据。不做 DB `CHECK` 约束（迁移代价 + 历史行），由常量 + 门禁保证。

### 6. 重试「不重组输入」被门禁钉住（P4，D8）

`RetryReuseContractTest` 断言：通用 retry 只重置状态、不重写 `input_snapshot_json`；
面试 `ai/retry` 原地重跑同一 attempt；retry 端点不带 `X-AI-Preview-Token`。
一旦有人把组装逻辑塞进 retry，门禁变红 —— 因为那时它**必须**纳入预览令牌并改文档。

### 7. 文档单一事实源（P1/P2）

- `OPEN-DECISIONS` 状态封闭集（`OPEN` / `RESOLVED` / `PARTIALLY-RESOLVED`）+ 机器门禁
  `OpenDecisionRegisterContractTest`（已闭环必带 `Resolution`/`Decision`、`PARTIALLY` 必写残余）；
- 数据留存口径统一到 `docs/04` §7.1（账户侧已实施 / 投递与面试硬删未兑现分开表述）；
- 派生指标（迁移版本、最新发布、探针项数）由实测供给 + `ManualFactConsistencyContractTest` 守护；
- `docs/DEPLOYMENT_DIRECT.md` §13 成为**全仓唯一**允许写线上精确数字的位置。

## 二、破坏性变更

| 变更 | 影响 | 处置 |
| --- | --- | --- |
| 确认草稿缺项 → `40904` | 自建客户端若只提交部分 `items`，现在会被拒绝（历史返回 200） | 提交**全部**草稿项；用户拒绝的项用 `REJECT`（仍是合法跳过） |
| `selection_reason` 未知值 → `40001` | 直接写入自定义原因的客户端会被拒 | 只用两值：`AI_REFERENCED` / `USER_EDITED` |
| 探针 33 项 + 项数强校验 | 自定义探针分支若删改检查项会红 | 增删检查项必须同步 `EXPECTED_ITEMS_SSH/NOSSH` |
| 备份保底 3 份 | 磁盘占用下限提高（≤3 份永不删） | 需要更少份数时显式设 `MIN_KEEP`（≥1） |

## 三、升级步骤

1. `bash scripts/deploy-direct.sh`（自动同步 rules 目录、systemd 单元、备份脚本与探针）；
2. 探针应报 **33 项 / 0 失败**；若报项数不等于期望，先看是不是探针被改动过；
3. `curl 127.0.0.1:9090/api/v1/rules` 应返回 ≥15 条且 `health="ok"`；
4. 手工验一次出口：`sudo systemctl stop intelligent-resume-api` → 等 ~90s →
   `sudo /opt/intelligent-resume/bin/check-alerts.sh` 应退出 2 → 启动 API 后应回 0；
5. 旧 jar 保留在 `app/api/intelligent-resume-server-0.4.4.jar.bak`，回滚只需换回并把单元 jar 名改回去。

## 四、已知边界（不在本版范围内）

1. **无告警投递通道**：出口是 journald + `systemctl --failed` + 探针。没有邮件/IM 推送，
   也没上 Alertmanager（内存红线）。要真正「叫醒人」需要另立一项。
2. **探针依赖 `sudo` 与 SSH 免密**：换机器跑需要显式传 `SSH_HOST`，否则只判 11 项（会明示 SKIP）。
3. **桌面端未收口**（P5）：`desktop-shell/package.json` 仍是 0.1.0，不在版本一致性门禁内；
   安装包需重打；AC-SHELL-1/2 验收仍未在图形会话中完成。
4. **40904 的文案只覆盖前端本仓**：第三方客户端需要自己映射该码。
5. `docs/05` 仍按「建议」表述错误码（`1.3 通用错误码建议`），未做法定化重写。
