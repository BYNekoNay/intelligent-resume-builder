## 一、版本范围

### 1. 桌面端 JSON 列双编码（缺陷修复，影响面 17 个 JSON 字段）

H2 的 JSON 列对**参数绑定方式**敏感，实测三种形态：

| 写入方式 | H2 里的物理形态 | Hibernate 能否读回 |
| --- | --- | --- |
| Hibernate（`SqlTypes.JSON` 绑定） | JSON 对象 `{"a":1}` | 能 |
| `setString` / `setObject` / `CAST(? AS JSON)` | JSON 字符串标量 `"{\"a\":1}"`（双编码） | **抛 `JsonJavaType`** |
| `? FORMAT JSON` | JSON 对象 `{"a":1}` | 能 |

MySQL 会把 JSON 文本规范化成对象，所以只有桌面端踩到。而桌面导入器正是用 `setObject` 绑字符串——
**每导入一份简历/职业资料，就产出一批 JPA 再也读不出来的行**，且发生在登录后的第一批操作里。

修法分读写两侧：

- **写侧根治**：新增 `ImportColumnBinder`，用 `information_schema.columns` 判定 JSON 列，对字符串值改用
  `? FORMAT JSON` 绑定。insert 与 `USE_IMPORTED` 的 update **两条路径一起修**（只修一半会留下「覆盖后又变坏」）。
- **读侧兼容存量**：新增 `LenientJsonFormatMapper`，**只挂在 `application-desktop.yml`**（生产 MySQL profile 零改动）。
  先按目标类型正常反序列化，仅当失败且节点是文本时再解一层；**非 JSON 文本仍然抛错**，由反证用例钉住。

### 2. 桌面导入冲突解决的两个端到端用例启用

上一版把 `USE_IMPORTED` / `KEEP_LOCAL` 两个用例 `@Disabled`，理由写的是「H2 file 库下内容比较不稳定」。
**这个归因是错的**：裸跑取证显示冲突检测逻辑本身没有缺陷，真正的问题有三条——

1. 断言查中文标题「Java 后端-502」，而包构造器写的是「Java Backend-504」，**这条断言永远不可能通过**；
2. 另一条「本地记录应仍存在」只数 `COUNT(*)==1`，**覆盖失败也会绿**，是空转断言；
3. 用例间共享 H2 file 库里的导入映射，**默认执行顺序恰好让只读用例排在写映射用例之前**，
   靠运气绿；强制字典序即失败（这条是潜伏的顺序依赖，本版一并修掉）。

现改为「用稳定 ID 定位记录 + 断言标题内容」，并新增 `@BeforeEach` 只清本类写过的映射
（ADD/SKIP/CONFLICT 判据只看映射存在性），不触碰 `resume ↔ resume_version` 的环状外键数据行。

### 3. 单文件行数棘轮门禁（新判据）

此前「单文件 ≤ 300 行」只是文档里的规则，**仓内没有任何判据**，12 个主代码文件越线也永远不红。

`SourceFileSizeRatchetContractTest` + `source-size-baseline.txt`，五条判据：

- 未登记且 `> 300` 行 → 红（不许欠新债）；
- 已登记文件行数上涨 → 红（棘轮只许下调）；
- 条目失效（文件已达标或已消失）→ 红（逼着拆完就收紧基线）；
- 基线格式必须合法、路径必须相对且用正斜杠；
- 扫到的 `.java` 少于 250 个 → 红（**防 glob 写错导致前三条断言全空转、门禁永远绿**）。

口径是**总物理行数**，与规则字面一致（刻意不用「非空行」：那会把 694 行的文件记成 629，等于规则说 300、判据量另一回事）。
基线登记 14 条当下欠债（2026-10-23 更正：现为 **12 条** —— `AccountExportService` 达标移出、`DesktopImportService` 拆到 ≤300 行后移出）；`ApplicationService` 已拆到 **261 行**（统计算法抽到无 Spring 依赖的
`ApplicationStatsCalculator`），故不在基线内——本版用一次真实降档证明了棘轮能往下走。

## 三、已知限制

- 桌面端仍无安装包与桌面壳（ADR-012 阶段五/六未做）。
- **导入预览不覆盖嵌套集合**：`resumes.versions`、`applications.statusHistory` 的内容变更既不判冲突也不会被更新，
  且无任何提示（与 R37「同 ID 内容变即冲突」口径不一致）。已登记 `OPEN-DECISIONS`，待产品口径。
  　*（2026-10-23 更正：批次 1.4 已让嵌套集合参与分类与写入，子记录逐条决策；本条不再成立，
  见 `OPEN-DECISIONS` 同日 RESOLVED 项与 `docs/reviews/2026-10-23-nested-import.md`。）*
- 行数门禁只扫 `src/main/java`；测试侧另有 18 个超 300 行文件不在判据内（已登记 `OPEN-DECISIONS`）。
- 读侧宽容 mapper 让**存量双编码行可读**，但它们的物理形态仍是非标准字符串标量；如需彻底归一，
  需一次性重写这些行（本版不做，避免动生产数据）。
- AI 成功路径仍需真实密钥验证（`workflow_dispatch` + `run_ai_live`）。

## 四、回滚

- 代码：`git revert` 本版五笔功能提交即可回到 `v0.4.0` 行为；`ImportColumnBinder` 与 `LenientJsonFormatMapper` 均为新增类，删除即恢复。
- 服务端：`cp -a app/api/intelligent-resume-server-0.4.0.jar` 已保留作回滚点，改回 `ExecStart` 指向它并重启。
- 数据：本版**不新增迁移、不改 schema**；写侧修复只影响后续新写入行的物理形态，历史行不动。
