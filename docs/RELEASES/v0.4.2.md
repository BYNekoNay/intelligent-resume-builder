## 一、版本范围

### 1. 导入正确性收官（批次 1.1 / 1.4）

1. **真实导出包导不进去**（P0）：稳定 ID 未注入、H2 JSON 列被当成 `JAVA_OBJECT`、`careerMaterials` 静默丢弃。
2. **嵌套集合不参与预览、父记录 SKIP 时子记录根本不写**（P0 数据丢失）：简历版本、投递状态历史
   全程不参与分类，父记录判 SKIP/CONFLICT 时包里的新版本直接消失。
3. 一并修掉 6 处相关缺陷：父 SKIP 时 `idMap` 未播种、`updateRecord` 传 `parentRecord=null`、
   3 处外键未重映射、值比较不归一 JSON/时间/数字、映射悬空后永久无法再导入。

口径（已写入 `docs/05` §18）：嵌套与顶层**同规则**；`added+skipped+conflicts == items.size()`；
父记录 SKIP 时子记录照自己的决策写入；同编号版本撞唯一键降级为 SKIP 且不改号。

### 2. 运维兑现（批次 2）

| 之前 | 现在 |
| --- | --- |
| 「每日备份 + 保留 14 天」只写在文档里，零实现 | `backup-database.sh` + 每日 03:30 timer，三道校验（gzip / 体积 / **dump 内建表数 == information_schema 表数**），保留 14 天，文件 600 + 目录 700 |
| 监控抓 `api:8080`（compose 服务名），直连部署永远解析不到 | prometheus 单进程抓 `127.0.0.1:8080`，7 天保留、只绑回环、`MemoryMax=256M` |
| systemd 同步只 glob `*.service`，`.timer` 永不生效 | 同步覆盖 `*.service` + `*.timer`，并在装完后 `enable --now` |

**刻意不上 Grafana / alertmanager**：宿主机 3.6G、swap 已吃 979MB，且与另一个项目共用。
代价写在 §四：**没有告警通道**。

首次恢复演练已执行：快照导入临时库 → 27 表 / 127 简历 / 82 条职业资料，比对后删库。

### 3. 门禁加固（批次 3）

- **行数棘轮扩到测试代码**：生产 ≤300、测试 ≤400；**每个扫描根各自有扫描下限**
  （不能只校验总数 —— 两场共 499 个文件，测试根被移走时总数仍达标，该根会静默失效）。基线 12 → 26 条。
- **vitest 落地**：6 个测试文件 / 29 条。其中 `errorCodes` 直接读后端 `ErrorCode.java` 对账 ——
  起因是原来的 `web/scripts/errorCodes.test.mjs` 是**孤儿测试**（不在任何 script/CI 里），已经红了很久
  （后端 13 个码、断言停在 11 个）。孤儿已迁走删除。
- **MySQL 8.4 全新迁移进 CI**：新增 `migration-84` job（`mysql:8.4` service）+ `scripts/assert-tests-ran.py`，
  **拒绝「跳过 = 通过」**（环境门控未生效时 `mvn` 退出码仍是 0，只看退出码会把「未验证」记成「通过」）。

### 4. 桌面工作区前端（批次 1.6）

`/desktop` 页面：本地备份（列表/创建/恢复，**恢复有二次确认**）、Web 导出包导入（预览分类 → 逐条决定冲突 → 应用）。
在线部署下入口隐藏、直接访问被守卫送回工作台（桌面端点不存在 → 404/401）。

两个后端契约陷阱已在代码与 e2e 里钉住：`POST /backups` 返回 **201**；`restore` 失败是 **HTTP 409 但信封 `code=0`**，
结论在 `data.ok`（按 `code` 判断会把失败当成功）。

### 5. 阶段五：本地 AI 设置 + DPAPI（R31 / R34）

- **V38 `local_ai_setting`**：只存非敏感设置。密钥**刻意不入表** —— 备份是整库 `SCRIPT TO`，
  密钥一旦入表就必然随备份与导出包出境，直接违反 R34。
- **真 DPAPI**（`CryptProtectData`，用户级 + 「应用:用户」派生 entropy）：密文存 `<dataDir>/ai-credentials/`。
  非 Windows **不降级为明文**，直接判不可用。
- 4 个端点：`GET/PUT/DELETE /api/desktop/ai-settings` 与 `POST .../test`（测试连接是**显式动作**且真发请求）。
- **保存即生效**：`AiRuntimeOverlay` 在 provider 的 6 个决策点生效，覆盖为空时行为与改造前逐字节一致；
  `enabled=false`/`DELETE` 回落到配置文件；启动时把已存设置装回去。

### 6. 阶段六：桌面壳骨架

`desktop-shell/`：`backend.js`（起 jar / 等就绪 / 停）+ `main.js`（窗口、单实例、退出清理）+ `smoke.mjs`。
加载策略 `loadURL('http://127.0.0.1:8082/')` —— 前端由同一个 jar 托管，**前端零改动**。

编排冒烟 6/6：22s 就绪、SPA 首页 200、`/api/desktop/ai-settings` 200、`SERVER__PORT` 未被劫持、退出无孤儿进程。

## 二、升级须知

1. **数据库**：V38 会随 Flyway 自动执行（新增 `local_ai_setting`）。无需手工操作。
2. **桌面端 AI 凭据**：从本版起密钥存在**数据目录的 DPAPI 密文文件**里，不在工作区库中。
   因此**恢复备份或迁移工作区后需要重新填写 API Key**（这是 R34 要求的，不是缺陷）。
3. **桌面端非 Windows 环境**：DPAPI 不可用，设置页会显示"凭据存储不可用"；此时 AI 仍走配置文件/环境变量。
4. **无破坏性接口变更**：新增端点只在 desktop profile 下存在，在线部署行为不变。

4. **备份不是异地容灾**：与数据库同机、未加密（靠文件权限 600/700）、无告警通道、恢复演练的季度节奏尚未自动化。
