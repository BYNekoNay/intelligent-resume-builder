## 一、需要你拍板的 5 条

### ⚑ D1. `POST /api/auth/logout-all` 是否让**已签发**的 access token 立即失效

**现状取证**（第四十八批实测）：撤销后该 token 仍可访问 `GET /api/auth/me` → **HTTP 200**，
直到自身 `exp`（`JWT_ACCESS_TTL=3600s`）。原因：access token 是**无状态 JWT 且不含会话标识**，
`auth_session.revoked_at` 不在请求链路上。文档措辞已按实测更正。
**注意**：这与**删号**不同 —— 删号把用户置 `DISABLED`，鉴权按用户状态即时拒绝（已有测试守护）。

| 选项 | 做法 | 代价 |
| --- | --- | --- |
| **A** | 维持现状 | 零成本。该接口**无前端入口**（暴露面仅为直接调用方）；已更正文档 |
| **B** | access token 加会话标识或 `iat` 水位 + 缓存「最近 logout-all 时刻」，鉴权时比较 | 每请求一次水位比较 + 时钟偏移处理；立即性受 30s 缓存 TTL 约束，需留宽限窗口，否则可能**误踢刚签发**的 token |
| **C** | 以「删号/停用」作为丢失设备兜底（**已即时失效**） | 零成本，语义上是"改用途"而非"改实现" |

**我的建议：A + C 组合**（维持 A 的实现，在文档里明确指向 C 作为兜底路径）。
理由：B 的收益（60 分钟内失效 vs 立即失效）与代价（每请求比较 + 时钟偏移 + 误踢风险）不成比例，
而"丢失设备"这一真实场景已有 C 这条**更强**的路径。
**答辩风险**：若被问"为什么不做即时失效"，答案要包含"无状态 JWT 的取舍 + 已有删号兜底"，不能只说"没做"。

### ⚑ D3. 短 JD 的语义：`jd-text.min-length`（默认 20，声明但无消费点）

**现状取证**（第五十三批）：`JobDescriptionService` 只读 `max-length`；

### 4.2 三项新决策

#### D6. 未列入 `items` 的 selected 素材：采显式 409

**结论**：`decision == null`（selected 有、items 无）抛 `40903 SELECTION_ITEM_UNKNOWN`；`decision != ACCEPT` 仍 `continue`（合法的用户拒绝）。

> **2026-10-29 落地更正**：码值取 **`40904`** —— 登记时未核对，`40903` 已被 `ACCOUNT_DELETION_WINDOW_EXPIRED` 占用（前端 `errorCodes.ts` 亦已映射该值），沿用会让两套文案撞车。实现与前置调查结论见 [ADR-013](./ADR-013-reject-selection-unknown.md)：前端 `items` 为全量映射（`draftItems.map`），**不存在**合法的部分提交路径。

**证据**：`DraftCommitService.java:196-203` 的 `continue` 让「用户勾 5 条、只提交 3 条」这类客户端 bug 静默变成「版本已落地但少 2 条溯源引用」，且无回滚路径。409 与既有 `40901` 家族同语义（客户端持有的选择集已过期）；400 不表达「可重取后重试」。

**代价**：后端 2 文件 + 错误码 + 前端映射/文案 + `docs/05` + 1 个 IT。无 DB 迁移。**改 API 行为**。

**前置**：先确认前端 `confirm-materials` 的 `selected` 与 `items` 是否恒同源；若存在合法的部分提交路径，必须先改前端，否则 409 会打断真实流程。

**何时复审**：若产品后续认定「部分确认」为合法语义，本决策反向 —— 改回 `continue` 但补显式警告字段。

#### D7. `selection_reason` 取值域：封闭为两值

**结论**：只允许 `AI_REFERENCED` / `USER_EDITED`；服务端归一化，未知值拒绝（不静默兜底）。

**证据**：全仓仅两处写入点（`JobGenerationService:452`、`DraftCommitService:452`），无第三值来源。当前把客户端传来的 `selectedReason` 直接透传入库，等于把溯源字段的取值域交给调用方决定。

**代价**：后端常量类 + 归一化（2 文件）、前端联合类型、`docs/04`、1 个双向门禁。无迁移。

**何时复审**：出现第三类来源（例如用户在编辑器里手工新增引用）时重开。

#### D8. 重试系列端点不纳入 `X-AI-Preview-Token`

**结论**：不纳入。`/api/optimize/tasks/{id}/retry` 与 `/api/interviews/{id}/ai/retry` 只重跑已落库的输入快照 / 同一场会话。

**证据**：令牌的价值是「让你看到将发送的内容」；这两个入口重跑的内容与上次逐字相同，令牌只增加一次点击。且 `AtsAiStarter` 的 `ai-retry` **本就**要求先 preview —— `docs/RELEASES/v0.4.4.md` §四·3 把它列为「未纳入」是不准确的。

**判断树**（实现时按此判定，不拍脑袋）：若某个 retry 会**重新组装 prompt**（如换模型重跑改 messages），则该端点**必须**纳入令牌，并在 `docs/05` 写明「重试前的预览可能与此前不同」。

**代价**：0 行生产代码；1 个门禁钉住「retry 不重新组装 prompt」；`docs/05` 两处措辞。

**何时复审**：新增任何「换模型重跑」或「改参数重跑」入口时。
