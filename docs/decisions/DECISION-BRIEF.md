## 一、需要你拍板的 5 条

### ⚑ D1. `POST /api/auth/logout-all` 是否让**已签发**的 access token 立即失效

**现状取证**（第四十八批实测）：撤销后该 token 仍可访问 `GET /api/auth/me` → **HTTP 200**，
直到自身 `exp`（`JWT_ACCESS_TTL=3600s`）。原因：access token 是**无状态 JWT 且不含会话标识**，
`auth_session.revoked_at` 不在请求链路上。文档措辞已按实测更正。
**注意**：这与**删号**不同 —— 删号把用户置 `DISABLED`，鉴权按用户状态即时拒绝（已有测试守护）。

| 选项 | 做法 | 代价 |
| --- | --- | --- |
| **A** | 维持现状 | 零成本。该接口**无前端入口**（暴露面仅为直接调用方）；已更正文档 |
| **B** | access token 加会话标识或 `iat` 水位 + 缓存「最近 logout-all 时刻」，鉴权时比较 | 每请求一次水位比较 + 时钟偏移处理；立即性受 30s 缓存 TTL 约束，需留宽限窗口，否则可能**误踢刚签发**的 token |
| **C** | 以「删号/停用」作为丢失设备兜底（**已即时失效**） | 零成本，语义上是"改用途"而非"改实现" |

**我的建议：A + C 组合**（维持 A 的实现，在文档里明确指向 C 作为兜底路径）。
理由：B 的收益（60 分钟内失效 vs 立即失效）与代价（每请求比较 + 时钟偏移 + 误踢风险）不成比例，
而"丢失设备"这一真实场景已有 C 这条**更强**的路径。
**答辩风险**：若被问"为什么不做即时失效"，答案要包含"无状态 JWT 的取舍 + 已有删号兜底"，不能只说"没做"。

### ⚑ D2. 数据生命周期的**硬删口径**（`docs/04` §7.1/§7.2 承诺尚未实现）

**现状取证**（第四十九批）：全仓 `@Scheduled` 仅 3 处（AI 任务留存、PDF 过期、导出过期），
**无任何软删资源清扫作业**；`account_deletion_job` 表在 `V1~V34` 中不存在（§7.2 是设计草案）；
`AuthService.deleteAccount` 是**同步**路径，不存在可撤销窗口。已按现状标注，并由
`RetentionPolicyContractTest` 守护（承诺在无实现时不得移除"计划中"标注）。

| 选项 | 做法 | 代价 |
| --- | --- | --- |
| **A** | 实现**分级清扫**：无引用者直接硬删；被引用者转最小不可编辑快照 + 匿名化 | 最高。需先定义每个资源"被引用时的保留边界"，并处理跨表级联与护栏 |
| **B** | 只实现**无引用资源**清扫；被引用者长期保留，并据此改写文档承诺 | 中。实现可控，但承诺要分档表述 |
| **C** | 维持现状（长期保留软删行），**按现状改承诺**（不再声明硬删期限） | 最低。但"数据可被彻底删除"这一常见合规诉求将无实现 |

**我的建议：B**（分档承诺：无引用者按期硬删、被引用者保留最小快照）。
理由：A 的级联硬删会破坏历史可读性与审计（评分/ATS/面试/投递都引用版本）；
C 则让"删除权"名存实亡。B 是**可实现 + 可解释**的中间态。
**前置**：需要你确认"**被引用数据允不允许保留**"——这是合规口径，不是技术选择。

### ⚑ D3. 短 JD 的语义：`jd-text.min-length`（默认 20，声明但无消费点）

**现状取证**（第五十三批）：`JobDescriptionService` 只读 `max-length`；
`JdKeywordParser.parse` 只判 `null/isBlank`。设计意图见
`docs/agent-tasks/T05-JD管理.md:97`「太短视为空，允许解析但关键词为空」→ 是**解析器阈值**，
不是入参拒绝。该键现由 `ConfigConsumerContractTest` 白名单登记。

| 选项 | 做法 | 代价 |
| --- | --- | --- |
| **A** | 在 `JdKeywordParser` 实现「短于阈值 → role/keywords/requirements 全空」 | 低。与 T05 设计一致；但短 JD 的 ATS/匹配分会**系统性偏低**（无关键词可取） |
| **B** | 改为入参拒绝（短 JD 直接 400） | 低，但**与 T05 语义相反**，且会拒绝合法短 JD（如"招 Java 工程师"） |
| **C** | 移除该键（承认不实施） | 最低。但丢掉了一个本可用的产品调节点 |

**我的建议：A**。理由：与已落盘的 T05 设计一致，且"短 JD 无有效关键词"本身就是事实
（不是人为限制）；C 会让"最小长度"这个直觉上的产品参数无处可调。

`ConfirmRequest` 的 `@Size(max = 200)` 硬编码实现** → **不存在"提交条数无上限"的风险**。

### ⚑ D5. ATS 分析 **600s 读超时尾部**：超时后用户应看到什么

**现状取证**（ADR-006 §6）：实测 Arm R 1/12 撞满 600.102s；直连中位 97s、生产任务级 212–405s。
本轮判定**保留推理**（不解除慢）。`BAILIAN_READ_TIMEOUT_S=300`、链总预算 600s。

| 选项 | 做法 | 代价 |
| --- | --- | --- |
| **A** | 超时 → 任务标记失败 + 前端展示"AI 分析超时，可重试"，**降级为纯规则分** | 中。用户总有结果可看；但需前端配合 |
| **B** | 超时 → 继续后台等待至成功（无上限） | 低。但用户可能长时间无结果，且占额度 |
| **C** | 超时 → 按现状（`AI_ACTION_REQUIRED` + `aiFailure` 暴露，界面已渲染重试/重新授权入口） | 零。**当前实现即如此**，只是未把它写成产品口径 |

**我的建议：C（把现状固化为口径）+ 补 A 的降级兜底**。
理由：现状已经做到了"失败可见 + 可重试"（`aiFailure` 会暴露 `retryable`/`reauthorizationRequired`），
真正缺的是**用户拿不到规则分兜底**。若时间紧，先选 C（零改动，只补文档口径）。
