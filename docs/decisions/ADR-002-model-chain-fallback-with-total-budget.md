# ADR-002: 模型链采用严格降级 + 总时间预算

## Status: Accepted (2026-09-23)

## Background

由 ADR-001 派生：既然额度按模型计量，就需要"按序尝试、失败顺延"的调度。
同时实测暴露两个必须一起解决的问题：

1. **失败必须分类**：`403` 在过去一律归为 `PROVIDER_4XX`，导致「密钥无效」与
   「额度耗尽」无法区分 —— 前者换模型也没用（应立即终止），后者换模型即可恢复（应顺延）。
2. **耗时必须有上界**：单次读超时 300s × 链长 8 = 最坏 40 分钟，而 worker 处理单条任务
   期间会一直占住线程，后续 AI 任务全部排队（head-of-line blocking）。实测生成任务
   在链首超时 300s 后顺延，总耗时 477s。

## Decision

采用**严格降级链**（不做轮询分摊、不做额度优先级）：

1. 按配置顺序取当前未处于冷却期的模型，**首个成功即返回**。
2. 失败按错误码分类判定动作：
   - 额度耗尽 / 模型下线 → 顺延 + **长冷却**（默认 1800s，额度不会短期恢复）
   - 超时 / 连接失败 / 5xx / 限流 / 空响应 → 顺延 + **短冷却**（默认 60s）
   - 密钥无效 / 请求参数非法 → **立即终止**（换模型无济于事，避免白耗额度）
3. 引入**链总时间预算**（`AI_CHAIN_TOTAL_BUDGET_S`，默认 600s）：每次顺延前检查已耗时，
   超预算即停止并快速失败（可重试），交 worker 重试机制稍后再跑。
   下限由构造器保证 `max(配置值, readTimeout)`。
4. 全部模型处于冷却期时**快速失败**，不做 8 轮无效探测。

## Consequences

**正面**
- 单模型失效可自愈；实测「链首 300s 超时 → 顺延成功」已救回原本必然失败的任务。
- 最坏阻塞从理论 2400s 压到约 600s。
- 密钥类故障不再浪费其余模型的额度。

**负面**
- **最坏耗时仍达 ~477s**（300s 超时 + 顺延），远超用户耐心，需前端配合（ADR-004）。
- 链首选择不经任务类型区分，导致生成这类大 prompt 任务每次都先在慢模型上白等 300s
  （已登记为 OPEN-DECISIONS 待评估项）。
- 冷却状态仅存内存，重启后清空 —— 接受该取舍（重启后重新探测一轮代价有限）。
