# 部署与运维说明书

## 1. 文档目标

本文件用于规范项目在开发、测试、预发布、正式环境中的部署方式、运行依赖、配置管理、监控方案与故障处理方式。

## 2. 环境规划

### 2.1 开发环境

建议组成：

- 前端本地运行
- 后端本地运行
- 本地 MySQL
- 本地 Node.js 导出服务

用途：

- 单人开发
- 日常联调
- 快速排查问题

### 2.2 测试环境

建议组成：

- 后端部署实例

- 独立文件输出目录

用途：

- 联调测试
- 功能测试
- 验收测试

### 2.3 预发布/演示环境

建议组成：

- 与正式环境接近
- 保留监控和日志
- 保留导出与 AI 配置

用途：

- 项目展示
- 面试演示
- 正式发布前验证

### 2.4 正式环境

建议组成：

- 前端 CDN 或 Nginx 静态资源

用途：

- 面向真实用户的生产服务

正式环境必须满足 §10.1 生产基线要求。

## 3. 部署结构建议

### 3.1 MVP 部署结构

```text
Nginx
├─ 前端静态资源
└─ 反向代理后端 API

Spring Boot API
├─ 业务主服务
└─ 内嵌工作器（数据库轮询线程池）

Node.js PDF Service
└─ Puppeteer 导出服务

MySQL
└─ 数据存储
```

MVP 阶段使用数据库轮询工作器（来源：03 §9.5），以内嵌线程池方式运行在 Spring Boot 应用内，不需要独立进程。工作器通过原子 SQL 抢占 PENDING 或租约过期任务；应用重启后，租约过期的 RUNNING 任务自动回到可重试状态。后续若任务量增长，可将工作器拆为独立进程（见 03 §7.2）。

### 3.2 后续增强结构

可在后续加入：

- Redis
- MQ
- Prometheus
- Grafana
- Alertmanager

### 3.3 网络分区

PDF 服务只监听私有网络接口（127.0.0.1 或内网 IP），不直接暴露给浏览器（来源：03 §9.7）。Nginx 作为唯一公网入口，反向代理后端 API。后端调用 PDF 服务走私有网络并携带轮换服务令牌。正式环境所有外部流量强制 HTTPS（来源：03 §9.8）。

该要求由 `PDF_SERVICE_HOST` 在应用层落实，两条交付路径的取值相反：**直连部署**（宿主机 systemd + 本机 nginx）由 `deploy/systemd/intelligent-resume-pdf.service` 注入 `Environment=PDF_SERVICE_HOST=127.0.0.1`——与 api 单元的 `Environment=SERVER_ADDRESS=127.0.0.1` 同口径，都必须作为真实环境变量注入而非只写 `.env`（`.env` 只对 `application.yml` 里写了 `${NAME}` 占位符的项生效，服务端未声明 `server.address` 时会被静默忽略）；**容器部署**（`deploy/docker-compose.prod.yml`）必须**不设置**该项——API 容器在私有网络内经服务名访问本服务（`PDF_SERVICE_BASE_URL=http://pdf-service:3001`），收敛到回环会让导出整体不可用。缺省（未设置）时 Node 绑定所有接口，服务启动日志会打出实际绑定地址，须与 `ss -lntp` 核对（`127.0.0.1:3001` 而非 `*:3001`）；该跨运行时契约由 `PdfServiceBindScopeContractTest` 静态门禁守护。

## 4. 配置管理

建议区分以下配置：

- 数据库配置
- JWT 配置
- AI 提供商配置
- AI 数据处理同意版本、提供商地区和数据留存配置
- 用户、IP、任务类型的限流与配额配置
- 反向代理与客户端 IP 契约：正式环境必须开启 `RATE_LIMIT_TRUST_FORWARDED_HEADERS`（prod profile 启动校验强制），且最外层 Nginx 需用 `$remote_addr` 覆写 `X-Forwarded-For`（阻断客户端伪造）、内层代理继续追加——限流分桶与会话审计依赖该链路取到真实客户端 IP；不开启会让所有客户端共用代理地址一个分桶（全站共享阈值）
- 文件输出路径
- PDF 导出配置
- 日志级别

代理层体积契约：三层 Nginx（`edge` → `web` → API）都必须显式声明 `client_max_body_size`（内置默认仅 `1m`）且不小于应用**整请求**上限 `spring.servlet.multipart.max-request-size`（6MB，而非单文件上限 5MB——该指令限制整个请求体含 multipart 开销）；漏声明或按单文件上限对齐会让内层悄悄收紧，上传在边界处被拒且返回 nginx 自带页面（非统一信封）。该关系由 `UploadPathContractTest` 静态门禁守护。

响应压缩契约：**接口**响应的压缩在应用层开启（`server.compression.enabled=true`，覆盖 `application/json` 等文本类 mime，`min-response-size` 2KB）——JSON 响应重复度高，实测账号导出（200 条 63KB 散文式职业资料）单次响应 **12.77MB → gzip 2.14MB（约 6×）**，列表类响应更高，同一份数据在慢网络下也不再触达客户端读超时。反代层无需对同一响应再开 gzip（已带 `Content-Encoding` 的响应不会被二次压缩）；静态资源由 web 容器经 Nginx 直接提供、不经应用，如需压缩应在 Nginx 侧单独开启。该关系由 `ResponseCompressionContractTest` 静态门禁守护。

静态资源交付契约：服务 SPA 产物的三层配置（`web/nginx.conf`＝镜像内实际生效的一份、`deploy/nginx/web.conf`＝部署侧同步副本、`deploy/nginx/host.conf`＝宿主机直连版）必须一致地满足三点：①开启 gzip（`gzip on` + `gzip_vary on`，`gzip_types` 含 `application/javascript` 与 `text/css`——nginx 默认只压 `text/html`）；②对**带内容哈希**的产物（`location ~* \.(js|css|woff2?|png|jpg|jpeg|svg|ico)$`）给 `public, immutable` + 长有效期；③SPA 回退入口（`location /`）保持 `Cache-Control: no-cache`，保证发版后立即引用新的哈希文件名。收益实测（同一份 `web/dist`）：64 个 js/css/svg **1001.1KB → gzip 285.5KB（3.51×）**，首屏入口 5 个文件 **457.4KB → 139.8KB**；漏掉②会让 60+ 个哈希产物每次导航逐个回源校验。契约由 `StaticAssetDeliveryContractTest` 守护。`gzip_proxied` 保持默认 `off`：本层不给 `/api/` 反代响应做二次压缩（接口压缩在应用层，见上一条）。

安全响应头交付契约（第六十九批补）：4 条头（`X-Content-Type-Options` / `X-Frame-Options` / `Referrer-Policy` / `Content-Security-Policy-Report-Only`，均带 `always`）集中在 `deploy/nginx/security-headers.conf`，由**每条对外生效的配置**在 `server` 级 include 一次；且**凡自带 `add_header` 的 `location` 必须在该 `location` 内再 include 一次** —— nginx 的 `add_header` **不跨层级累加**，`location` 内一旦有自己的 `add_header`（如 `Cache-Control`），server 级那 4 条对该 location **整体失效**，而 `nginx -t` 照样通过、探针也看不见（探针只看进程级事实）。契约由 `SecurityHeaderDeliveryContractTest` 守护（片段完整性 / server 级 / 继承陷阱的 location 级 / include 指向真实文件）。

> **一处刻意保留的不对称（已记录取舍）**：`web/nginx.conf`（镜像内实际生效的一份，`web/Dockerfile` COPY 进 `/etc/nginx/conf.d/`）**不** include 安全头片段 —— 它的构建上下文是 `web/`，**拿不到** `deploy/nginx/` 下的片段。合并成单一来源需要把 compose 的 build context 提到仓库根（`web/build.context: ../web` → 根目录并调整 Dockerfile 路径），而容器拓扑在当前环境未用于生产、代价与收益不成比例，故**保留不对称 + 用门禁固定住**：
> - 容器拓扑 `edge → web → api` 中由**最外层 `edge` 统一下发**（`deploy/nginx/edge.conf` 已在 server 级 include）；
> - 门禁断言 `web/nginx.conf` **不得**出现 `include snippets/...`：万一有人为了「消除不对称」把它加上，镜像**构建照样成功**（只是 COPY 一个文件），但容器**启动时 nginx 直接退出**（`open() ".../snippets/security-headers.conf" failed`）—— 这是构建期与全部自动化都看不见的失败，正是本门禁要挡住的那一类。

容器资源边界契约：生产 compose（`deploy/docker-compose.prod.yml`）的**每个服务**都必须声明 `mem_limit` 与有界日志（顶部 `x-logging` 锚点：json-file + `max-size 10m` × `max-file 5` = 每容器 ≤50MB）——docker 默认 json-file 驱动**不轮转**，而 systemd 路径已显式用 journald 轮转（`deploy/systemd/*.service`），两条交付路径的边界必须一致。API 的 `JAVA_TOOL_OPTIONS` 必须显式给 `-Xmx`（与 systemd 单元同为 `-Xmx768m`），且 `mem_limit ≥ 堆上限 + 256m` 元空间/线程余量：未指定 `-Xmx` 时 JVM 按可用内存的 25% 默认（本机实测 15.71GiB → `MaxHeapSize=4219469824` 字节），3.6GiB 宿主上等价 **≈922MB**，高于该宿主刻意压到的 768m。`deploy/docker-compose.ip-test.yml` 是**叠加层**（`-f prod -f ip-test` 合并使用）：日志上限继承基础文件，内存上限按验收环境覆盖（api 512m 堆 / 800m 上限）。契约由 `ComposeResourceBoundsContractTest` 守护。

配置原则：

- 不在代码中硬编码密钥
- 环境间配置分离
- 敏感配置通过环境变量或外部配置文件传入
- 正式环境必须记录密钥所有者、轮换周期和最近轮换时间；轮换不得要求重新构建镜像
- **数值型运维配置必须为正**：`NumericConfigurationValidator` 在启动时校验限流阈值（login/register/refresh/resume-import-parse/jd-parse/change-credential/account-export + max-buckets）、AI 任务留存（retention-days / cleanup-batch-size / cleanup-max-rows-per-run / cleanup-interval-ms）、PDF 过期清理（cleanup-batch-size / cleanup-interval-ms）与数据生命周期分档清扫（retention/purge 的 batch-size / interval-ms，以及 recovery-days / grace-days 下限为 0）共 18 个键，取非法值直接启动失败——这些键由环境变量注入，`@Value` 只保证「能解析成整数」，0/负值会被静默接受并表现为：清理作业每次抛 `PageRequest` 异常、续批上限 0 导致静默不清理、保留期 0 天导致刚建任务立刻被压缩、恢复期负值导致**尚未超期**的软删数据被提前纳入删除候选、限流阈值为 0 导致对应端点永久 429（应用健康检查却仍 200）。该表在启动时还会自检「键是否都解析到」，防配置解析路径失效后门禁静默空转。
- **配置的三种失效形态都必须有门禁**：① `@Value("${key:fallback}")` 的兜底值与 yml 默认不一致；② `@ConfigurationProperties` 的**数值/布尔字段**默认值与 yml 默认不一致（① ② 都表现为「配置缺省时静默采用另一个值」）；③ 键在 yml 声明却**没有任何消费点**（**声明即虚构**：改它不生效，却让运维以为可配）。① ② 由 `ConfigFallbackContractTest` 两个用例守护，③ 由 `ConfigConsumerContractTest` 守护（未实现项必须显式登记进 `KNOWN_UNCONSUMED` 白名单并附理由，且一旦获得消费点门禁会要求移出白名单，防白名单腐化）。按此清理：`app.pdf.max-output-bytes` 补消费点与 pdf-service 第二道闸（第五十二批）、`app.ai.worker.lease-seconds` 字段默认 180→660（第五十三批；yml 早在第一批 #60 已是 660，只改了 yml 漏改绑定类）、移除死键 `app.ai.quota.JOB_MATERIAL_SELECTION`（与 JOB_GENERATION 共用额度）与 `app.job.parser.rule-version`（第五十三批）。另外，**环境变量样例（`server/.env.example`）是配置的第三个来源**（前两个是代码 `@Value` 兜底与 yml 默认值）：样例键若无 yml 占位符会被**静默忽略**、样例值与该键的 yml 默认不一致则**照抄即踩坑** —— 由 `EnvExampleContractTest` 守护（第五十四批清理：移除死键 `AI_MOCK_FAIL_RATE`/`AI_MOCK_LATENCY_MS`，修正样例 `AI_WORKER_LEASE_S` 60→660，后者照抄会把租约压到链总预算 600s 之下）。列表型默认值（含逗号，如 `CORS_ALLOWED_ORIGINS`）跳过值比对：样例给出最小可用子集是合理的。
- **文本判据必须在「已抹白注释」的文本上运行**（第六十六批）：上述门禁普遍用「在文件全文里找某个 token」作判据，而**注释里的同名文本会让它假绿**。已实测确认：`ConfigConsumerContractTest` 曾把 `JdKeywordParser` javadoc 里的 `app.job.jd-text.min-length` 当成消费点 —— 把真正的 `@Value` 去掉后门禁**仍然通过**；而它守护的正是上一条的「键声明了就必须有消费点」。现所有门禁读源码/配置统一走 `SourceText.read(...)`，按扩展名识别注释风格（C 风格 `//` 与 `/* */`、`#`、SQL `--`），且**原地抹成等长空白**而不是删除 —— 因为部分判据是**距离窗口**式的（如「`@Transactional` 之后 300 字符内不得出现 X」），删注释会缩短文本、让窗口变紧从而制造**假红**（实测把 `ExportStreamingContractTest` 由绿变红）。`SourceText` 是**词法级**实现（跟踪字符串/字符字面量与 Java 文本块 `"""`），故 `"http://host"` 里的 `//`、`'a--b'`、`"a#b"` 都不会被误当注释，而 `@Scheduled(fixedDelayString = "${app.x.y:1}")` 这类**字符串里的真实消费点**也不会丢失；未知扩展名与 `.md`/`.json` 原样返回。自测见 `SourceTextTest`（含「等长/换行守恒」与「字符串保留」两个方向的断言）。残留：字符串字面量里的 token 仍算命中（多数命中本身即合法消费点）。

## 6. 日志规范

建议至少保留以下日志：

- 应用启动日志
- 登录与鉴权异常日志
- AI 调用日志
- 职业资料筛选与岗位定制生成日志（仅记录任务、资料 ID 和结果状态）
- 评分执行日志
- ATS 体检、成果量化、沟通文案和投递状态变更日志
- 面试答案资产创建日志
- PDF 导出日志
- 全局异常日志
- **上游细节日志（第六十九批）**：AI / PDF 链路的失败原文不再回给客户端（见 `docs/05` §1.3 的「失败文案的公开边界」），
  改为记进日志：`Business failure with provider detail, code=<50002|50003>, traceId=…, raw=…`（WARN 级）。
  排查 AI/PDF 失败时以这行为准（同一 traceId 可与响应里的 `traceId` 对上）；`ai_task.error_message` /
  `export_task.error_message` 两列也仍保留原文（截断到 1000 字符）

注意事项：

- 日志中不得打印密码、Token、敏感原文
- AI 请求体如包含简历原文，需避免完整打印
- 日志只记录提供商、模型、同意版本、任务类型、脱敏摘要和配额消耗，不记录完整资料、JD、面试回答或文案

## 7. 监控建议

### 7.1 基础监控

- 服务是否存活
- API 响应时间
- 错误率
- 认证失败率、限流命中率和 AI 配额消耗
- 导出成功率

建议阈值（与 `monitoring/prometheus/rules/intelligent-resume-alerts.yml` 中的规则一一对应，条数与分级由 `AlertRuleContractTest` 静态门禁守护）：

- **API 可用性**：抓取失败（`up == 0`）持续 ≈1 分钟（4 个抓取周期）触发严重告警；抓取目标整体消失（`absent(up)`，配置漂移/目标被移除）10 分钟后触发警告。该条不可省略——其余规则全部建立在应用自身导出的指标上，应用不可用时这些序列随抓取失败一起消失（`rate`/`histogram_quantile` 在空区间返回空向量、gauge 走 staleness），「整机不可用」将没有任何告警，`up` 是唯一不受此影响的可用性信号
- API p95 响应时间：超过 500ms 触发警告，超过 2s 触发严重告警
- 错误率（5xx）：超过 1% 触发警告，超过 5% 触发严重告警
- AI 任务成功率：低于 95% 触发警告
- AI 模型链可用模型数：≤2 触发警告，≤0 触发严重告警
- PDF 导出成功率：低于 90% 触发警告
- 限流/配额拒绝率：超过 10% 触发警告
- 队列积压：AI 待处理 >20 或最老待处理 >300s、PDF 待处理 >10 或最老待处理 >300s 触发警告

### 7.2 增强监控

- AI 调用耗时
- 岗位定制生成成功率和资料选择耗时
- ATS 体检、成果量化和沟通文案生成耗时及失败率
- 投递状态变更失败率和答案资产创建成功率
- 导出耗时
- 任务队列积压情况
- 缓存命中率

### 7.3 监控栈落地（可选）

监控与告警组件（Prometheus、Grafana、Alertmanager）位于 `monitoring/`，默认不随主栈启动，使用 Compose profile 显式启用。部署目录下执行：

```bash
# 仅启动监控三件套（主栈需已运行）
docker compose --env-file production.env \
  --profile monitoring up -d prometheus grafana alertmanager

# 或连同主栈一起启动
docker compose --env-file production.env \
  --profile monitoring up -d
```

启动后健康检查：

```bash
docker compose exec prometheus wget -qO- http://localhost:9090/-/healthy  # Prometheus（容器内探测，未映射宿主机端口）
curl -fsS http://127.0.0.1:9093/-/healthy   # Alertmanager（仅本机回环）
# Grafana 通过 Edge 反代访问 https://<PUBLIC_HOST>/grafana/
```

告警链路：

1. Prometheus 按 `monitoring/prometheus/rules/*.yml` 评估 15 条告警规则（可用性、成功率、错误率、延迟、模型链、队列积压）；规则引用的指标名必须与 `AppObservability` 注册的一致、可用性规则必须用抓取配置里的 job 名且容忍 ≥3 次抓取失败、`severity` 必须能被 `alertmanager.yml` 的路由匹配器接住、§7.1 承诺的分级阈值必须都在——以上由 `AlertRuleContractTest` 静态门禁守护（指标改名或删掉一级阈值即红）
2. 命中规则后推送至 Alertmanager（`alertmanager:9093`）
3. Alertmanager 按 `severity` 路由：`critical` → 邮件 + Webhook，`warning` → Webhook；Webhook 用于对接钉钉/企业微信机器人

告警渠道配置：所有敏感值（机器人 Webhook URL、SMTP 凭据）从环境变量注入，见 `deploy/production.env.example` 中 `ALERTMANAGER_WEBHOOK_URL`、`SMTP_*` 各项。提交到仓库的 `monitoring/alertmanager/alertmanager.yml` 只含占位符，容器启动时由 `monitoring/alertmanager/entrypoint.sh` 渲染后启动 Alertmanager；未配置告警渠道时监控栈仍可启动，仅告警不会真正送达（Alertmanager 日志会记录投递失败）。

## 8. 文件管理建议

- PDF 文件统一保存到固定目录
- ~~文件名建议带任务 ID、用户 ID、时间戳~~（该建议与下一行直接冲突，已被取代：落盘文件名＝随机存储键，任务/用户关联由数据库列承载〔`export_task.storage_key` / `user_id`〕，实现从未采用该建议）

- 文件必须使用私有存储标识；仅通过受控下载或短时签名地址提供给资源所属用户

## 9. 故障处理建议

### 9.1 AI 调用失败

处理策略：

- 返回明确错误提示
- 保留错误日志和任务记录
- 支持重试
- 提供商不可用、用户未同意或配额不足时，明确返回不可执行状态，不发送用户内容

### 9.2 岗位定制生成失败

处理策略：

- 保留任务状态、JD ID 和资料选择上下文，避免记录完整敏感资料原文
- 返回可重试状态；资料不足时返回缺失项提示而非生成虚构内容
- 不覆盖用户资料和已有简历版本

### 9.3 ATS、沟通文案或成果量化失败

处理策略：

- 返回明确失败状态，保留可重试任务记录
- 成果量化未确认时不更新资料或简历；沟通文案失败不影响投递记录
- 日志不得记录完整简历、资料或沟通文案原文

### 9.4 PDF 导出失败

处理策略：

- 记录模板和渲染上下文
- 返回导出失败状态
- 可重新发起导出

### 9.5 数据库连接异常

处理策略：

- 启动时检查连接
- 运行时记录异常
- 及时阻断高风险写操作

### 9.6 数据删除与保留

处理策略：

- 资源删除先软删，再按保留期异步清理数据库记录和私有导出文件
- 历史版本和审计所需的上下文只保留不可编辑快照，禁止继续作为 AI 输入
- 账户删除任务应记录完成状态，失败时可重试并告警
- 职业资料（`career_material`）、简历版本（`resume_version`）、简历主记录与 JD（`resume` / `job_description`）软删恢复期 30 天，恢复期结束后 7 天内处置：**无引用者物理删除、被引用者转最小不可编辑快照 —— 两档均已实施**（决策 D2 阶段 1 + 阶段 2 + 阶段 2b，默认 `app.retention.purge.enabled=false` + `dry-run=true`，两条护栏都落在「不写数据」一侧；数值键由 `NumericConfigurationValidator` 在启动时校验）。投递/面试数据的硬删仍**计划中，尚未实现**（见 `docs/decisions/OPEN-DECISIONS.md` 生命周期条目）。AI 任务原始输入和结果完成 90 天后删除非必要内容（默认 `app.ai.task.retention-days=90`，已实现）。账户删除 7 天撤销窗口、窗口结束后 30 天内完成清理（**计划中，尚未实现**：当前为立即停用 + 立即清理，见 `docs/05` §2.7 与实际实现一致的口径）。（来源：04 §7.1）
- **浏览器本地残留同样属于「用户数据」**：退出登录与删除账号都在客户端同步清理该账号在浏览器里持久化的数据（清单集中在 `web/src/utils/localUserData.ts`：编辑器草稿＝完整简历 JSON〔含姓名/联系方式/工作经历〕、待恢复的 AI 任务 id、导入解析出的简历原文、沟通/投递文案草稿、当前面试会话 id）。不清的理由只有「共享设备上换人使用仍能读到上一账号的 PII」与「删号后本地仍留有副本」两条，二者都不可接受；用户无关的键（界面语言、侧栏折叠状态）刻意保留。该行为由 `web/e2e/privacy-local-data.spec.ts`（登出 / 删号两条路径）守护。

## 10. 发布流程建议

建议流程：

1. 完成功能开发并同步数据库、接口、测试和运维文档
2. 执行单元、集成、端到端、安全和迁移测试
3. 生成不可变构建产物并记录版本
4. 备份数据库并验证最近一次恢复演练成功
5. 在测试环境执行 Flyway 迁移、启动检查和主流程验证
6. 记录回滚版本；迁移不兼容时禁止发布
7. 部署正式环境，验证 readiness/health、错误率和任务积压
8. 发布异常时回滚应用；数据库变更按迁移说明执行前向修复或已验证的回滚

### 10.1 生产基线

- Nginx 终止 TLS，启用 HSTS；MySQL、PDF 服务和管理端口不得暴露公网（应用层监听地址的落实方式见 §3.3：直连部署用 `PDF_SERVICE_HOST=127.0.0.1` + `SERVER_ADDRESS=127.0.0.1`，容器部署不设置、由私有网络隔离）。
- 每日加密备份，RPO 24 小时、RTO 4 小时；至少每季度执行一次恢复演练。
- 后端和 PDF 服务必须配置 CPU、内存、并发和超时上限。
- 数据库、AI、PDF 和文件存储均需 readiness 检查；依赖不可用时阻止高风险写操作。

### 10.2 CI/CD 与容器化建议

建议使用 GitHub Actions 或 Gitee Go 实现基本 CI 流水线：推送触发 → 后端 mvn test → 前端 npm run build → PDF 服务 npm run check。MVP 阶段可使用 Docker Compose 编排本地和测试环境（项目根目录已提供 docker-compose.yml），但不作为正式部署的强制要求。Kubernetes 不在当前范围内（来源：01 §3.3）。

## 11. 运维检查清单

- 服务是否成功启动
- 数据库连接是否正常
- AI 配置是否有效

- ATS、投递和面试资产接口是否正常，且无自动对外发送行为
- 导出路径是否可写
- 文件下载是否正常
- 私有下载、账号删除、AI 同意和配额限制是否按预期生效
- 前后端接口是否联通
