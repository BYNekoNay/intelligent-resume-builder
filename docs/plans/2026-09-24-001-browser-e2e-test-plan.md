## 0. 执行者须知（先读，违反会导致结果不可用）

### 0.1 你的角色

你以**真实用户**身份操作浏览器，全程只通过 UI 交互（点击、输入、滚动、切换视口）。
不要直接调用后端 API 绕过界面 —— 那样测不到 UI，本次任务就失去意义。

### 0.2 证据铁律（最重要）

1. **没有证据的"通过"无效。** "页面看起来正常"不是证据。每个用例必须附带：
   - **截图**（按 §5.2 命名规范）
   - **关键断言的可见文本原文**（必须逐字引用，禁止转述或概括）
2. **区分"观察到"与"推断"。** 报告里凡是你没有直接看到的，一律标注为推断，并说明推断依据。
3. **异常必须原文记录。** 控制台报错、网络失败、界面报错文案，一律照抄，不要"清洗"。
4. **不确定就标 BLOCKED**，并写清卡在哪里。**不要猜**。宁缺勿滥。

### 0.3 记录等待时长

AI 操作是异步的，等待体验本身就是被测对象。每个 AI 相关用例必须记录：
- 从触发到出现结果/提示的**实际秒数**
- 等待期间界面**显示了什么**（有没有进度、有没有"可离开本页"之类提示）
- 你是否曾因为"看起来没反应"而想刷新

### 0.4 必须处理原生弹窗（首轮实测教训）

本应用在若干主流程中使用了**浏览器原生 `confirm()` 弹窗**（如"未选岗位时开始面试"）。

⚠ **浏览器自动化默认会把原生弹窗当作"取消"**，函数会直接 `return`，表现为
**"点了按钮什么都没发生、也不发任何请求"**。首轮执行就因此漏测了整条面试路径。

因此你必须：
1. 监听并**显式接受**原生弹窗（Playwright：`page.on('dialog', d => d.accept())`）；
2. 在报告中记录**每次弹窗的原文文案**与你的选择；
3. 若某操作点击后无任何网络请求，**先排查是否被原生弹窗拦截**，再考虑记为缺陷。

### 0.5 环境属性（影响你的操作边界）

该环境是**可随时重置的测试环境**，不是生产。因此：
- ✅ 可以自由注册账号、创建/删除**你自己创建的**数据
- ❌ 不要动别人的数据（用你自己注册的账号，看不到别人的数据，这是正常的）
- ❌ 不要修改服务器配置、不要登录服务器、不要清数据库
