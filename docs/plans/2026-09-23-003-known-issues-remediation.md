### I1 前端超时窗口与后端耗时结构脱节

**表现**：生成任务在后端正常执行，前端却在中途进入"超时"分支。

**触发条件**：任一次 `JOB_GENERATION` 落在链首模型超时（300s）+ 顺延后续模型成功的路径上 —— 即**只要链首模型在大 prompt 上超时，就必然触发**。

**复现步骤与证据**（`.workbuddy/tools/repro_issues.py`，轮询参数严格取自 `useTaskPolling.ts`：`initialDelay=1500ms, interval=2000ms, maxAttempts=150`）：

```
T+  77.7s  【长任务】JOB_GENERATION id=15 已启动
T+  78.0s  【短任务】INLINE_OPTIMIZE id=16 已启动
  第  50 次  T+ 187.5s  生成=RUNNING
  第 100 次  T+ 299.0s  生成=RUNNING
  第 150 次  T+ 411.2s  生成=RUNNING
  ★ 前端窗口用尽（150 次 × 2s = 300s）：生成任务状态 = RUNNING
```

即：**前端窗口到期时，后端任务仍在正常执行**（后续确认其成功，见 §2.1）。

**连带发现（初判有误，已更正）**：超时分支渲染为

```html
<!-- GenerationConfirmView.vue:200 -->
<div v-else-if="error && (pollingTimedOut || ...)" class="status-card error">
  <p class="error-text">任务仍在后台执行，可刷新页面查看结果</p>
  <button @click="handleRetry">重新生成</button>
</div>
```

- 文案本身**是对的**（i18n `common.taskTimeout = "任务仍在后台执行，可刷新页面查看结果"`），我最初只看到 `error.value = t('common.taskTimeout')` 就误判为"超时失败文案"，**不成立**；
- 但**主按钮是「重新生成」**，与文案自相矛盾。用户照做后服务端返回
  `400「只有失败的任务可以重试」`（`AiTaskService.java:194` 有 `FAILED` 状态守卫），
  该错误信息会**覆盖**掉原文案 → 用户既看不到进度、也无法重试，而后台任务再等约 177s 本会成功。
- **服务端守卫有效，不存在"重复消耗额度"** —— 这一点初判也错了，更正。

### I1b 直接打开/刷新运行中的生成任务 → 内容区空白（**编写回归用例时新发现**）

**表现**：进入生成确认页后，内容区整片空白（仅剩顶部导航），持续到任务完成为止。

**触发条件**：`taskId` 对应任务处于 `PENDING` / `RUNNING` 时**直接打开或刷新页面** ——
即用户从工作台「继续办理」进入运行中的生成，或按提示"刷新页面查看结果"时必然触发。

**发现方式**：为 I1 编写 e2e 用例时，断言"运行中应展示运行态卡片"，实际得到空白。
最初怀疑是测试写法问题（Playwright 时钟），改为**导航后**再断言，依然是空白，
逐步排除测试因素后定位到视图自身。

**根因**（`GenerationConfirmView.vue#loadTask`）：

```js
} finally {
  loading.value = false        // ← 对 RUNNING/PENDING 分支也执行
}
```

而 RUNNING/PENDING 分支已经调用 `startPolling(id)` 把渲染交给轮询，且 `startPolling`
**不会**把 `loading` 恢复为 true。于是 `loading=false`、`error` 为空、`task.status=RUNNING`，
模板的 `v-if="loading"` / 失败分支 / 草稿分支**全部不匹配** → 无内容渲染。

**关键对照（证明这是偏离而非设计）**：同仓库的 `MaterialSelectionConfirmView#loadTask`
**没有 `finally`**，而是逐分支显式结束加载态、轮询分支保持 `loading=true` —— 正确范式就在代码库里，
生成页只是背离了它。

**连带放大**：I1 的超时文案写着"可刷新页面查看结果"，而**刷新后正好是白屏**，
比不提示更糟 —— 两个缺陷叠加成"让用户照做反而更坏"的路径。

**修复**：`loadTask` 改为逐分支显式结束加载态（对齐选材页范式），轮询分支 `return` 时保持 `loading=true`。

**验证**：新增 e2e `直接打开仍在运行的生成任务时展示运行态，而不是空白内容区` —— 修复前失败、修复后通过。

### I2 AI worker 串行执行导致队列饥饿

**表现**：短任务长时间停在 `PENDING`，`retryCount` 始终为 0（说明 worker 从未领取）。

**触发条件**：任一长任务（如 `JOB_GENERATION`）占住唯一的执行线程。

**复现证据**（同一轮）：

```
短任务 id=16 INLINE_OPTIMIZE：T+78s 投放 → T+411s 仍为 PENDING，retryCount=0
对照：同类任务平时耗时 13s（id=7 实测）
历史上同类排队：id=11 ATS_ANALYSIS 排在 477s 的生成之后 → 338s
```

**机制证据**：`DatabaseTaskWorker` 每次 `leaseService.claimBatch(owner, 1)` —— 一次只领 1 条、串行执行。

### I3 链首模型在大 prompt 上必然超时

**表现**：`JOB_GENERATION` 每次先白等 300s，再顺延到 `glm-5.3` 才成功。

**触发条件**：任务使用大 prompt（生成任务：三段式 prompt + 全部资料 + JD）。

**复现证据**（两次，时间线精确到秒）：

```
第一次：20:12:38 发起 → 20:17:38 outcome=failure category=TIMEOUT（整 300s）→ 顺延 glm-5.3 → 20:20:21 产出
第二次：本轮 id=15 同样在链首超时
对照：同一模型 qwen3.8-max 在【小 prompt】的选材任务上 32~77s 即成功
```

判定：**prompt 规模相关，不是模型故障**。

### I4 / I5 / I6

- **I4**：`monitoring/prometheus/rules/` 现有 9 条规则（含 `AiProviderSuccessRateLow`、`AiQueueBacklog` 等），**无任何规则引用 `resume_ai_model_chain_available`** → 链全失效只能靠人工查健康检查发现。
- **I5**：`docs/decisions/` 不存在。今日多个决策（链总预算 600s 的取值依据、额度是**模型级**而非账号级的判定、`_source`/`_pending` 互斥的修法）只存在于 commit message 与评审文档。
- **I6**：`SELECT COUNT(*) total, SUM(username LIKE 'aitest%' OR 'e2e%' OR 'local%') test FROM user` → **5 / 5**，该环境用户表**全是测试账号**，本质是可丢弃环境，但未在任何文档中声明。

## 2. 根因分析与影响范围

### 2.1 I1 根因

**根因链**（三层）：

1. **窗口取值依据已失效**：`useTaskPolling` 的 150×2s=300s 是**按单模型时代的 `BAILIAN_READ_TIMEOUT_S=300`** 对齐的（注释明确写着）。模型链上线后，任务耗时结构由「单次调用」变为「**首次超时 300s + 顺延调用 N 次**」，窗口依据与实际耗时结构脱钩。
2. **超时语义被当作失败**：`onTimeout` 走的是与 `FAILED`/`CANCELLED` 相同的 `status-card error` 分支，并把 `pollingTimedOut` 与失败等同处理，于是渲染出重试按钮。
3. **缺少"仍在运行"的表达**：产品里已有正确的样板 —— `AtsCheckView` 的 `analyzingBackground`（"AI 仍在后台分析 / 刷新页面可继续获取"）软状态，但两个生成类确认页未采用。

**影响范围**：

| 维度 | 影响 |
| --- | --- |
| 功能模块 | `GenerationConfirmView`、`MaterialSelectionConfirmView`（生成类确认页）；`AtsCheckView` 窗口同样偏短（实测 338s > 300s） |
| 数据 | 无数据损坏。任务在后端正常完成，草稿/版本正常落库 |
| 依赖 | 依赖 `useTaskPolling` 默认常量；无后端依赖 |
| 连带风险 | ① 用户误以为生成失败而放弃，重复发起选材/生成 → **额外消耗模型额度**；② 用户被引导到必然 400 的操作，产生"产品坏了"的印象；③ 若用户反复刷新，AI 任务续办列表会堆积 |

**优先级判定**：**P1**。不损坏数据，但直接伤害核心流程的用户体验，且**必然触发**（不是偶发）。

### 2.2 I2 根因

**根因**：AI worker 按 id 串行执行（`claimBatch(owner, 1)`），且**任务耗时方差极大**（13s ~ 477s，差 36 倍）。串行 + 高方差 = 队首阻塞（head-of-line blocking）。

**影响范围**：

| 维度 | 影响 |
| --- | --- |
| 功能模块 | 全部 9 类 AI 任务共用一条队列 |
| 数据 | 无损坏；任务最终都会执行（只要不超租约） |
| 依赖 | `DatabaseTaskWorker` + `AiTaskRepository.claimableTasks`（`FOR UPDATE`）；租约由 heartbeat 续期，长任务不会因租约过期被抢占 |
| 连带风险 | ① 用户感知"点了没反应"（短任务被饿死）；② **额度消耗节奏不可控**；③ 已有 `AiQueueBacklog`（`oldest_pending_seconds > 300` 持续 5m）告警**可以检出**该现象 —— 即**检测已有、缓解缺失** |

**优先级判定**：**P1**。当前单用户不致命，但随用户量线性恶化，且已有告警会在生产持续触发。

### 2.3 I3 根因

**根因**：模型链是**单一有序列表，不区分任务类型**。`JOB_GENERATION` 的 prompt 规模远大于其他任务，而链首 `qwen3.8-max` 恰好在"大 prompt 长输出"场景下超过 300s 读超时。链没有"该模型不适合该任务规模"的表达能力。

**影响范围**：

| 维度 | 影响 |
| --- | --- |
| 功能模块 | 仅 `JOB_GENERATION`（其余任务 prompt 小，链首表现正常） |
| 数据 | 无损坏 |
| 依赖 | `BAILIAN_READ_TIMEOUT_S=300`、`AI_CHAIN_TOTAL_BUDGET_S=600`、链序配置 |
| 连带风险 | ① 每次生成浪费 300s 与一次失败的 provider 调用（**是否计费待确认**）；② 生成总耗时被推高到 ~477s，直接放大 I1 与 I2；③ 若链首固定不变，小任务也会持续优先占用优质模型 |

**优先级判定**：**P2**。是 I1/I2 的**放大器**但不独立造成故障。

### 2.4 I4 / I5 / I6

| 编号 | 根因 | 影响范围 | 优先级 |
| --- | --- | --- | --- |
| I4 | 指标先行、告警规则滞后（当时评估后选择不做） | 运维可观测性；无功能影响 | P2 |
| I5 | 专家团 SOP 的 ADR / 悬而未决登记册实践未落地 | 工程过程；影响后续维护者对决策的追溯 | P3 |
| I6 | 环境定位未文档化 | 运维；无功能影响 | P3 |

## 3. 修改方案

### 3.1 I1 方案（P1）

**改动点**（**纯前端**，服务端行为正确、不动）：

| # | 文件 | 改动 |
| --- | --- | --- |
| 1 | `web/src/composables/useTaskPolling.ts` | 默认窗口由 `150×2s=300s` 提升至 `300×2s=600s`，并把注释依据从"对齐单次读超时"改为"对齐 `AI_CHAIN_TOTAL_BUDGET_S` 并预留排队余量" |
| 2 | `web/src/views/GenerationConfirmView.vue` | 超时分支与失败分支**分离**：`pollingTimedOut` 渲染为独立的"后台执行中"软状态卡片；主操作从「重新生成」改为「去工作台继续」，跳 `/`（复用既有 `resumableTasks` 入口） |
| 3 | `web/src/views/MaterialSelectionConfirmView.vue` | 同上；`retry` 按钮的显示条件去掉 `|| pollingTimedOut`（避免对运行中任务展示必然 400 的操作） |
| 4 | `web/src/views/AtsCheckView.vue` | 窗口 200×1.5s=300s → 与 #1 对齐；其软状态文案已是正确样板，仅需复用 |
| 5 | `web/src/i18n/index.ts` | 新增软状态文案（中英双语）；`common.taskTimeout` 保留给真正的超时语义 |

**技术取舍**：

- **不做指数退避**：600s/2s = 300 次请求，单用户单任务可接受；引入退避会把请求数降到 ~150 但增加状态复杂度，ROI 不足，**先不做**（列入后续可选）。
- **不加长后端**：问题的本质是**前端窗口取值依据失效**，不是后端太慢。加长后端读超时会同时放大 I2 的阻塞，方向相反。
- **不引入 WebSocket/SSE**：现有轮询机制成熟（含 epoch 代次隔离、卸载清理），改推送属架构级变更，收益与风险不匹配。
- **不使用"自动跳转工作台"**：静默跳转会打断用户，改为**提供明确入口**由用户决定。

**验证方式**：

1. 单测：`useTaskPolling` 的窗口常量断言（若已有测试则同步）。
2. e2e（Playwright + mock，无需真实栈）：新增用例 —— mock 任务持续返回 `RUNNING` 至窗口耗尽 → 断言出现"后台执行中"软状态、**不出现**「重新生成」按钮、且存在跳转工作台的入口。
3. 回归：`npm run build`（含 `check:i18n` 双语门禁）+ `npx playwright test`。
4. 真实联调：复用 `repro_issues.py`，确认窗口从 300s 提升后不再在任务完成前触发超时分支。
5. 新增 `web/e2e/generation-timeout.spec.ts` 三条用例：窗口不短于后端 600s 预算 / 运行中不白屏 / 真实失败仍可重试。

> **覆盖边界（如实告知）**：「窗口耗尽 → 软状态卡片」是纯模板条件分支。e2e 中不用 Playwright 时钟驱动 300 轮 async 轮询（`clock.runFor` 不等待异步回调，逐次同步既慢又不稳），故该分支的渲染由代码评审保证，未做机器断言。

**风险控制**：纯前端文案/常量/分支改动，**不触碰后端契约与数据**，回滚 = 单次 revert。主要风险是 i18n 双语遗漏 → 由仓库既有 `check:i18n` 门禁兜住。

### 3.2 I2 方案（P1）

**改动点**（需先做容量决策，见 §4）：

| 方案 | 改动 | 取舍 |
| --- | --- | --- |
| A（推荐先做） | `AiTask` 增加按任务类型的领取优先级或独立并发槽：短任务（`INLINE_OPTIMIZE`/`ACHIEVEMENT_GUIDANCE`/`COMMUNICATION_GENERATE`）不被长任务阻塞 | 改动集中在 worker 领取查询；不动业务逻辑。需注意 `claimableTasks` 目前是 `ORDER BY id ASC`，改序会影响公平性 |
| B | worker 提高并发（多线程/更大 batch） | 见效快，但需评估 DB 连接池、租约竞争、内存（本机 7.5G 且已给 JVM 1G） |
| C | 把长任务（生成）单列队列 | 隔离最彻底，但引入第二套 worker 与租约语义 |

**建议**：先做 A（按类型分组领取，长任务一次领 1、短任务可插队），成本最低且直击"饿死"；B 作为容量选项在压测后决定。

**风险控制**：领取逻辑涉及 `FOR UPDATE` 与租约，改动必须配**并发测试**（多实例同时领取同一任务只能成功一次）—— 已有 `DatabaseTaskWorkerIT` 可作为基础。

### 3.3 I3 方案（P2）

三个候选，需产品取舍：

| 方案 | 说明 | 取舍 |
| --- | --- | --- |
| a. 按任务类型分链 | 生成任务用"快模型优先"的链，小任务保留现有链 | 最对症，但要引入链的维度与配置复杂度 |
| b. 按任务类型设读超时 | 生成任务用更短读超时，让链首**快速失败**、尽快顺延 | 改动小；但需确认"300s 超时"到底是被 provider 阻塞还是模型真的在算 —— 若模型确实需要更久，缩短会误杀 |
| c. 调整全局链序 | 把 glm-5.3（177s 可完成）提到链首 | 零代码；但会牺牲小任务的模型质量（qwen3.8-max 在小 prompt 上更快更好） |

**建议**：先做 **b 的诊断**（在链首超时后检查 provider 侧是否仍在生成），再定 a/b/c。

### 3.4 I4 方案（P2）

在 `monitoring/prometheus/rules/intelligent-resume-alerts.yml` 新增一条：

```yaml
- alert: AiModelChainExhausted
  expr: resume_ai_model_chain_available <= 0
  for: 2m
  labels: { severity: critical }
```

**技术取舍**：用 `<= 0` 而非"下降速率"，因为该指标语义就是"当前可调度模型数"，为 0 即 AI 能力实际不可用，无需趋势判断。**需注意**指标为 0 也可能是"全部处于短冷却（60s）"的瞬时态 → 故 `for: 2m` 滤掉抖动。

### 3.5 I5 / I6 方案（P3）

- **I5**：建立 `docs/decisions/`，先把**今日已发生的 4 条决策**补录为 ADR（链总预算取值、模型级额度语义、`_source`/`_pending` 互斥修法、模型链路由策略），再立 `OPEN-DECISIONS.md` 承接未决项（如 I3 的 a/b/c 选择）。
- **I6**：在 `docs/DEPLOYMENT_DIRECT.md` 明确声明该环境的属性（**可随时重置的测试环境**、测试账号命名前缀 `aitest*/e2e*/local*`、重置方式），避免后续把它当准生产环境。

## 4. 优先级与实施计划

| 步骤 | 内容 | 依赖 | 回归验证 | 风险控制 |
| --- | --- | --- | --- | --- |
| **S1** | I1 + I1b 前端修复（窗口对齐 + 软状态 + 去掉必然 400 的按钮 + 修掉运行中白屏 + 耗时文案） | 无 | `npm run build`（含 i18n 门禁）+ 新增 e2e 用例 + `repro_issues.py` 复验 | 纯前端、可单次 revert；i18n 双语由门禁保证 |
| **S2** | I4 新增链路失效告警规则 | 无 | `promtool check rules`（或 compose 校验） | 只增规则文件，不影响运行 |
| **S3** | I5 补录 ADR + 建 OPEN-DECISIONS（含 I3 的 a/b/c 决策条目） | 无 | 文档链接校验（沿用 `docs/README.md` 索引校对方式） | 纯文档 |
| **S4** | I2 领取策略改造（方案 A） | 需先确认容量预期 | `DatabaseTaskWorkerIT` + 新增并发领取测试 + 真实环境并行投放长短任务复验 | **高风险**（涉及 `FOR UPDATE` 与租约），必须先在测试环境验证多实例领取唯一性 |
| **S5** | I3 诊断后定 a/b/c 并实施 | 依赖 I3 诊断结论 | 生成任务耗时对比（目标：从 ~477s 降至 <300s） | 链序/超时属运行配置，可快速回滚 |

## 5. 与初判不符处的更正（复盘）

复现阶段推翻了我此前三处判断，记录下来以免后续重复踩坑：

| 初判 | 复现后结论 |
| --- | --- |
| 超时会展示"超时失败"文案 | **错**。文案是"任务仍在后台执行，可刷新页面查看结果"，语义正确；真正的问题是**主按钮是「重新生成」**，与文案矛盾且必然 400 |
| 点「重新生成」会重复触发 AI、重复消耗额度 | **错**。`AiTaskService:194` 有 `FAILED` 状态守卫，运行中任务重试返回 400。真实后果是**用户被困住**，不是额度浪费 |
| 续办查询未按类型过滤，`HomeView` 路由会跳错页 | **错**。`findContinuationsByUserId` 的 `taskType IN (JOB_MATERIAL_SELECTION, JOB_GENERATION)` 已过滤，二元路由因此正确 |
| 生成确认页超时只是文案不当 | **不完整**。编写回归用例时发现更严重的 **I1b：运行中直接打开/刷新该页内容区整片空白**，且超时文案恰好引导用户去刷新 → 两缺陷叠加 |
| 服务器测试账号残留属数据卫生问题 | **口径需调整**。`user` 表 5/5 全是测试账号 → 该环境本就是可丢弃的测试环境，问题在于**未声明**，而非"污染" |

**方法论教训**：`grep` 输出被截断时不能据此下结论（第 3 条即因此误判），必须读完整语句；断言"UI 会展示什么"必须读 i18n 实际文案，不能只看绑定变量名。
