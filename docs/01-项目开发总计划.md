# 项目开发总计划

## 1. 项目概述

项目名称：智能简历生成与岗位匹配平台  
项目目标：构建一个面向求职场景的 AI 求职平台，支持职业资料沉淀、岗位定制简历生成、成果量化引导、ATS 体检、求职沟通文案、投递管理、AI 面试复盘和 PDF 导出。

本项目的核心价值不是“做一个普通简历编辑器”，而是提供从简历编写、岗位适配到结果导出的完整智能化闭环。

## 2. 开发目标

### 2.1 业务目标

- 支持用户沉淀和管理可复用的职业资料，以及创建、编辑和管理多份简历
- 支持用户输入目标公司和岗位 JD，由 AI 从资料库中筛选相关经历生成岗位定制简历
- 支持用户输入岗位 JD 并进行简历定制化优化
- 支持输出简历匹配分数、ATS 体检结果和优化建议
- 支持关联岗位、简历版本和进度的投递管理，以及求职沟通文案生成
- 支持将最终简历导出为 PDF

### 2.2 技术目标

- 采用前后端分离架构
- 后端采用 Spring Boot 作为主开发框架
- 集成 Spring AI 作为大模型能力接入层
- 保持系统具备后续扩展到缓存、异步任务、微服务的能力

## 3. 范围边界

### 3.1 MVP 交付边界

MVP 只交付可验证的“资料库 -> JD -> 岗位定制简历 -> 基础评分 -> 单模板 PDF”闭环：

- 用户注册、登录、资源归属校验和基础限流
- 职业资料库、简历与版本管理
- JD 管理、基于 JD 的岗位定制简历生成和用户确认
- 基础规则评分与单模板 PDF 导出

零碎资料生成、实时优化、ATS 体检、成果量化、沟通文案、投递管理和 AI 面试均保留在产品路线图中，但不作为 MVP 验收条件。

### 3.2 产品路线图范围

- 用户注册、登录、鉴权
- 简历 CRUD
- 简历版本管理
- 职业资料库管理
- JD 管理
- 基于岗位的资料筛选与简历生成
- 成果量化引导与 ATS 体检
- 求职沟通文案与投递管理
- AI 面试复盘与答案资产沉淀
- AI 简历优化
- 匹配评分
- PDF 导出

### 3.3 暂不纳入路线图范围

- 向量数据库
- RAG 检索增强
- Kubernetes 部署
- 多租户
- 复杂后台管理系统
- 大规模分布式微服务拆分

## 4. 开发原则

- 先做可用，再做复杂
- 先保证主流程闭环，再补工程增强
- 先模块化单体，再按实际需要拆服务
- 所有 AI 能力必须可追踪、可解释、可回退

## 5. 总体阶段划分

### 第一阶段：基础系统

目标：完成账号体系和简历基础能力

交付内容：

- 用户登录注册
- 短期访问令牌、刷新令牌、退出登录与基础限流
- 基础权限和资源归属校验
- 简历新增、编辑、删除、查询
- JSON Resume 数据模型落地

### 第二阶段：MVP 求职闭环

目标：完成项目核心价值闭环

交付内容：

- JD 输入与管理
- 基于 JD 筛选资料并生成岗位定制简历
- 版本快照保存
- 基础匹配评分
- 单模板 PDF 导出和私有文件下载

### 第三阶段：求职质量与投递体验

目标：让成果可展示、可使用

交付内容：

- 零碎资料导入为待确认职业资料
- 实时优化、成果量化引导与 ATS 体检
- 求职沟通文案、投递记录和状态流转
- 多模板规划、优化结果对比和评分解释

### 第四阶段：面试与工程增强

目标：提升稳定性、性能和可维护性

交付内容：

- 平台简历 AI 面试、面试报告和答案资产库
- 自带简历文本面试
- Redis 缓存
- MQ/分布式工作器、任务租约恢复与高级重试机制
- MQ 接入
- 监控与日志体系
- 限流与失败重试

## 6. 里程碑计划

| 里程碑 | 阶段目标 | 核心结果 |
| --- | --- | --- |
| M1 | 基础系统完成 | 用户可安全地登录并管理简历和版本 |
| M2 | MVP 求职闭环完成 | 用户可基于 JD 生成、确认、评分并导出定制简历 |
| M3 | 求职质量与投递完成 | 用户可体检简历、生成沟通文案并跟踪投递 |
| M4 | 面试与工程增强完成 | 用户可完成 AI 面试复盘，系统具备分布式任务、监控和增强限流能力 |

## 7. 交付标准

项目在开发期结束时，应满足以下标准：

1. 主流程可端到端运行
2. 数据结构清晰且便于扩展
3. AI 筛选依据和优化结果可保存、可追踪
4. MVP 的生成内容、资料来源和用户确认可追溯
5. 匹配评分具备基本可解释性，PDF 可用于真实演示
6. 后续阶段的 ATS、投递和面试数据可追溯
7. 文档、代码、接口、数据库保持一致

## 8. 角色分工建议

若为单人开发：

- 一人同时承担产品、后端、前端和测试职责
- 优先按阶段推进，避免并行铺太多功能

若为小组开发：

- 后端：认证、资料库、简历、AI、ATS、投递、面试复盘、评分、导出接口
- 前端：登录、资料库、简历编辑器、JD 输入、体检、投递、面试复盘、结果展示
- 测试/协同：接口联调、回归验证、文档维护

## 9. 当前建议执行路径

建议开发顺序如下：

1. 建后端和前端骨架，建立统一错误码、鉴权和限流
2. 实现职业资料库、简历与版本管理
3. 落地 JD、岗位定制生成的数据库任务状态、后台执行、来源映射和用户确认
4. 实现基础规则评分、私有 PDF 导出和端到端验收
5. 仅在 M2 验收后启动 ATS、投递和 AI 面试等后续能力
6. 仅在任务量或并发证明确有需要后补 Redis、MQ、分布式工作器和监控

### 9.1 异步能力分层

- M2 必须具备“数据库持久化任务 + 后台执行 + 状态查询 + 幂等 + 超时恢复”的最小异步能力，不依赖 MQ。
- M4 的“分布式任务增强”是指 MQ、独立工作器、任务租约、队列积压监控和跨实例恢复，不得被解释为 M2 才开始支持异步。
