# 接口设计说明书

## 1. 设计约定

### 1.1 接口风格

- 风格：RESTful
- 数据格式：JSON
- 鉴权方式：Bearer Token
- 字符编码：UTF-8

### 1.2 统一响应格式

```json
{
  "code": 0,
  "message": "success",
  "data": {},
  "traceId": "xxx"
}
```

约定：

- `code = 0` 表示成功
- 非 0 表示业务失败或系统失败

### 1.3 通用错误码建议

| 错误码 | 说明 |
| --- | --- |
| 40001 | 参数错误（含协议级调用方错误：方法不允许 `405`、不支持的媒体类型 `415`、不可接受的响应媒体类型 `406`、上传超限 `413`——HTTP 状态保留协议语义，响应体仍为统一信封） |
| 40101 | 未登录或 Token 无效；**亦用于「当前密码校验失败」**（`/api/auth/me/password`、`/api/auth/me/email`、`/api/auth/export` 三处复验当前密码，见 §2.7 与 §1.3） |
| 40301 | 无权限访问 |
| 40302 | AI 数据处理未授权或已撤回 —— 调用 AI 能力前须获得对应**任务范围**与**数据类别**的同意；未授权或已撤回时返回（前端按此码引导用户去同意页） |
| 40401 | 资源不存在 |
| 50001 | 系统异常 |
| 50002 | AI 调用失败 |
| 50003 | PDF 导出失败 |
| 42901 | 请求频率或 AI 配额超限 |
| 40901 | 资源版本冲突或非法状态迁移 |
| 40902 | 简历版本已归档（可逆状态；下游消费被拒，请先恢复该版本再重试） |
| 40303 | 账号处于删除撤销期 —— 登录被拒；登录页据此展示「恢复账号」入口（凭用户名/邮箱 + 密码调用 `POST /api/auth/deletion/restore`） |
| 40903 | 删除撤销期已结束（或账号从未处于撤销期）—— 恢复被拒，数据已进入永久删除流程 |
| 40904 | 选材已过期 —— 确认草稿时 `selected` 里的素材路径未被本次 `items` 覆盖（客户端少提交，ADR-013）；处置是**重新载入选材**而非刷新重试，故与 `40901` 分码 |

> **失败文案的公开边界（第六十九批）**：50002 / 50003 两条的 `message` **不再是上游或框架原文**，
> 而是按失败类别给出的**稳定文案**（如「AI 服务暂时不可用，请稍后重试」）。原因是这两条链路的异常
> 消息会夹带上游细节（模型名、HTTP 状态码、上游错误体、内部字节上限），此前被原样回给客户端 ——
> 既外泄实现信息，又让可见文案随上游措辞漂移、无法用于测试与客服话术。
> 原文仍完整落在 `ai_task.error_message` / `export_task.error_message` 与日志
> （`Business failure with provider detail, code=…, traceId=…, raw=…`）里供排查。
> 同一口径适用于 `AiTaskStatusResponse.errorMessage` 与 `ExportTaskStatusResponse.errorMessage`，
> 由 `PublicFailureCopy` 统一实现，`PublicFailureCopyTest`（映射与残留片段）与
> `AiTaskPublicFailureCopyContractTest`（**行为级**：走一遍响应装配）守护。
> ⚠ **`errorMessage` 为 `null` 表示「无错误」**（重试会清空该列），不得为展示需要凭空生成文案。
> 面试路径自始只暴露 `messageCode`，不受影响。体积超限两条保留**可行动**文案
> （`INPUT_TOO_LARGE` / `OUTPUT_TOO_LARGE`），只是不再带内部字节数。

> 频率限流按**归一化路径**匹配（解码百分号转义、去掉矩阵参数）：`/api/auth/%6Cogin` 与 `/api/auth/login` 属同一分桶，等价写法不能绕过。受限端点：login/register/refresh、凭证变更（`/api/auth/me/password` 与 `/api/auth/me/email`，两者共享同一分桶）、`/api/auth/export`（见下）、resume-imports/parse、jobs/{id}/parse（阈值见 `app.security.rate-limit.*`）。
>
> **口令验证面共三处**（均在请求内校验「当前密码」）：`/api/auth/me/password` 与 `/api/auth/me/email` 共享同一分桶（默认 5 次/分钟，`change-credential-per-minute`），目的是防止在两端点间交替获得双倍预算；`/api/auth/export` 目前用**独立分桶**（默认 3 次/分钟，`account-export-per-minute`），因为它同时是「数据放大器」——单次请求即重读并序列化全账号数据，阈值取最严一档。**已知取舍**：导出改为复验密码（§2.7）后，等于给口令猜测多出一个 3 次/分钟的面，与凭证变更的 5 次/分钟并行（合计 8 次/分钟），尚未并入共享桶；若要压制到与凭证变更同强度，应把 `/api/auth/export` 并入 `change-credential` 桶（见 `RateLimitFilter.limitFor` 与 `application.yml` 中 `security.rate-limit.*` 的分桶注释）。
>
> 频率限流的 429 响应携带 `Retry-After`（秒，1~60）：计数为**滑动窗口**（当前窗口 + 上一窗口按剩余比例加权，窗口长度 60s），取值即距下一次配额可用的秒数——不是距下一自然分钟，因为窗口滚动后上一窗口仍按接近 100% 的权重计入、滚动瞬间重试仍会被拒。客户端据此退避而非盲目重试（与 pdf-service 503 的 `Retry-After` 语义一致）。AI 日配额超限也返回 429 + 42901，但不带该头（配额按天重置，无等价的短窗口值）。

## 2. 认证接口

### 2.1 注册

`POST /api/auth/register`

请求体：

```json
{
  "username": "zhangsan",
  "email": "test@example.com",
  "password": "123456"
}
```

返回：

```json
{
  "userId": 1
}
```

### 2.2 登录

`POST /api/auth/login`

请求体：

```json
{
  "username": "zhangsan",
  "password": "123456"
}
```

返回：

```json
{
  "accessToken": "jwt-token",
  "accessTokenExpiresIn": 900,
  "refreshToken": "refresh-token",
  "userInfo": {
    "id": 1,
    "username": "zhangsan"
  }
}
```

### 2.3 刷新令牌

`POST /api/auth/refresh`

浏览器通过 `Secure`、`HttpOnly`、`SameSite=Lax` Cookie 提交刷新令牌。刷新成功后必须轮换 Cookie；已注销、过期、被撤销或已被替换的令牌不得再次使用。检测到旧令牌复用时撤销同一令牌族并返回 `40101`。

### 2.4 退出登录

`POST /api/auth/logout`

撤销当前刷新令牌和关联会话。访问令牌到期前无需写入完整 Token 原文到日志。

可选请求参数 `allSessions=true` 用于退出当前用户的所有会话；默认只退出当前会话。

### 2.5 获取当前用户

`GET /api/auth/me`

返回当前登录用户信息。

### 2.6 AI 数据处理同意

- `GET /api/ai/consent`：返回当前有效同意、提供商、用途、任务范围、数据类别和政策版本。
- `POST /api/ai/consent`：记录用户明确授权；必须提交 `policyVersion`、`providerCode`、`taskScopes` 和 `dataCategories`。
- `DELETE /api/ai/consent`：撤回同意，立即阻止新 AI 任务；不改写历史审计记录。

### 2.7 导出个人数据

`POST /api/auth/export`

导出前必须**复验当前密码**：导出物是本账号的全量数据文档，仅凭一个已签发的 access token 即可整体下载等于把「拿到未锁屏设备」直接升级为「拿到全账号数据副本」，故下载动作本身是一次凭据确认。

请求体：

```json
{ "currentPassword": "当前登录密码" }
```

| 字段 | 类型 | 约束 | 说明 |
| --- | --- | --- | --- |
| currentPassword | string | 必填，8–128 字符 | 当前登录密码；与 `POST /api/auth/me/password`、`POST /api/auth/me/email` 同口径（`@NotBlank` + `@Size(min=8, max=128)`） |

响应是可直接保存的缩进 JSON 文件，**不是**统一响应信封：

- 头：`Content-Type: application/json;charset=UTF-8`、`Content-Disposition: attachment; filename="intelligent-resume-export-<yyyy-MM-dd>.json"`。
- 传输：响应**流式写出**（分块传输，无 `Content-Length`）——账号数据无体积上限，整份缓冲的峰值堆 ≈ 2× 响应体（先建 JSON 字符串、再编码成字节数组），实测 12.2MB 响应在 `-Xmx128m` 上直接 OutOfMemoryError；流式写出的堆占用为常数级，客户端按流读取即可（已开始写出后无法再改写为错误信封）。导出端点受频率限流（默认 3 次/分钟），见 §1.3。
- 密码错误：返回 `40101`（详见下方「错误码」）。
- 结构（`formatVersion: 3`，字段增删时递增）：

```json
{
  "formatVersion": 3,
  "exportedAt": "2026-09-30T12:00:00",
  "account": { "id": 1, "username": "zhangsan", "email": "test@example.com", "displayName": "张三", "registeredAt": "2026-01-01T09:00:00" },
  "personalProfile": {},
  "resumes": [{ "id": 1, "title": "Java后端简历", "versions": [{}] }],
  "careerMaterials": [{}],
  "jobDescriptions": [{}],
  "applications": [{
    "id": 1,
    "status": "SCREENING",
    "statusHistory": [
      { "id": 1, "fromStatus": null, "toStatus": "DRAFT", "note": null, "changedAt": "2026-09-01T10:00:00" },
      { "id": 2, "fromStatus": "DRAFT", "toStatus": "APPLIED", "note": "官网投递", "changedAt": "2026-09-02T09:30:00" },
      { "id": 3, "fromStatus": "APPLIED", "toStatus": "SCREENING", "note": null, "changedAt": "2026-09-05T14:00:00" }
    ]
  }],
  "interviewSessions": [{ "id": 1, "records": [{}] }],
  "interviewAnswerAssets": [{ "id": 1, "sections": [{}] }],
  "communicationTemplates": [{}],
  "communicationDrafts": [{}],
  "aiConsents": [{}]
}
```

- 归属规则：所有列表按当前用户过滤（跨用户不串号）；`communicationTemplates` 仅含自定义模板，内置系统模板（`user_id` 为空）属全局种子数据、不导出。
- 嵌套：简历 → 版本（含已归档版本，`deletedAt` 非空）、面试会话 → 轮次记录、答案资产 → 关联章节、投递记录 → 状态历史 `statusHistory`（按 `changedAt` 升序，字段定义见 §9.2）；`resumeJson`/`contentJson` 等 JSON 列以嵌套对象输出。
- **`formatVersion` 变更史**：`1` = 首版（V35 之前的能力面）；`2` = 投递记录改为带 `statusHistory` 的节点（V36 投递状态历史表）。消费方（如桌面端离线工作台的导入侧）必须按 `formatVersion` 分支处理，不得假设 `statusHistory` 恒存在。
- 排除项：AI 任务（含内联输入快照与结果）及其派生的 ATS/匹配分析（可再生成的中间产物）、登录会话凭据（不导出 `passwordHash` 等字段）。

**错误码**：密码错误返回 `40101`。该码与「未登录 / Token 无效」共用（见 §1.1），前端 `web/src/api/client.ts` 对 `/api/auth/**` 前缀的请求**不做**自动续期，因此输错密码不会触发 `POST /api/auth/refresh`、也不会清理会话或把人踢回登录页——调用方应按「当前密码不正确」提示，而不是「登录已过期」。**已知取舍**：`40101` 无法区分「token 失效」与「密码输错」，若后续需要精确文案，应新增独立错误码而不是在客户端猜测。

### 2.8 删除账号

`DELETE /api/auth/me`

删除请求进入 **7 天撤销窗口**（决策 D2 阶段 3）：账号立即停用、撤销全部刷新会话（已签发的 access token 立即失效）、取消进行中的 AI/PDF 任务、撤回 AI 同意并作废刷新 cookie；任务表新增 `PENDING` 行（`cancel_until = now + ACCOUNT_DELETION_GRACE_DAYS`，默认 7 天）。前端入口要求输入用户名二次确认，文案写明撤销期与恢复方式。窗口内恢复：登录被 `40303` 拒绝时登录页引导 `POST /api/auth/deletion/restore`（用户名/邮箱 + 密码，匿名可达、限流同登录）——恢复后账号回 `ACTIVE` 并签发全新会话；**不可逆动作不回滚**（AI 授权需重新同意、已取消任务不恢复）。窗口结束且 `ACCOUNT_PURGE_ENABLED=true` 时由清扫作业级联硬删全部数据（`PARTIAL_FAILED` 重入、每任务独立事务）。

### 2.9 修改邮箱、修改密码与退出全部会话

- `POST /api/auth/me/email`：请求体 `{ "email": "...", "currentPassword": "..." }`；修改成功后作废当前刷新 cookie（需重新登录）。
- `POST /api/auth/me/password`：请求体 `{ "currentPassword": "...", "newPassword": "..." }`；新密码至少 8 位；修改成功后作废当前刷新 cookie。
- `POST /api/auth/logout-all`：撤销当前用户**全部刷新会话**（其它设备无法再续期，`POST /api/auth/refresh` 返回 `40101`）并作废当前刷新 cookie。**边界**：access token 是无状态 JWT 且不携带会话标识，撤销会话不会使其立即失效——其它设备已签发的 access token 在自身到期前（≤ `app.jwt.access-token-ttl-seconds`，默认 3600s）仍可通过鉴权；与 §2.7 的**删号**不同（删号把用户置为 `DISABLED`，鉴权链路按用户状态即时拒绝，故删号是「已签发的 access token 立即失效」）。**已决策（2026-10-01，见 `docs/decisions/DECISION-BRIEF.md` D1）**：维持现状（方案 A）—— 不为 access token 引入会话标识或 `iat` 水位比较（每请求一次比较 + 时钟偏移处理，且受 30s 缓存 TTL 约束、可能误踢刚签发的 token，收益与代价不成比例）；**丢失设备场景以「删号 / 停用」兜底（方案 C）**，该路径**已即时失效**且有测试守护。契约由 `AuthControllerIT.postLogoutAll_revokesEveryDeviceRefreshSession` 守护。

## 3. 职业资料库接口

### 3.1 新增职业资料

`POST /api/career-materials`

请求体：

```json
{
  "materialType": "PROJECT_EXPERIENCE",
  "title": "订单系统重构",
  "contentJson": {},
  "sourceText": "负责订单模块重构与性能优化",
  "usagePreference": "NORMAL"
}
```

### 3.2 查询职业资料列表

`GET /api/career-materials?materialType=PROJECT_EXPERIENCE`

### 3.3 查询、更新和删除职业资料

- `GET /api/career-materials/{id}`
- `PUT /api/career-materials/{id}`
- `PATCH /api/career-materials/{id}`
- `DELETE /api/career-materials/{id}`

> 资料被简历版本引用的情况通过 AI 生成结果与 `resume_material_reference` 记录体现，不提供独立 HTTP 端点（原 `GET /api/career-materials/{id}/references` 从未实现，已从本说明书移除）。

### 3.4 搜索职业资料

`GET /api/career-materials/search?q=&type=&usagePreference=&page=0&size=25`

- `q` 命中 `title` / `sourceText` / `contentJson`（结构化字段如 `skillName`、`outcome` 也可命中，ideation #2），最长 100 字符，超限返回 `40001`；
- 返回分页对象：`items`（摘要 + `excerpt`）/ `page` / `size` / `totalElements` / `totalPages` / `typeCounts`（各类型命中数）。

## 5. 简历版本接口

### 5.1 查询版本列表

`GET /api/resumes/{id}/versions`

> 列表为**摘要投影**（ideation #50）：只返回元数据（`id` / `versionNo` / `sourceType` / `templateCode` / `optimizationSummary` / `createdAt` / `archivedAt` / `restoredFromVersionId`），不返回 `resumeJson`（单版本上限 256KB）与 `generationContext`（编辑器仅从版本详情读取）。`templateCode` 取自 V32 派生列：新版本在写入时归一化，历史行由读路径惰性回填。

### 5.2 保存版本

`POST /api/resumes/{id}/versions`

请求体：

```json
{
  "sourceType": "MANUAL",
  "resumeJson": {},
  "optimizationSummary": "手动调整项目描述"
}
```

### 5.3 查询版本详情

`GET /api/resume-versions/{id}`

### 5.4 归档、恢复与取消归档版本

- `POST /api/resumes/{resumeId}/versions/{versionId}/archive`：归档版本（从可见历史移出，可恢复）；
- `POST /api/resumes/{resumeId}/versions/{versionId}/restore`：从归档恢复为可见历史；
- `POST /api/resumes/{resumeId}/versions/{versionId}/unarchive`：取消归档（幂等：已是活动版本时直接返回成功）。

归档版本是**可逆状态**：不能设为当前版本，且 ATS 体检 / PDF 导出 / 投递关联 / 沟通 / 规则评分 / AI 面试会拒绝——**消费类拒绝用专属码 `40902`**（文案「该简历版本已归档，请先恢复后再…」，恢复后可重试；前端按码给出双语「先恢复」指引，不透传服务端 message）；版本管理类冲突（归档版本设为当前版本、乐观锁）仍用 `40901`。归属校验一律**先于**归档判定，他人版本仍以 `40401` 收口（不泄露归档状态）。列表接口仍可见归档版本（`archivedAt` 非空）。

`GET /api/jobs/{id}/reference`：仅返回 `id` / `title` / `companyName`，供选择器与列表展示，不加载 `jdText` 与解析结果。

## 7. AI 接口

### 7.1 基于岗位生成简历（选材 → 确认 → 生成）

1. `POST /api/ai/select-materials-for-job`：按 JD 发起**选材任务**（`JOB_MATERIAL_SELECTION`，见 §7.9）；轮询 `GET /api/ai/tasks/{id}` 获取候选资料与选择建议。
2. `POST /api/ai/tasks/{taskId}/confirm-materials`：确认选材，请求体含客户端最后看到的 `taskUpdatedAt`（乐观锁，过期返回 `40901`）；**必须带** `X-AI-Preview-Token`（取自 `POST /api/ai/tasks/{selectionTaskId}/confirm-materials/preview`，缺令牌 `40001`、令牌不符 `40901`，两者都不落库，见 §18.2.2）；服务端在同一事务内校验 AI 同意与每日配额、落库选择并创建 `JOB_GENERATION` **子任务**，响应即为该生成任务状态。
3. 轮询生成任务 `GET /api/ai/tasks/{id}` 获取生成草稿、资料选择结果、来源映射和缺失项。

生成任务的成功结果**不得自动写入简历版本**；用户确认采用时按 §7.6 调用确认接口，服务端在同一事务中创建 `resume_version`、保存资料引用和确认时间。

### 7.2 简历优化（RESUME_OPTIMIZE）

经通用任务端点创建（§7.8 白名单）：`POST /api/ai/tasks`，`taskType = "RESUME_OPTIMIZE"`，输入含 `resumeVersionId` 与 `jobDescriptionId`。

返回 `202`、任务标识与 `PENDING` 状态；优化内容只能在任务结果中返回，并由用户确认后保存为新版本。

### 7.3 重写自我介绍

不再提供独立端点：章节级重写统一走 §7.7 的 `POST /api/ai/inline-optimize`（`INLINE_OPTIMIZE`），请求中指定目标章节（自我介绍 = `summary`）。

### 7.4 重写项目描述

不再提供独立端点：章节级重写统一走 §7.7 的 `POST /api/ai/inline-optimize`（`INLINE_OPTIMIZE`），请求中指定目标章节（项目描述 = `projects`）。

### 7.5 查询 AI 任务状态

`GET /api/ai/tasks/{id}`

任务状态：`PENDING`、`RUNNING`、`SUCCESS`、`FAILED`、`CANCELLED`。成功结果必须包含输入快照摘要、模型/提示词版本、来源映射和用户确认状态。

**任务留存（ideation #26）**：终态任务超过 `app.ai.task.retention-days`（默认 90 天）后，服务端把内联快照（`input_snapshot_json`）与结果（`result_json`）压缩为元数据（保留 id/类型/状态/时间等行数据，`snapshot_purged` 标记一次性压缩）；待确认（`SUCCESS + PENDING`）与进行中的任务不压缩。清理作业每 `app.ai.task.cleanup-interval-ms`（默认 24h）触发，**续批**处理（每批 `app.ai.task.cleanup-batch-size` 默认 200 行、一批一事务）直到清完或达到单轮上限 `app.ai.task.cleanup-max-rows-per-run`（默认 20000 行；触达上限记 WARN，剩余积压下一轮继续）——即单轮清理量随积压增长，不再受「200 行/天」的硬上限约束。用户可随时用 `DELETE /api/ai/tasks/history` 清空本人已完成的 AI 任务历史（返回删除条数），进行中与待确认任务保留。

### 7.6 确认或拒绝 AI 结果

`POST /api/ai/tasks/{id}/confirm`

请求头必须携带 `Idempotency-Key`，请求体必须包含客户端最后看到的 `taskUpdatedAt`。仅所属用户可确认 `SUCCESS + PENDING` 的任务。服务端在同一事务中校验来源、创建唯一 `resume_version`、写入资料引用并把任务标记为 `CONFIRMED`。

- 相同幂等键重放：返回已创建的版本，不能重复创建。
- 任务已被其他请求确认：返回现有版本。
- 任务结果已变化或状态不允许：返回 `40901`。
- `selected` 中的素材路径未被本次 `items` 覆盖（客户端少提交了某些项）：返回 `40904`（`SELECTION_ITEM_UNKNOWN`），**不落库**。条款见 ADR-013：v0.5.0 之前该情形是静默跳过，导致「版本已落地但少了溯源引用」且无信号；用户选择 `REJECT` 的项仍是合法的静默跳过，不触发本码。
- 无法映射的 AI 自行生成事实不能通过确认接口直接采纳；用户必须主动编辑并通过职业资料接口新增事实。

`POST /api/ai/tasks/{id}/reject` 将确认状态改为 `REJECTED`，不创建版本。

### 7.7 实时优化与零碎资料导入

- `POST /api/ai/inline-optimize`：章节级实时优化（`INLINE_OPTIMIZE`）；`Idempotency-Key` **必填**且 ≤128 字符，返回 `202` + 任务标识；
- 零碎资料导入：经通用端点 `POST /api/ai/tasks`（`taskType = "MATERIAL_IMPORT"`，§7.8）或 §13 简历导入；任务结果只能产生「待确认职业资料」与草稿简历，用户逐条确认后才写入职业资料库。

### 7.8 通用任务端点与白名单契约

`POST /api/ai/tasks`

通用创建入口：请求体含 `taskType` 与输入字段（`input`、`targetResumeId`、`jobDescriptionId`、`jdText`、`companyName`、`positionTitle`、`resumeTitle`）；请求头可选 `Idempotency-Key`，缺省时服务端生成随机键。成功返回 `202`、`taskId` 与 `PENDING` 状态。`input` 序列化后不得超过服务端语义大小上限（默认 262144 字节，配置项 `app.ai.max-input-json-bytes`），超限返回 `40001` 且不落库（不做截断，避免静默丢数据）。

仅下列任务类型允许经通用端点创建；其余类型必须走各自域端点，违者返回 `40001`：

| 白名单任务类型 | 对应域入口 |
| --- | --- |
| `RESUME_OPTIMIZE` | §7.2 简历优化 |
| `INLINE_OPTIMIZE` | §7.7 实时优化 |
| `MATERIAL_IMPORT` | §7.7 零碎资料导入 |
| `ACHIEVEMENT_GUIDANCE` | §8.1 成果量化引导 |
| `INTERVIEW_COACH` | §9.4 面试专项练习（follow-up） |
| `ATS_ANALYSIS` | §8.2 ATS 体检 |

白名单由服务端单点注册并做枚举完整性检查（fail-closed：新增任务类型未注册即拒绝，不会静默放行）。幂等键、内容指纹与任务状态机语义（同键重放、指纹冲突 `40901`、租约领取、重试上限）详见 ADR-009。

### 7.9 任务续办、重试与选材确认

- `GET /api/ai/tasks/continuations`：可续办任务的**元数据投影**（`id` / `taskType` / `status` / `confirmationStatus` / `resultResumeVersionId` / `retryCount` / 时间），不返回结果 JSON 与输入快照（ideation #52）；

#### AI 分析超时 / 失败时的用户可见行为（产品口径 · 2026-10-01 决策 D5）

**规则分始终可用，AI 只是增量** —— 因此 AI 侧超时/失败**不得**阻塞体检结论：

| 情形 | `analysisStatus` | 用户看到 |
| --- | --- | --- |
| AI 正常 | `COMPLETED`（`analysisSource=AI`） | 规则分 + AI 洞察（`aiInsights`） |
| AI 超时（撞满链总预算 600s）/ 失败 / 未授权 | `RULES_FALLBACK`（`analysisSource=RULES`） | **规则分照常可用** + `fallback.message` 说明原因；`fallback.retryable` 表示可否重试、`fallback.consentRequired` 表示需先授权 |
| AI 任务仍在进行 | `RUNNING` | 前端按 `aiTaskId` 轮询任务状态 |

前端应据 `fallback.retryable` 展示「重试」入口（`POST /api/ats/checks/{id}/ai-retry`），据
`fallback.consentRequired` 引导至同意页；**不得**因 AI 失败而隐藏规则分、或把整次体检判为失败。

> 说明：该口径即**现状固化** —— 「降级为规则分 + `fallback` 暴露」本就已实现（`AtsFallbackInfo`
> 含 `code/message/retryable/consentRequired`），此前只是没有写成产品口径。行为由
> `suite_edges.py` 的「aiFailure 暴露」断言与 `AtsCheckResponse.fallback` 字段契约守护。
> 决策记录见 `docs/decisions/DECISION-BRIEF.md` D5（不引入「后台无限等待」，也不额外新增降级分支）。

### 9.2 投递记录 CRUD

- `POST /api/applications`
- `GET /api/applications`
- `GET /api/applications/{id}`
- `PUT /api/applications/{id}`
- `PATCH /api/applications/{id}/status`

> 列表（`GET /api/applications`）为**摘要投影**（ideation #50）：不返回草稿长文本（`coverLetterText` / `emailBodyText` / `openingMessageText`），改用 `draftCount` 标记卡片上的「n/3」；展开卡片或打开编辑面板时按需调用 `GET /api/applications/{id}` 拉取全文。`feedbackText` 仍在摘要中（列表页客户端搜索会匹配备注，展开面板以其为初值）。

`PATCH /api/applications/{id}/status` 请求体：

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| status | string | 是 | 目标状态，取值见下表；字段名为 `status`（历史文档曾误写作 `targetStatus`） |
| version | long | 是 | 乐观锁版本号，与记录当前值不等时返回 `40901` |
| feedbackText | string | 否 | 投递/面试备注（≤ 30000 字符）；**未发送即保留**语义：缺席或 `null` 不改动现有备注，显式空串（或纯空白）清空备注 |
| note | string | 否 | 本次**状态变化**的说明（≤ 30000 字符），写入 `statusHistory` 的 `note`；状态未实际变化时该字段不落库（不产生历史行） |

状态取值与状态机：`DRAFT`、`APPLIED`、`SCREENING`、`INTERVIEWING`、`OFFERED`、`HIRED`、`REJECTED`、`WITHDRAWN`、`NO_RESPONSE`。服务端按下表校验迁移（**每格逐条枚举，不存在「同层可互跳」的隐含规则**；每态含自循环，用于原地更新 `feedbackText`），非法迁移返回 `40901`。**本表是机器可读契约，不是纯文档**：`ApplicationStatusMatrixContractTest` 以本表的**表头行**作定位锚点，再逐格与 `ApplicationService.TRANSITIONS`、`web/src/views/ApplicationsView.vue` 的 `transitions` 比对（口径以后端为准）。**修改表头文案、或调整行结构（行首反引号状态名、中文顿号分隔、9 行）都必须同步该门禁**，否则门禁会以「找不到迁移表头」失败——设计如此，不允许解析失败后跳过：

| 当前状态 | 允许迁移到 |
| --- | --- |
| `DRAFT` | `DRAFT`、`APPLIED`、`WITHDRAWN` |
| `APPLIED` | `APPLIED`、`SCREENING`、`INTERVIEWING`、`OFFERED`、`REJECTED`、`WITHDRAWN`、`NO_RESPONSE` |
| `SCREENING` | `SCREENING`、`INTERVIEWING`、`OFFERED`、`REJECTED`、`WITHDRAWN`、`NO_RESPONSE` |
| `INTERVIEWING` | `INTERVIEWING`、`OFFERED`、`REJECTED`、`WITHDRAWN`、`NO_RESPONSE` |
| `OFFERED` | `OFFERED`、`HIRED`、`REJECTED`、`WITHDRAWN`、`NO_RESPONSE` |
| `HIRED` | `HIRED`（终态） |
| `REJECTED` | `REJECTED`（终态） |
| `WITHDRAWN` | `WITHDRAWN`（终态） |
| `NO_RESPONSE` | `NO_RESPONSE`、`APPLIED`、`SCREENING`、`INTERVIEWING`、`OFFERED`、`REJECTED`、`WITHDRAWN` |

`NO_RESPONSE` 是唯一可重开的「收尾」态：雇主回复后按实际进展回到 `APPLIED`/`SCREENING`/`INTERVIEWING`/`OFFERED`，或由用户明确关闭为 `WITHDRAWN`；另有一条 **`NO_RESPONSE → REJECTED` 的直接收尾边**，用于「投出去没回音、最终确认被拒」这一最常见的收尾——若强制经 `APPLIED` 中转（`NO_RESPONSE → APPLIED → REJECTED`），会在 `statusHistory` 里留下一条**并不存在**的 `NO_RESPONSE → APPLIED` 事件，污染审计时间线；`REJECTED` 本身仍是终态（只自环），故这条边只进不出。重开时状态历史保留，`NO_RESPONSE` 事件不删除。`HIRED` 为纯终态（入职后离职无法在本模型内表达，与 `REJECTED`/`WITHDRAWN` 同口径）。

`statusHistory`（**仅详情 `GET /api/applications/{id}` 与写操作响应返回**；列表摘要 `ApplicationSummary` 不含该字段，需要时按需拉详情）：

| 字段 | 类型 | 可空 | 说明 |
| --- | --- | --- | --- |
| id | long | 否 | 历史行 ID，与 `changedAt` 共同构成稳定排序 |
| fromStatus | string | 是 | 原状态；记录首条（创建）与 V36 存量回填行为 `null`（前者表示「创建」，后者表示「此前状态不可知」） |
| toStatus | string | 否 | 目标状态 |
| note | string | 是 | 本次变更说明，来自请求体的 `note` |
| changedAt | datetime | 否 | 变更时刻（服务端时间） |

排序：按 `changedAt` 升序、同一时刻按 `id` 升序。写入时机：创建记录时写一条 `fromStatus=null, toStatus=DRAFT`；此后每次状态**实际变化**各写一条；`feedbackText`-only 更新不写历史。**审计边界**：`DELETE /api/applications/{id}` 会物理删除投递记录，历史行随外键 `ON DELETE CASCADE` 一并消失（见 `docs/04` §3.12）——历史用于「进行中的复盘与并发冲突排查」，不是删除后仍须保留的合规审计。

统计口径（`GET /api/applications/stats`）：先定义三个状态集合 —— `A`（投递及以后）= `APPLIED`+`SCREENING`+`INTERVIEWING`+`OFFERED`+`HIRED`；`I`（进入筛选及以后）= `SCREENING`+`INTERVIEWING`+`OFFERED`+`HIRED`；`O`（拿到 offer 及以后）= `OFFERED`+`HIRED`。则 `appliedToInterviewing` = `I / A`、`interviewingToOffered` = `O / I`、`appliedToOffered` = `O / A`，分母为 0 时返回 `null` 而非 0。`NO_RESPONSE`、`REJECTED`、`WITHDRAWN`、`DRAFT` **均不进这三个集合**（无回复不能被算作「已进入流程」，否则转化率被系统性拉低）。时长口径按**当前状态**取行，不做历史回推：`applied` = 当前处于 `APPLIED` 或 `SCREENING` 的记录从 `appliedAt` 到现在的平均天数；`interviewing` = 当前处于 `INTERVIEWING` 的记录从进入该状态的时刻到现在的平均天数；**`totalToOffer` 仅统计当前处于 `OFFERED` 的记录**（从 `appliedAt` 到进入 `OFFERED` 时刻的平均天数）——已是 `HIRED` 的记录不计入该指标，因此「标记录用」会让该指标的样本数减一（口径取舍，非数据丢失；明细仍在 `statusHistory`）。三者均有兜底：`appliedAt` 为空时回退 `createdAt`，进入时刻为空时回退 `updatedAt`（仅存量极端行会命中）。

### 9.4 AI 面试

会话与轮次：

- `GET /api/interviews`：当前用户的面试会话历史；可选 `jobDescriptionId` 过滤。
- `POST /api/interviews/start`：发起面试。请求头必须携带 `Idempotency-Key`；请求体须指定 `sourceType`、`interviewMode`；平台简历模式提供 `resumeVersionId`，外部文本模式提供 `externalResumeText`（≤100000 字符）；可选 `jobDescriptionId`、`targetQuestionCount`（4–12）、`outputLanguage`、`initialQuestion`（≤500 字符）。
- `GET /api/interviews/{id}`：查询会话当前状态、当前问题与 AI 失败信息；`lastEvaluation` 只含**最近一轮**。该端点是前端 1/2/4/5s 轮询的热路径，服务端只读取末轮记录（`round_no desc, id desc` 取 1 条），单次调用的读取量与已完成轮数**无关**——此前全量读取本会话所有轮次（含 `answer_text`/`feedback_json`）再取末条，实测 9 轮会话每次轮询向数据库取 99.6KB，改后 13.6KB（契约由 `InterviewStateAssemblerTest.buildStateResponse_neverLoadsAllRecords` 守护）。
- `POST /api/interviews/{id}/answer`：提交本轮回答，请求头必须携带 `Idempotency-Key`；返回本轮反馈和下一题。
- `POST /api/interviews/{id}/finish`：提前结束面试；至少完成 1 题后才可结束，AI 操作进行中返回 `40901`；重复调用幂等返回当前状态。
- `GET /api/interviews/{id}/report`：读取面试报告（只读）。

AI 失败处置：

- `POST /api/interviews/{id}/ai/retry`：对最近一次失败的 AI 操作重试（仅 `AI_ACTION_REQUIRED` 状态）。**异步执行**：请求只做校验与计数，立即返回 PROCESSING 状态（首题重试为 `GENERATING_QUESTION`，评估重试为 `EVALUATING_ANSWER`），AI 由与 `/answer` 相同的后台执行器承载，终态经 `GET /api/interviews/{id}` 轮询获取；执行器队列满时以 `200` + `aiFailure`（`messageCode=QUEUE_REJECTED`，可重试）快速失败，不会让会话静默停在 PROCESSING。
- `POST /api/interviews/{id}/continue-with-rules`：放弃 AI，降级为规则模式继续（`RULE_FALLBACK` 为终态，不可逆）。
- `POST /api/interviews/{id}/follow-up`：基于已完成的会话与某个薄弱项创建专项练习（异步 AI 任务）。请求头必须携带 `Idempotency-Key`，会话须为 `COMPLETED`；请求体 `weakness` 必填且 ≤500 字符；**必带** `X-AI-Preview-Token`（缺 `40001`、不符 `40901`，均不落库，见 §18.2.4）；返回 `202` 与任务标识，完成后通过 `GET /api/ai/tasks/{id}` 读取结果。
- `POST /api/interviews/{id}/follow-up/preview`：发起前的发送前预览（只读，返回待发 `messages` 与 `previewToken`，见 §18.2.4）。

同一轮回答即使更换幂等键重复提交也会被服务端拒绝（`40901`），不会产生第二次评估；回答原文在 AI 调用前先落盘，重试无需用户重新输入。会话归属、轮次顺序和报告只允许所属用户访问。幂等键与 attempt 状态机详见 ADR-010。`/answer` 与 `/ai/retry` 均不在请求线程内等待 AI（单次评估实测平均 108.7s，远超前端 60s 超时）：二者都以「秒回 PROCESSING + 前端轮询 `GET /api/interviews/{id}`」收口，里外一致。

面试引用的平台简历版本若已归档，发起（`/start`）与**进行中每轮的评估**都会以 `40902` +「该简历版本已归档，请先恢复后再继续」拒绝——归档是可逆状态，恢复该版本后重试即可，不会回落为原因错误且重试无效的「简历版本不存在」（口径与 ATS/评分/导出一致；归属校验先于归档判定，他人版本仍以 `40401` 收口，不泄露归档状态）。前端按 `aiFailure.messageCode === 'VERSION_ARCHIVED'` 在失败面板给出「先恢复该版本再重试」的双语指引（不透传服务端 message），由 `web/e2e/interview-archive-failure.spec.ts` 守护。

### 9.5 沟通模板库与草稿

- `GET /api/communications/templates?scene=&type=&outputLanguage=`：内置模板 + 本人自定义模板，按 `usageCount` 降序；

## 11. 导出接口

### 11.1 发起 PDF 导出

`POST /api/exports/pdf`

请求体：

```json
{
  "resumeVersionId": 1,
  "templateCode": "classic"
}
```

返回：

```json
{
  "taskId": 3001,
  "status": "PENDING"
}
```

结果复用：同一（用户, 简历版本, 模板）已存在未过期的在途（`PENDING`/`RUNNING`）或 `SUCCESS` 任务时，直接返回该任务（`taskId` 与当前状态），不再重复排队渲染；PDF 内容由（版本, 模板）唯一决定，已过期的 `SUCCESS` 任务才重新渲染。文件过期判定为条件更新：仅当服务端真正把任务落地为 `EXPIRED` 时才把响应标为已过期，行被并发推进（例如过期前重试排队）时返回库存最新状态。

体积上限：调用 PDF 服务前按序列化字节校验**输入**（`app.pdf.max-input-bytes`，默认 512KB），渲染结果**落盘前**校验**输出**（`app.pdf.max-output-bytes`，默认 10MB）——超限的导出任务失败，任务记录给出「导出数据/文件超出最大允许大小」的明确原因，文件不落盘也不可下载；pdf-service 侧另有 `PDF_SERVICE_MAX_OUTPUT_BYTES`（默认同名 10MB）作第二道闸，其取值不得低于 API 上限（否则 API 声明的允许区间不可达）。声明、消费点与跨运行时关系由 `PdfOutputBoundContractTest` 守护。

## 13. 简历导入接口

`POST /api/resume-imports/parse`（`multipart/form-data`，字段 `file`）

解析 TXT / PDF / DOCX 为可编辑文本与初步结构化输入；响应含 `fileName` / `mediaType` / `extractedText` / `normalizedResumeInput` / `originalFileStored`。

单文件超过 5MB（`spring.servlet.multipart.max-file-size`）时返回 **`413` + `40001`**（生产环境前置 nginx 的同名限制亦为 413）；非法 multipart 表单返回 `400` + `40001`。

代理层体积契约：`edge`/`web` 两层 Nginx 均显式声明 `client_max_body_size 6m`（nginx 内置默认仅 `1m`，漏声明会让内层把上限悄悄收紧为 1m；取 6m = 应用的「整请求」上限 `max-request-size`，**而非**单文件上限 5MB——该指令限制整个请求体含 multipart 开销，按 5MB 对齐会让恰好 5MB 的文件在边界被 413 拒绝）；文件级 5MB 判据由应用持有并返回统一信封；契约由 `UploadPathContractTest` 守护。

资源边界（ideation #17）：单文件 ≤5MB；PDF 页数 ≤60；抽取文本 ≤200000 字符；单次解析 ≤15s（超时按业务错误返回，不落任何数据）。

## 15. 联调注意事项

- 所有需要登录的接口必须在 Header 中携带 `Authorization: Bearer {token}`
- 创建、更新类接口必须做参数校验
- `resumeJson`、`explanation` 等复杂结构字段建议前后端统一 Type 定义
- AI 接口需要约定好失败提示文案和重试逻辑
- 岗位定制生成接口必须返回资料选择结果；服务端需校验被引用资料和 JD 均属于当前用户
- 所有 AI 创建接口必须携带幂等键，并执行用户同意、输入长度、任务类型配额和限流校验
- 所有按 ID 查询的子资源必须沿父链校验当前用户归属，包括版本、AI 任务、评分、导出任务和文件；不得只按裸 ID 查询
- AI 任务轮询建议使用 1s、2s、4s、5s 的退避并以 5s 封顶；页面重载后必须能够从任务 ID 恢复，不得重复创建任务
- 投递状态更新必须带目标状态与乐观锁版本；非法迁移返回 `40901`
- 下载 PDF 时不得返回永久公开 URL；未登录、跨用户、过期和已删除资源均应拒绝
- 前端 `web/src/api/*.ts` 中每个 `/api` 调用的 `(method, path)` 必须在后端控制器中存在（否则运行时 404/405）；由静态门禁 `FrontendApiContractTest` 守护（第五十六批对账：**93 个前端调用 × 95 个后端端点，双向一致、零缺陷**）
- 反向不约束：后端存在而前端未调用的端点是合理的（运维端点 `GET /api/system/health/detail`、暂无 UI 入口的 `POST /api/auth/logout-all`），故门禁只做「前端 → 后端」单向断言

## 17. 桌面本地工作区接口

仅在**桌面模式**（`--spring.profiles.active=desktop`）下可用；在线部署里这些端点返回 404，
避免把「本地工作区快照」误当云端能力。设计与取舍见
[`ADR-012`](../decisions/ADR-012-windows-desktop-local-workspace.md)。

- `GET /api/desktop/backups`
- `POST /api/desktop/backups`
- `POST /api/desktop/backups/{backupId}/restore`

**备份形态**：H2 的 `SCRIPT TO` 导出的 SQL 文本（含全部表结构、数据与 `flyway_schema_history`），
落在数据目录的 `backups/` 下。选 SQL 脚本而非复制 `.mv.db` 文件，是因为数据库文件在运行时被连接占用，
而脚本**可以被独立校验**。快照**不含 AI 凭据**（AI 凭据是本地设置，不属工作区内容，R34）。

**恢复语义**（R39）：顺序固定为「**先校验 → 再建安全备份 → 才替换工作区**」。
校验方式是把快照放进**一次性临时库真跑一遍**（快照必须真能被 H2 执行，而不只是语法正确）。
校验不通过则直接拒绝，**当前工作区一个字节都不动**；执行过程中失败会用安全备份回滚。
恢复会重建全部表结构，因此需要清掉持久化上下文与二级缓存，否则仍会读到旧数据。

## 18. 桌面端迁移导入端点

仅在**桌面模式**（`--spring.profiles.active=desktop`）下可用；在线部署返回 404。

前端入口是「桌面工作区」页面（路由 `/desktop`）。在线部署下该入口不显示、直接访问会被守卫送回工作台：
页面挂载后会发一次 `GET /api/desktop/backups` 探测能力，非 200 即视为不可用（不阻塞首屏，详见 `composables/useDesktopMode`）。

- `POST /api/desktop/import/preview`
- `POST /api/desktop/import/apply`

请求体是 Web 端导出的**工作区包**（`formatVersion` 3，含 `manifest` 与逐条记录的 `stableId`），
返回把记录分成三类的结果：

| 类别 | 判据（R37） |
| --- | --- |
| 新增 | 本地没有这个 `stableId` |
| 跳过 | `stableId` 已有，且**归一化后内容一致**（比较时只取包里给出的字段；字段名驼峰/下划线归一；忽略 id / userId / 时间戳等易变字段） |
| 冲突 | `stableId` 已有，但内容变了 —— 交给你选择保留哪一版，**绝不按文本相似度自动合并** |

包内若出现本版不支持的集合（如访谈会话、沟通模板），预览结果会**点名列出**这些集合而不是静默丢弃；
缺 `manifest` 或格式版本高于支持范围的包会被**整份拒绝**。

`POST /api/desktop/import/apply` 的请求体是 `{ "package": {...}, "resolutions": { "<稳定ID>": "KEEP_LOCAL" | "USE_IMPORTED" | { "字段": "值" } } }`：
`resolutions` 只用于**冲突**记录（新增与跳过不需要指定；未指定的冲突默认保留本地）。
应用是**原子**的：任何一步失败整体回滚，工作区保持原状。
导入会按依赖顺序（岗位 → 职业资料 → 简历 → 版本 → 投递 → 状态历史）执行，把 Web 侧主键**重映射**为本地自增主键，
并逐级改写外键（投递记录引用的是 Web 侧的岗位/简历版本 ID，本地要用映射后的本地 ID）。

### 18.1 返回结构（预览）

`preview` 返回 `packageId`、三个计数、`unsupportedCollections`，以及逐条 `items`：

| 字段 | 含义 |
| --- | --- |
| `collection` | 集合路径。取值域固定 6 个：`jobDescriptions` / `careerMaterials` / `resumes` / `applications` / **`resumes.versions`** / **`applications.statusHistory`**（点分表示嵌套层级） |
| `stableId` | 包内稳定记录 ID；嵌套记录带父前缀（`web:resumes:5:versions:9`） |
| `decision` | `ADD` / `SKIP` / `CONFLICT` |
| `entityType` | 本地表名（`resume` / `resume_version` / `application_status_history` …），与导入映射表的 `entity_type` 同口径 |
| `localId` | 本地已有记录的 id；`ADD` 时为 `null` |
| `reason` | 面向用户的中文说明 |
| `localSnapshot` / `importedSnapshot` | 本地行与包内记录的快照，供冲突对比；`ADD` 的 `localSnapshot` 为 `null` |

三条口径（自批次 1.4 起成立，有守护用例）：

1. **计数计入嵌套**：恒有 `added + skipped + conflicts == items.size()`；
2. **`items` 顺序即写入顺序**：父记录先于其子记录，按 `items` 顺序重放不会违反外键；
3. **嵌套记录与顶层同规则**：同 `stableId` 内容变了同样判 `CONFLICT`，`resolutions` 的键可以是子记录的 `stableId`。
   父记录判 `SKIP` / 保留本地时，子记录仍按**自己的**决策处理（不会被父的分支吞掉）。

### 18.1.1 已知边界与特例

- **同编号简历版本被占用**：本地已存在 `(resume_id, version_no)` 相同的另一条版本时，该版本被判 `SKIP`，
  `reason` 明示「本地已存在同编号的简历版本」，**不改动本地数据、也不改号**（改号会破坏二次导入的幂等）。
- **当前版本指针**：导入结束后 `resume.current_version_id` 指向包里声明的 `currentVersionId`
  （映射得到本地版本时）；解析不到则保持不变，不猜。
- **外键改写**：`resume_version.created_by` 一律改写为**本地用户**（桌面工作区只有一个本地用户，包内是 Web 用户 id）；
  `restored_from_version_id` 能在包内解析则映射成本地版本，否则置 `NULL`；
  投递的 `job_description_id` / `resume_version_id` 若在包内找不到，**整份拒绝**（列 NOT NULL，不写半份）。
- **幂等**：只由 `stableId` 映射保证（映射表 `source_stable_id` 唯一）。状态历史没有唯一键，
  因此**不做**「同父 + 同时间 + 同状态即视为同一条」的自然键去重 —— 那属于按内容合并，违反 R37。
- **映射悬空**：映射存在但本地行已被留存清扫删除时，按新增处理并修正映射（否则该记录永久无法再导入）。

## 18.2 AI 任务发送前预览（R32）

| 端点 | 说明 |
| --- | --- |
| `POST /api/ai/tasks/preview` | 返回**将要发送的确切 messages**、本轮脱敏摘要与 `previewToken`。**只读**：不写库、不调 provider |

请求：`{"taskType": "...", "input": {...}, "includeContact": false}`（`includeContact` 省略时按 `false` 处理）。

响应字段：

| 字段 | 说明 |
| --- | --- |
| `messages` | 实际会发给模型的消息（`[{role, content}]`），已按脱敏策略处理 |
| `includeContact` | 本次是否包含联系方式 |
| `redactions` | 被替换的类别与次数（如 `[{category: "EMAIL", count: 1}]`） |
| `previewToken` | 提交任务时必须回传的令牌 |

**创建任务必须带令牌**：把 `previewToken` 放进 `input._previewToken`（下划线开头的键不会进入 prompt 正文）。

| 情况 | 响应 |
| --- | --- |
| 未带 `previewToken` | `40001`，**不落库** |
| 令牌与当前载荷不符（预览后改了内容或切换了脱敏开关） | `40901`，**不落库** |
| 令牌有效 | 正常 `202` |

脱敏口径：**默认排除邮箱与手机号**（替换为 `[EMAIL]` / `[PHONE]`），URL、版本号、金额与正文不动。
用户显式要求包含时，预览与发送都会原样发出。

## 18.2.1 选材预览（JOB_MATERIAL_SELECTION）

| 端点 | 说明 |
| --- | --- |
| `POST /api/ai/select-materials-for-job/preview` | 返回选材任务**将要发送的确切 messages** 与 `previewToken`。只读：不落库、不调 provider |

请求体与创建端点相同。候选筛选与 prompt 组装由 `MaterialSelectionContextBuilder` 统一提供 ——
与 worker 执行时用的是同一个类，因此预览内容与实际发送内容同源。
没有可用素材时返回 `40001`（提示先补充职业资料）。

## 18.2.2 生成预览（JOB_GENERATION）

| 端点 | 说明 |
| --- | --- |
| `POST /api/ai/tasks/{selectionTaskId}/confirm-materials/preview` | 返回岗位简历生成任务**将要发送的确切 messages** 与 `previewToken`。只读：不落库、不调 provider、不消耗配额、不改选材确认状态 |

请求体与 `POST /api/ai/tasks/{taskId}/confirm-materials` 相同（`ConfirmMaterialsRequest`：
`selectedMaterialIds` / `forcedIncludedMaterialIds` / `resumeTitle` / `taskUpdatedAt`）。
两条链路共用同一份组装实现：`MaterialSelectionConfirmationService#buildGenerationInput` 产出子任务快照
（confirm 落库的就是这一份），`JobGenerationInputAssembler` 由快照得到待发消息（worker 执行时同步调用），
因此预览内容与实际发送内容同源。

预览的前提条件（不满足即返回业务错误，**不写库**）：

| 情况 | 响应 |
| --- | --- |
| 选材任务不属于当前用户，或 `taskType` 不是 `JOB_MATERIAL_SELECTION` | `40401` |
| 选材任务尚未成功（`status != SUCCESS`），没有候选结果可确认 | `40901` |
| 提交的素材不属于本轮候选、或数量不在 1..30 | `40001` |
| 岗位已不存在 / 素材已删除（不属于当前用户） | `40401` |

`confirmationStatus` 为 `PENDING` 是预览的正常前置状态（预览发生在确认之前）。

**确认选材必须带令牌**：把预览返回的 `previewToken` 放进请求头 `X-AI-Preview-Token`。

| 情况 | 响应 |
| --- | --- |
| 未带 `X-AI-Preview-Token` | `40001`，且 `ai_task` **零新增**（选材任务仍为 `PENDING`） |
| 令牌与当前请求不符（预览后改了 `selectedMaterialIds` / 强制加入） | `40901`，且 `ai_task` **零新增** |
| 令牌有效 | 正常 `202`，创建 `JOB_GENERATION` 子任务并把选材任务置为 `CONFIRMED` |

令牌校验的位置是**幂等重放之后、任何写库之前**：同一 `Idempotency-Key` 的重复提交按幂等语义直接返回既有子任务
（不会因为重试时缺令牌而失败），而真正创建之前一定先验令牌。

## 18.2.3 沟通文案预览（COMMUNICATION_GENERATE）

| 端点 | 说明 |
| --- | --- |
| `POST /api/communications/ai-generate/preview` | 返回沟通生成任务**将要发送的确切 messages** 与 `previewToken`。只读：不落库、不调 provider、不消耗配额、不要求 `Idempotency-Key` |

请求体与 `POST /api/communications/ai-generate` 相同（`GenerateCommunicationRequest`：
`resumeVersionId` / `jobDescriptionId` / `type` / `outputLanguage`）。

**为什么预览必须连三段式 prompt 一起算**：`CommunicationAiService` 是拿任务 input 现场调
`CommunicationAiPromptBuilder#build(Map)` 得到消息的，**不走** `PromptTemplates` 回落。
因此 `CommunicationService#prepareInput` 同时产出「落库的任务 input」与「待发 providerInput」，
预览与创建共用同一份，避免「看到的」和「发出去的」是两套模板。

预览前置校验：版本/岗位不属于当前用户 → `40401`；版本已归档 → `40902`。

**创建必须带令牌**：`X-AI-Preview-Token` 请求头。

| 情况 | 响应 |
| --- | --- |
| 未带 `X-AI-Preview-Token` | `40001`，且 `ai_task` **零新增** |
| 令牌与当前请求不符（预览后改了 `type` / 版本 / 岗位） | `40901`，且 `ai_task` **零新增** |
| 令牌有效 | 正常 `202` |

校验位置与生成一致：**幂等重放之后、配额与写入之前**（`AiTaskService#create` 的 `beforeCreate` 守卫），
因此同一 `Idempotency-Key` 的客户端重试不需要重复带令牌。

## 18.2.4 面试追问预览（INTERVIEW_COACH）

| 端点 | 说明 |
| --- | --- |
| `POST /api/interviews/{id}/follow-up/preview` | 返回追问练习任务**将要发送的确切 messages** 与 `previewToken`。只读：不落库、不调 provider、不消耗配额、不要求 `Idempotency-Key` |

请求体与创建端点相同（`FollowUpPracticeRequest`：`weakness`，必填且 ≤500 字符）。

**为什么必须抽 dry-run 组装**：这段 prompt 原本只在 `InterviewFollowUpAiService.executeTask`
里现场拼（任务创建时根本不存在"将要发送的内容"）。现在由 `InterviewFollowUpPromptAssembler`
统一产出 `_systemPrompt` / `_taskPrompt`，worker 与预览共用，因此两侧逐字节相同。
其中 `InterviewPromptContextAssembler` 只读（不写库、无事务），可安全用于预览。

预览前置校验：会话不属于当前用户 → `40401`；会话不是 `COMPLETED` → `40901`；
`weakness` 为空或超 500 字 → `40001`。预览**不校验 consent**（授权是创建期检查）。

**创建必须带令牌**：`X-AI-Preview-Token` 请求头。缺 → `40001`、不符（预览后改了 `weakness`）→ `40901`，
均 `ai_task` 零新增。校验位置同样是**幂等重放之后、配额与写入之前**，同键重试无需重复带令牌。

## 18.2.5 ATS 分析预览（ATS_ANALYSIS）

| 端点 | 说明 |
| --- | --- |
| `POST /api/ats/checks/{id}/preview` | 返回该检查的 AI 分析**将要发送的确切 messages** 与 `previewToken`。只读：不落库、不调 provider、不消耗配额、不要求 `Idempotency-Key`、不改检查状态 |

### 与其它四个领域的唯一差异：AI 启动是两段式的

前四片都是「预览 → 带令牌创建」，一步到位。ATS **不行**，原因是 prompt 正文里带着
`atsCheckResultId` —— worker 靠它把 AI 结论写回那条检查记录。这就造成一个死锁：

1. 令牌 = 服务端对**自己组装的 input** 算 SHA-256；
2. 组装 input 必须有真实的 `atsCheckResultId`；
3. 而首次检查时，检查记录还不存在（id 要落库后才有）；
4. 于是「预览必须先有 check，而首次检查没有 check」。

被否决的方案是「改 prompt 把 id 剔掉」——那会改动 AI 实际收到的输入，
动摇已建立的 ATS 评估基线，代价远大于收益。

采纳的方案（D-AI-11）是**不动 prompt，改为收敛 AI 的启动入口**，把它拆成两段：

| 段 | 端点 | 行为 |
| --- | --- | --- |
| 第一段：检查 | `POST /api/ats/check` | **总是**落库检查记录。带令牌 → 直接启动 AI；不带令牌 → **不创建** `ai_task`，返回 `analysisStatus=RULES_FALLBACK` 且 `fallback.code=PREVIEW_REQUIRED`（`retryable=true`，`consentRequired=false`） |
| 第二段：启动 AI | `POST /api/ats/checks/{id}/preview` → `POST /api/ats/checks/{id}/ai-retry` | 先预览拿令牌，再带令牌重试，此时才创建 `ai_task` |

即「不带令牌的 `/check` 不再静默启动 AI」，而是把规则结论照常交付、
把"要不要发 AI"的决定权交回给客户端。代价是客户端多一步「预览 → 启动」，
换来的是 ATS 与其它领域**同一套预览协议**，且 AI 实际输入一字未改。

`useAi=false` 的纯规则检查**完全不受影响**，仍返回 `analysisStatus=RULES_ONLY`
且不带 `fallback` 字段 —— 只有「启动 AI」才需要预览确认。

### 新增的 fallback 码

`AtsFallbackCode` 新增 `PREVIEW_REQUIRED`：

| 字段 | 值 | 说明 |
| --- | --- | --- |
| `code` | `PREVIEW_REQUIRED` | 需要先预览确认 |
| `retryable` | `true` | 预览后重试即可继续 |
| `consentRequired` | `false` | 与授权无关，不要误导前端去引导授权 |

### 错误码

| 场景 | 结果 |
| --- | --- |
| 启动 AI 未带 `previewToken` | 落 `PREVIEW_REQUIRED` 兜底（HTTP 200，非 40001） |
| `ai-retry` 未带 `previewToken` | `40001`，`ai_task` **零新增** |
| 令牌来自另一次检查 | `40901`，`ai_task` **零新增** |
| 令牌有效 | 正常 `200` 且返回 `aiTaskId` |

**注意两段的区别**：`/check` 不带令牌是**正常的兜底路径**（检查照常完成，只是不跑 AI），
所以返回 200 + `PREVIEW_REQUIRED`；而 `/ai-retry` 的语义就是"我现在要发 AI"，
缺令牌/令牌错是协议错误，必须 40001/40901 抛给客户端，不能被兜底逻辑吞掉。

### 校验顺序（ATS 专有）

`startAiOrFallback` 的顺序是**可用性 → 令牌 → 落库任务**：

- 可用性检查在最前 —— 无密钥环境（如测试默认 profile）要先落成 `AI_DISABLED`，
  令牌校验不能抢在它前面，否则会把"服务没配"误报成"你没预览"。
- 令牌校验在 `createTask` 之前 —— 被拒绝的请求不消耗配额、不产生 `ai_task` 行。

`retryAi` 里令牌守卫放在 `try` **之外**：否则 `applyExpectedFallback` 会把
令牌异常也吞成规则结果，客户端永远看不到 40901。

## 18.3 桌面端本地 AI 设置端点（ADR-012 阶段五 / R31）

同样只在**桌面模式**下存在，在线部署返回 404（已登录 404 / 匿名 401）。
密钥处理是本节的要点：**写接口可以带 `apiKey`，任何读接口都不回传它** —— 页面只知道"有没有存过"。

| 端点 | 说明 |
| --- | --- |
| `GET /api/desktop/ai-settings` | 读取设置；未配置时返回默认值（不落库），让页面有可填内容 |
| `PUT /api/desktop/ai-settings` | 保存 `baseUrl` / `model` / `enabled`，可选 `apiKey`。`apiKey` 为空表示"只改其它字段"，不会清掉已有密钥 |
| `DELETE /api/desktop/ai-settings` | 删除设置**与加密凭据** |
| `POST /api/desktop/ai-settings/test` | **显式**测试连接（R31）：真的向所配端点发一次最小请求；请求体可空，带 `apiKey` 时用它测（允许"先测再存"） |

响应字段（`GET`/`PUT`）：

| 字段 | 说明 |
| --- | --- |
| `providerCode` | 首版固定 `openai-compatible`（ADR-012 D7） |
| `baseUrl` / `model` | 端点根地址与模型名 |
| `enabled` | 是否启用本地设置 |
| `credentialPresent` | 本机是否已保存加密凭据（**不含密钥本身**） |
| `credentialStoreAvailable` / `credentialStoreName` | 当前保护器是否可用及其名字（非 Windows 时 DPAPI 不可用） |
| `lastTestedAt` / `lastTestOk` / `lastTestMessage` | 最近一次测试连接的时间、结果与说明 |

生效口径：`PUT` 成功后**立即**对后续 AI 任务生效（无需重启）；`enabled=false` 或 `DELETE` 会回落到
配置文件/环境变量里的 AI 配置。覆盖生效时只使用本设置里的那一个 `model`，不沿用配置中的模型链。

密钥落盘（R34 / D8）：`<dataDir>/ai-credentials/user-<id>.bin`，用 Windows DPAPI
（`CryptProtectData`，用户级 + 应用/用户派生的 entropy）加密，**在工作区库之外** ——
因此不会进备份、Web 导出包或桌面迁移包。非 Windows 环境不降级为明文，直接判"不可用"。
