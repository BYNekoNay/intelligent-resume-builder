## 6. 确认的生产缺陷（P1）：ATS 关键词覆盖度被系统性低估

**这不是新发现**（`docs/decisions/OPEN-DECISIONS.md` 已登记 E3-F1），但本轮**在新环境上复现，并取得了比登记册更精确的证据**。

### 6.1 复现证据（对同一份简历与 JD）

| 事实 | 实测 |
| --- | --- |
| 简历正文是否**逐字**含 `Spring Boot` | **是** |
| JD 是否**逐字**含 `Spring Boot` | **是** |
| ATS 风险项判定 | ❌ `缺少 JD 关键词: Spring Boot, MySQL, Redis, 高并发` |
| `keywordCoverage` | **20.0**（若 `Spring Boot` 正确命中应为 **40.0**） |
| 对照：`Java`（单词关键词） | ✅ **正确命中**，未出现在缺失列表 |
| 对照：`MySQL` / `Redis`（简历里确实没有） | ✅ **正确判缺失** |
| 配置是否齐全 | `application.yml` L206–213 明确配置 `synonym-dictionary`，含 `spring: ["spring","spring boot","spring cloud"]` |

### 6.2 缺陷边界（本轮新收敛的结论）

不是"关键词全判错"，而是**精确地只错在多词关键词上**：

- **单 token 关键词**（`Java`）→ 判断**正确**；
- **含空格的多词关键词**（`Spring Boot`）→ **必然误判缺失，即使两侧逐字相同**；
- 真正缺失的关键词（`MySQL`/`Redis`/`高并发`）→ 判断**正确**。

**影响**：① 用户看到的 ATS 规则分**低于其应得分**；② 风险项会建议用户"补充 Spring Boot"——**而用户简历里本来就有**，属误导性建议。本项**不传导到 AI 层**（同一次检查中 AI 的分析正确指出了真实缺口）。

### 6.3 待决策的修法（沿用登记册的三个选项，未擅自实施）

1. 让配置词典真正生效（同时修 tokenizer 对多词关键词的处理）；
2. 或明确废弃该配置并移除；
3. 至少补一条"配置词典生效"的测试。

> 本轮**刻意未修**：修它会改变评分行为，应先确认采用哪个口径，并配套回归用例。

## 7. 测试工具自身的问题（诚实披露）

本轮 58 项断言最终全绿，但**前几轮曾产出错误结论**，全部源于我的测试脚本缺陷而非被测系统：

| # | 缺陷 | 造成的错误结论 | 根因 |
| --- | --- | --- | --- |
| 1 | `C="curl -s --noproxy *"` 中的 `*` 被 shell 展开成文件列表 | 公网验证输出全是垃圾（出现无关的 FASTPANEL 页面），**首轮结论作废** | 变量拼接 + 未加引号 |
| 2 | 用 `bash /tmp/test_non_ai.py` 执行 Python 脚本 | 报一堆 `command not found` | 解释器用错 |
| 3 | 导出接口按 `data.id` 取值（实际字段是 `data.taskId`） | **7 个已成功创建的导出任务被全判为失败** | 未先读响应契约 |
| 4 | 探针函数用 `token=` 传参（形参名是 `t`） | 探针中断，未取到证据 | 未核对签名 |
| 5 | SQL 查 `completed_at` 列（该表无此列） | 耗时明细查询失败 | 未先看表结构 |

**可复用教训**：本轮第 3、4、5 条与上一轮审计脚本的两个 bug **是同一类错误** —— **凭印象假设接口/字段名，而不先读契约**。
对策已在本轮落实：所有断言前先读 DTO/表结构；写入结论前用**已知坏样本**验证判据会失败（第 3 条的修正即由此发现）。
