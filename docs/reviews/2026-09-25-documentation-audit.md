### 核心结论：问题不在"文件太多"，而在**三类时效性缺陷**

审计没有发现需要删除的文档。真正的问题是这个体系**缺少"时效性标注"这一层**，导致三类误导：

| 类型 | 实例 | 危害 |
| --- | --- | --- |
| **① 单文档内部自相矛盾** | `docs/ideation/2026-09-04-...md` 顶部"当前仍存在的错误或风险"把 **#10 / #34 / #35** 列为现存风险，而同一文档后半部分的"第四十二/四十三/四十四轮审查问题修复"已记录它们**已修复** | **最严重**：读者只读顶部就会去"修一个不存在的问题" |
| **② 状态行与事实不符** | `docs/plans/2026-09-23-001` 状态行仍写"待确认（未动工）"，实际方案已实施并验收通过；`docs/plans/2026-09-01-001` 的"候选/待做项"多数已闭环 | 误导排期与工作量评估 |

| **链接提取未跳过代码块** | 报出 2 条"失效链接"，实为我在本报告里**引用的示例文本** | 先把 ``` 围栏与 `行内代码` 剥离再提取 | 假失效（2 条） |
| **索引覆盖率判据恒真** | 输出"收录 80/80，0 遗漏" | Windows 下 `os.walk` 产出反斜杠路径，而过滤条件写的是 `p.startswith('docs/')` → 集合恒为空 → **差集恒为 0** | **结论完全无效**：真实为 6 个未收录，其中 1 个（ADR-007）是真实遗漏 |

修正后重新取数，才发现 `docs/README.md` 确实漏了 ADR-007 与 `ats-reasoning-eval/` 的 4 个子文件，已补齐。

> **这条比任何一个文档缺陷都更值得记**：审计的价值完全取决于判据是否真的在执行。
> 一个"永远返回通过"的检查会让人误以为体系健康 —— 本次两名受害者都是"看起来很有说服力"的输出
> （`237 条链接 / 失效 1 条`、`80/80 全覆盖`）。**新增任何门禁或校验脚本时，必须先用已知的坏样本验证它会失败。**

### 5.2 其他方法论教训（供后续复用）

1. 用 `grep -c $'\r'` 判断 CRLF 在本机 Git Bash 下会匹配每一行，曾把一个纯 LF 文件报成"全程 CRLF" —— **判据本身要被质疑**；
2. "未完成标记 51 处"实际全是 `待确认` 等**领域术语**误报，靠人工复核才排除 —— **关键词扫描必须人工过一遍**；
3. 因此本报告每条结论都标注**验证方式**，而非只给判定。
