### 1.1 架构师贡献的三项独有输出（其余角色未给出）

**① 最脆弱三点的机制层表述**（不是现象层）：

| 脆弱点 | 机制 | 若失效的后果 |
| --- | --- | --- |
| 同一业务事实缺少单一真相来源 | 读写模型混淆 + JSON 无模式约束 + 前后端契约并行维护 | 修一处漏一处（**这正是本轮 4 个缺陷的共同形态**） |
| worker 领取机制 | `FOR UPDATE` + `ORDER BY id` 串行 | 长任务饿死短任务；**这是"架构级"而非配置级问题** |
| 单机共置（与另一个项目共用 3.6 GiB） | 内存静默竞争 | 无 OOM 告警则故障不可归因 |

**② 判据清晰的两栏债务划分**：

- **现在必须还**（只在证明有备用容量时才可延期）：① 同步端点输入上限（`OFFSET` 分页 / 全文 `like` 扫描 / 无长度边界的列表）；② 外部流量重试幂等；③ 长耗时调用释放 DB 连接；④ 资金级写路径事务边界。
- **可以延后**（记录 + 触发器条件即可）：多方言 SQL 抽象层、监控栈拆分、配置中心化、读写分离。

**③ 机制层结论（值得单独记住）**：

> 缺陷率**不随代码量增长，而随"生产者—消费者边数"增长** —— 每新增一种文档载体（第二真相来源），
> 同类缺陷概率上升。这解释了为什么本项目质量最高的地方恰好是**消费者唯一的地方**
> （AI prompt 契约、JSON schema、Flyway 迁移、i18n 文案）。

**④ 架构师另外指出证据包的不足（已在本报告 §3 补齐）**：未标注"哪条链路哪个端点无压测数据"、
"4 处已修缺陷没有附 diff 与回归测试名"、"未说明是否有前端单元测试基础设施"。
→ 已补：回归测试名为 `ScoringDictionaryBindingIT` / `KeywordCoveragePhraseTest` / `NormalizerTest`(扩展) / `templates.test.js`(+6)；
前端**无**单元测试框架（未装 vitest）。

## 3. 我在汇总阶段补充实测并**纠正的三处判断**（含我自己的一处错误）

为保证结论可信，六角色报告中标注"需实测/需读代码"的关键项，我在汇总阶段逐项核实。

| # | 谁的判断 | 核实结果 | 处置 |
| --- | --- | --- | --- |
| 1 | **我自己的初步判断**：告警规则中有 4 个指标（`resume_ai_provider_calls_total` / `resume_ai_quota_rejections_total` / `resume_ai_task_attempts_total` / `resume_pdf_export_tasks_total`）"应用未暴露 → 规则永不触发" | ❌ **我的判断错误，已撤回**。这 4 个指标在 `AppObservability` 中**确实被定义为 Counter**；Micrometer 的计数器在**零样本时不导出序列**，而 API 在部署时刚重启、AI 调用发生在重启之前 → 属于**取样假象**，不是死规则 | 不作为缺陷上报 |
| 2 | **后端角色**："所有 `ai_task.retry_count=1`，疑似参数被硬编码或重试语义异常" | ❌ **误判**。项目文档明确"`retryCount` 只在 worker 实际领取执行时增加"，故 `1` = **首次执行**，属设计如此 | 归因于**证据包未写明该语义**，已在此加固 |
| 3 | **后端/架构师**：担心 131 秒外部调用在事务内占住数据库连接 | ✅ **不成立（好消息）**。实测 `TaskExecutionService` **没有 `@Transactional`**，AI 调用不在事务内 → 不会长期占用连接 | 但另发现：**Hikari 池未配置 = Spring Boot 默认 10**，与 `max_connections=50` 的组合仍缺压测标定 |

**同时确认了两项运维事实（此前证据包标注为"未显示"，现已实测）**：

- **监控链路未部署，且资产本身也不可用（比"未部署"更严重）**：
  - `prometheus` / `prometheus-node-exporter` / `grafana-server` / `alertmanager` **均未安装**，9090/3000/9093/9100 端口**均未监听**；`monitoring/` **不在部署上传范围**（仅定义在 `deploy/docker-compose.prod.yml` 的 `profiles: [monitoring]`，而 Docker 路线当前未使用）。
  - **即使现在把监控栈起起来，它依然不会工作** —— 两处资产缺陷已定位到行：
    - `monitoring/prometheus/prometheus.yml:20` → `targets: [api:8080]`，**抓取目标写死容器名**，而当前是直连部署（应用在 `127.0.0.1:8080`）→ **抓不到任何指标**；
    - `monitoring/alertmanager/entrypoint.sh:17` → 默认 `ALERTMANAGER_WEBHOOK_URL=http://127.0.0.1:9/...`，**`:9` 是丢弃端口** → 未显式配置接收人时**告警有去无回**。
  - → 结论：**"有埋点、有规则，没有告警"**，且 11 条规则当前不可能产生任何通知。
- **备份为零**：`/opt/intelligent-resume/backups/` 为空目录，全环境**无 mysqldump 脚本**、无备份 crontab（仅有云厂商 agent）。
  → 一旦数据损坏，**只能靠"空库重建"**（该环境本就是空库起步、无数据迁移）。

**另行确认的两处「制品与文档/实现不一致」（均属可复现的具体缺陷）**：

| # | 缺陷 | 证据 | 影响 |
| --- | --- | --- | --- |
| 1 | **systemd 两个单元都没有内存/CPU 上限** | `grep -cE "MemoryMax\|MemoryLimit\|CPUQuota" deploy/systemd/*.service` → 两文件命中均为 **0** | Puppeteer 拉起的 Chromium **无内存上限**；在与另一项目共用的 3.6 GiB 主机上，一次并发导出就可能触发宿主 OOM，而 **OOM-killer 可能先杀 MySQL 或对方容器** —— 表现为"智历起来了、别人挂了"，且脚本不会报错 |
| 2 | **手册 §9 的「API 回滚」实际不可执行** | `deploy-direct.remote.sh` 第 91 行直接 `cp` 覆盖 `app/api/*.jar`，**只有 `web.bak` / `pdf-service.bak`，没有 api 备份**；且构建用 `mvn clean package` 会清空 `src/server/target` | 一旦新版 API 异常，手册指引的"用上一版 jar 覆盖"**无 jar 可用**，实际回滚只能回退 git 提交重新构建（约 1 分 25 秒 + 占用共用主机内存）。**回滚手段与文档承诺不符，是上线前的实质风险** |
