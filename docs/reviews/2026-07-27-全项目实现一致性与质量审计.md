# 全项目实现一致性与质量审计

> 审计日期：2026-07-27
> 审计基线：`codex/complete-resume-workflows`，提交 `4b87dfc887f6402ef4b40bad47408a9e848e1375`
> 审计范围：从简历编辑器出发，覆盖 Web、Spring Boot API、AI 任务、PDF 服务、测试、部署与项目文档。

## 1. 结论摘要

项目不是“只有页面的原型”。账号、个人档案、职业资料、JD、两阶段 AI 选材与生成、人工确认、简历版本、评分、PDF 异步任务、租约恢复和生产配置校验等核心能力已有较完整实现，现有自动化检查也全部通过。

但项目当前还不能被准确描述为“完整求职闭环已经交付”。审计确认了两类关键问题：

1. 简历编辑、预览、模板和 PDF 导出之间没有共享且受约束的数据契约，用户保存的部分内容会在设计预览或 PDF 中消失，模板选择也不会被导出链路完整兑现。
2. ATS、投递、沟通、导入和面试等外围模块的前端已按完整产品建模，后端仍是固定响应或空列表，且多处请求/响应结构直接不兼容。Mock 浏览器测试掩盖了这些真实集成故障。

建议当前对外口径为：**核心简历生成与版本链路已实现，求职管理外围模块仍处于 UI/API 脚手架阶段；在修复 P1 契约问题和补齐真实联调测试前，不应宣称完整业务闭环可用。**

## 4. P1：发布前必须处理

### P1-1 同一路由切换简历 ID 时，编辑器不会重新加载

`ResumeEditorView` 只在 `onMounted` 中调用 `loadEditor()`，没有监听 `props.id`（[ResumeEditorView.vue:540](../web/src/views/ResumeEditorView.vue#L540)、[ResumeEditorView.vue:566](../web/src/views/ResumeEditorView.vue#L566)）。Vue Router 在 `/resumes/1/edit` 切换到 `/resumes/2/edit` 时可能复用组件实例。

影响：页面仍显示简历 A 的内容和版本状态，但保存请求会使用当前的简历 B ID，存在把 A 内容保存成 B 新版本的风险。

建议：监听 `props.id`，在切换时取消或废弃旧异步结果，重置草稿、版本、AI 助手和脏状态，再重新加载。增加同组件路由参数切换测试。

### P1-2 编辑器、设计预览与 PDF 的内容集合不一致

编辑器支持 14 类内容，并保存 `layout.sectionOrder`（[ResumeEditorView.vue:47](../web/src/views/ResumeEditorView.vue#L47)、[ResumeEditorView.vue:191](../web/src/views/ResumeEditorView.vue#L191)）。设计预览只渲染概要、工作、技能、项目、教育、证书、奖项和语言（[ResumeEditorView.vue:689](../web/src/views/ResumeEditorView.vue#L689)），遗漏求职目标、链接、志愿经历、课程、出版物和自定义章节，也未按 `sectionOrder` 渲染。

PDF renderer 更少，只读取工作、技能、项目、教育、证书和语言（[classic.js:81](../pdf-service/src/templates/classic.js#L81)），固定顺序输出这些章节（[classic.js:114](../pdf-service/src/templates/classic.js#L114)）。奖项、自定义章节等已保存信息会从导出文件中消失。

影响：用户在编辑器看到、保存并确认的数据，可能不出现在设计预览或最终 PDF；这是数据呈现完整性问题。

建议：建立唯一的 `ResumeDocument` schema 和统一章节注册表，让表单、全屏预览、设计预览和 PDF 共用章节可见性、排序和格式化规则。至少为每一种章节做保存到 PDF 的契约测试。

### P1-3 模板选择跨三层不兼容

编辑器提供 7 种模板：`classic`、`modern`、`minimal`、`ats`、`executive`、`compact`、`academic`（[ResumeEditorView.vue:145](../web/src/views/ResumeEditorView.vue#L145)）。PDF 服务接受 3 种（[classic.js:3](../pdf-service/src/templates/classic.js#L3)），API 导出 DTO 和服务只接受 `classic`（[CreateExportRequest.java:11](../server/src/main/java/com/intelligentresume/export/dto/CreateExportRequest.java#L11)、[ExportService.java:59](../server/src/main/java/com/intelligentresume/export/service/ExportService.java#L59)）。简历详情又把任何版本的模板都固定解释为 `classic`（[ResumeDetailView.vue:29](../web/src/views/ResumeDetailView.vue#L29)）。

影响：用户选择的模板虽然写进简历 JSON，但详情页显示和实际导出都不会兑现；前端类型还暗示 `modern/minimal` 可导出，与 API 实际限制冲突。

建议：先决定真实支持范围。若近期只支持 classic，编辑器必须只暴露 classic；若支持多模板，则由版本响应返回模板代码，并让 API、PDF 服务使用同一枚举和契约测试。

### P1-4 ATS 真实响应会破坏页面

前端要求 `totalScore`、`checks`、`passedChecks`、`risks`、`priorities`、`disclaimer`（[ats.ts:3](../web/src/api/ats.ts#L3)），页面直接访问 `result.checks.structure`（[AtsCheckView.vue:48](../web/src/views/AtsCheckView.vue#L48)）。后端返回的是 `checkId`、`score`、`structure`、`keywords`、`suggestions`（[AtsController.java:17](../server/src/main/java/com/intelligentresume/ats/controller/AtsController.java#L17)）。

影响：真实调用成功后，页面仍会因 `checks` 不存在而报错或渲染失败。

建议：在后端定义正式 DTO 与实现语义，前端从生成的 OpenAPI 类型或共享契约消费；在 CI 中执行一次不经过 Mock 的 ATS 调用。

### P1-5 投递管理前后端语义不成立

前端按完整 `ApplicationRecord` 处理列表和创建结果（[application.ts:4](../web/src/api/application.ts#L4)）。后端列表恒为空，创建恒返回 `{id: 1}`，更新仅返回传入 ID，删除不操作任何存储（[ApplicationController.java:16](../server/src/main/java/com/intelligentresume/application/controller/ApplicationController.java#L16)）。控制器还没有使用当前用户或请求体完成业务校验。

影响：新建后前端立即把只有 ID 的对象加入记录列表，随后读取状态、JD/简历版本、时间等字段；刷新后记录消失，完整工作流不可用。

建议：在宣称该模块可用前补齐数据模型、Flyway、用户归属、乐观锁/版本、状态机和 CRUD 集成测试；否则将入口和文档明确标为实验性。

### P1-6 沟通文案响应契约不兼容

前端期待 `{type, draft, sentAutomatically, requiresManualConfirmation}`（[communication.ts:3](../web/src/api/communication.ts#L3)），后端固定返回 `{body, subject}`（[CommunicationController.java:16](../server/src/main/java/com/intelligentresume/communication/controller/CommunicationController.java#L16)）。

影响：真实环境无法取得 `draft`，也无法表达“系统绝不自动发送、必须人工确认”的产品约束。

建议：先固化 DTO 和人工确认语义，再实现生成与保存；保留 `sentAutomatically=false` 为服务端不可变事实，而不只是前端展示字段。

### P1-7 简历导入的 Content-Type 与响应契约均不兼容

前端上传 `FormData` 文件并期待文件信息、抽取文本、`normalizedResumeInput` 和存储标记（[resumeImport.ts:2](../web/src/api/resumeImport.ts#L2)）。后端使用 `@RequestBody Map<String,Object>` 接收 JSON，并只返回空 `extractedText`、`normalizedPreview` 和建议（[ResumeImportController.java:15](../server/src/main/java/com/intelligentresume/imports/controller/ResumeImportController.java#L15)）。

影响：真实 multipart 请求无法按控制器签名绑定，即使返回成功，字段也不匹配。

建议：明确上传大小、MIME、病毒/压缩炸弹防护和原文件保留策略，使用 `MultipartFile` 与正式响应 DTO，并做真实 PDF/DOCX 样本集成测试。

## 5. P2：应在下一迭代修复

### P2-1 插入职业资料存在竞态、重复提交与未处理失败

`insertMaterial()` 只快照资料 ID；请求返回后依据实时的 `activeSection` 决定写入位置，且没有 loading、`catch` 或重复点击保护（[ResumeEditorView.vue:278](../web/src/views/ResumeEditorView.vue#L278)）。

影响：请求期间切换章节会把资料插入另一个章节；重复点击可重复插入；失败产生未处理 Promise，用户没有反馈。

建议：同时快照资料 ID、目标章节和当前简历 ID；请求期间禁用按钮；捕获错误；响应落地前核对编辑上下文仍有效。

### P2-2 自定义章节允许选资料，但插入后静默无效

资料映射为 `customSections` 配置了 `LEADERSHIP_EXPERIENCE` 和 `ACHIEVEMENT`（[ResumeEditorView.vue:260](../web/src/views/ResumeEditorView.vue#L260)），但插入分支只处理工作、项目、技能、教育、志愿、课程、证书、出版物和奖项，之后仍清空选择（[ResumeEditorView.vue:285](../web/src/views/ResumeEditorView.vue#L285)）。

建议：实现明确的自定义章节映射，或在支持前移除该候选类型；不要在未写入时清空选择。

### P2-3 加载示例后被错误标记为“已同步”

`loadSample()` 设置新内容后立即把 `initialContent` 设为相同值（[ResumeEditorView.vue:135](../web/src/views/ResumeEditorView.vue#L135)），而 `dirty` 以两者差异判断（[ResumeEditorView.vue:208](../web/src/views/ResumeEditorView.vue#L208)），保存按钮在非 dirty 时禁用。

影响：用户加载示例后无法直接保存，必须再做一次无关编辑。

建议：加载示例应产生未保存变更，或提供单独的“以示例创建版本”命令。

### P2-4 AI 手动重试计数两次，并绕过创建配额

创建任务时检查授权与配额（[AiTaskService.java:55](../server/src/main/java/com/intelligentresume/ai/task/service/AiTaskService.java#L55)、[AiTaskService.java:85](../server/src/main/java/com/intelligentresume/ai/task/service/AiTaskService.java#L85)）。手动 retry 直接把失败任务改回 `PENDING` 并增加 `retryCount`（[AiTaskService.java:166](../server/src/main/java/com/intelligentresume/ai/task/service/AiTaskService.java#L166)）；worker 领取时又增加一次（[TaskLeaseService.java:49](../server/src/main/java/com/intelligentresume/ai/worker/TaskLeaseService.java#L49)）。手动 retry 没有最大次数或配额检查。

影响：一次手动重试记为两次，自动重试上限提前触发；用户可反复让失败任务重新进入队列，调用量不计入创建配额。worker 执行前仍会复查授权，因此当前证据不支持将其定性为授权绕过。

建议：把 attempt 和 retry 分成清晰字段；只在实际执行开始时增加 attempt；手动重试执行授权、配额和最大次数检查。

### P2-5 大型页面与弱类型 schema 已造成实际漂移

三个核心页面分别约 921、859、696 行；编辑器大量使用 `Record<string, any>` 和 `any[]`（[ResumeEditorView.vue:155](../web/src/views/ResumeEditorView.vue#L155)）。后端主要约束顶层 JSON，PDF 又独立解析字段。

这不是单纯的代码风格问题：章节遗漏、模板漂移和预览差异正是缺少共享领域 schema 和渲染边界的结果。

建议按领域拆分 composable 与组件，但优先抽取稳定的 `ResumeDocument`、章节 registry、模板能力表和序列化校验；不要只按文件行数机械拆组件。

### P2-6 国际化规则没有被持续执行

`PROJECT_CONTEXT.md` 明确要求页面不得新增硬编码用户文案（[PROJECT_CONTEXT.md:80](../PROJECT_CONTEXT.md#L80)），但至少 9 个 Vue/组件文件仍包含硬编码中文，编辑器中的项目、教育、证书、语言等标签可见于 [ResumeEditorView.vue:768](../web/src/views/ResumeEditorView.vue#L768)。`ApplicationsView` 还有硬编码英文错误。

建议：迁移到 `web/src/i18n/`，并增加 lint/AST 检查阻止新的模板文本和用户可见字符串绕过 i18n。

### P2-7 当前交付文档高估了外围业务完成度

`DEPLOYMENT_READINESS` 将 PDF、投递和面试资产列为已完成业务闭环（[DEPLOYMENT_READINESS.md:9](./DEPLOYMENT_READINESS.md#L9)）；README 声称保留投递、沟通和面试答案业务记录（[README.md:14](../README.md#L14)）；`PROJECT_CONTEXT` 也把这些模块描述为业务记录模块（[PROJECT_CONTEXT.md:98](../PROJECT_CONTEXT.md#L98)）。这与固定响应控制器不一致。

建议：文档增加“已实现 / 脚手架 / 规划中”标记，并把生产就绪范围限定到有持久化、归属校验和真实集成测试的模块。

### P2-8 PDF 服务 README 与健康状态也已漂移

`pdf-service/README.md` 仍写“当前只提供健康检查”（[pdf-service/README.md:3](../pdf-service/README.md#L3)），但 `/render` 与 Puppeteer 已实现。反过来，PDF 健康响应和 API 健康响应仍报告 `stage: SCAFFOLD`（[server.js:30](../pdf-service/src/server.js#L30)）。

建议：用可发布版本、构建提交或明确的 capability 字段替代模糊 stage；同步更新 README。

## 6. P3：维护性与清理项

- `AuthService.refresh()` 中存在创建后未使用的 `AuthSession next`，建议清理死代码并确认刷新会话轮换意图。
- `ResumeEditorView` 的多个内联一行处理器降低可读性和可测试性；在 schema 稳定后再拆分。
- 多个占位控制器使用 `Map<String,Object>`，编译期无法暴露契约漂移；即便暂时不实现业务，也应使用明确 DTO 并返回 `501 Not Implemented` 或功能开关，而不是伪造成功。

## 7. 测试盲区

### 7.1 当前缺失

- Web 没有组件/单元测试框架和对应脚本，主要依赖两组 Playwright 流程。
- API 未发现 application、ATS、communication、resume import、interview、interview asset 的针对性测试。
- Mock E2E 使用前端自行定义的响应形状，无法发现本报告中的 ATS、沟通和投递契约错位。
- 常规 Playwright 运行跳过了 5 个 `@local-services` 用例。

### 7.2 最小新增测试集

1. 编辑器在同组件内从简历 A 切换到 B，断言内容、草稿、版本和保存目标全部刷新。
2. 插入资料期间切换章节、双击按钮和请求失败，断言不会错插、重复或静默失败。
3. 自定义章节插入资料，以及加载示例后的 dirty/save 状态。
4. 用包含全部 14 类章节和自定义顺序的固定 fixture，验证编辑器、两种预览和 PDF 的章节集合及顺序一致。
5. 对每个暴露模板执行 Web -> API -> PDF 的契约测试。
6. 使用真实 Spring Boot 服务运行 ATS、投递、沟通、导入与面试流程，不允许路由 Mock。
7. 从 OpenAPI 或共享 schema 生成/校验前端类型，并在 CI 做 breaking-change 检查。

## 8. 安全、归属和运维复核

本轮没有发现可证实的跨用户数据读取漏洞。核心资料、JD、简历、AI 任务、确认、评分和导出路径普遍使用 `findByIdAndUserId` 或等价的关联归属校验。例如简历版本保存先校验简历归属（[ResumeVersionService.java:47](../server/src/main/java/com/intelligentresume/resume/service/ResumeVersionService.java#L47)），AI 状态查询按用户读取（[AiTaskService.java:101](../server/src/main/java/com/intelligentresume/ai/task/service/AiTaskService.java#L101)），导出任务也按用户查询。

AI 授权在任务创建和 worker 执行前均检查，撤回后待执行任务会失败而不会继续发送数据。生产配置通过环境变量提供数据库密码、CORS 和 JWT secret，并有默认密钥拒绝逻辑。AI/PDF 队列租约、Prometheus 指标和告警规则也确实存在。

仍需注意：这些结论只覆盖已实现的核心模块。占位控制器没有真实数据，因此“当前看不到越权”不代表它们未来实现时自动安全；新增持久化时必须把用户归属测试列为准入条件。备份恢复、告警通知接收和真实生产容量也属于环境验证，不能仅凭仓库静态配置判定已完成。

## 9. 建议整改顺序

### 阶段一：停止错误承诺并守住数据完整性

1. 修复简历 ID 切换、资料插入竞态和示例 dirty 状态。
2. 将可用模板暂时收敛到端到端真正支持的集合。
3. 确保所有可编辑章节都进入最终 PDF，并统一章节顺序。
4. 把 ATS、投递、沟通、导入和面试标为脚手架或暂时隐藏入口；同步修正文档。

### 阶段二：建立契约边界

1. 定义版本化 `ResumeDocument` schema 和章节 registry。
2. 为所有 HTTP 接口使用明确 DTO/OpenAPI，消除业务边界上的裸 `Map`。
3. 增加 Web/API/PDF 跨服务契约测试，CI 至少运行一组真实服务 smoke test。
4. 修复 AI 重试 attempt、上限和配额语义。

### 阶段三：逐个完成外围模块

按“数据模型与归属 -> API -> 前端 -> 真实集成测试 -> 文档”的顺序逐个交付，建议先完成投递管理，再完成沟通资产、面试资产、ATS 和导入。不要同时铺开所有占位模块，否则契约漂移会继续扩大。

### 阶段四：维护性治理

在共享 schema 和接口稳定后拆分大型 Vue 页面，补组件测试和 i18n 静态门禁，清理死代码与健康状态命名。

## 10. 验收门槛

下列条件全部满足后，才适合把项目描述为“完整求职闭环可用”：

- 编辑器保存的全部章节、顺序和模板能在详情与 PDF 中一致复现。
- ATS、投递、沟通、导入和面试不再返回固定成功数据，并具备用户归属和持久化测试。
- 前端不依赖与后端不同的手写响应结构。
- CI 运行真实 Web/API/PDF 集成 smoke test，关键流程不只依赖 Mock。
- 当前交付文档与实际能力矩阵一致。
- 生产环境完成备份恢复演练、告警通知和容量验证。

---

总体判断：项目核心技术底座和主简历链路已经具备继续迭代的价值，主要风险不是“全部未实现”，而是**不同模块成熟度被同一种完成口径覆盖，以及简历 schema/渲染/API 契约缺少统一所有者**。先收敛承诺和契约，再扩展外围业务，成本和返工风险最低。
