### 2.1 两处修正的意义

**DEF-4 的修正很重要**：若按报告字面去"修 ATS 卡死"，会去找一个不存在的死锁，
而真正要修的是**文案**与**ATS 未关闭推理导致的耗时**。这正是"先复现再动手"的价值。

**DEF-6 的修正同样重要**：若按字面去"修面试按钮不发请求"，会去改一个正常工作的
`start()` 函数。真实待修项是**静默无反馈**（UX），以及**补测**（测试方法）。

### 3.1 新增静态门禁 `check:draft-fields`（替代慢速 e2e）

**为什么不用 e2e**：这是**映射完整性问题**，与渲染无关。实测走浏览器验证该场景，
单个用例需约 2 分钟（且在全量套件中把总时长从约 1 分钟推到 20 分钟以上未收敛），
既慢又脆。改为 `node --test` 静态检查（与既有 `check:i18n` 同范式）：
**毫秒级、进 `npm run build` 门禁、覆盖同样完整。**

检查项：
1. 草稿 schema 的全部字段都有标签映射（漏配即失败 —— 正是当初的缺陷）；
2. 所有引用的 i18n 键在中英两种语言下都存在且非空；
3. 中文表里的值确实含中文（防止"加了映射但中文没翻译"）；
4. 枚举值字典同样满足 2、3（保证 `EXPERT` 不再裸上屏）。

自测用变异测试覆盖：删掉 `category` 映射、删掉英文键、把中文值改成英文、
把枚举中文改成英文 —— 四种"漏配"都必须被拦住，共 5 条用例。

> **门禁上线即立功**：它当场抓出了**我方修复自身的漏配** —— 补了 8 个字段却漏了
> `label`（basics 的职位头衔，真实报告里也出现过该字段）。即 DEF-1 的实际范围
> 比外部报告的观察更宽，靠肉眼不可靠，靠静态门禁才拦得住。

**未做（需决策）**：是否对 `ATS_ANALYSIS` 也关闭模型推理。ATS 单次实测 212–405s，
关闭推理预计降到十几秒，但**判断类任务的质量影响尚未测量**，需先做质量对比实验（见 §5）。

## 6. 测试计划本身的缺陷（我方疏漏，已修补）

1. **未要求处理原生弹窗** → 浏览器自动化默认"取消"原生 `confirm`，
   导致**整条面试路径未被测到**。已在计划 §0.4 补充要求（含 `page.on('dialog', d => d.accept())`）
   与"点击无请求时先排查弹窗"的排查顺序。
2. **C-04 未写明触发条件** → 报告把"未见软状态"记为缺陷，实为条件未达到。
   已在 C-04 明确"需超过 600 秒"并允许标 BLOCKED。
