# 面向 AI 代理的开发流程与交付规范

## 1. 目标

本规范用于让能力较弱的代码代理也能在本项目中稳定完成小范围开发。核心原则是：代理不负责产品决策，只负责在已确认的任务边界内实现、测试和报告。

适用对象：代码生成模型、自动化编码代理、协作开发中的初级工程代理。

## 2. 文档权威顺序

代理开始任务前，按以下顺序读取与任务相关的文档：

1. `01-项目开发总计划.md`：确认当前阶段和 MVP 边界。
2. `02-需求规格说明书.md`：确认用户行为、规则和非功能要求。
3. `03-系统架构设计说明书.md`：确认模块边界和调用方向。
4. `04-数据库设计说明书.md`：确认表、字段、快照和删除规则。
5. `05-接口设计说明书.md`：确认路径、请求、响应、状态和错误码。
6. `06-开发任务拆解与里程碑.md`：确认任务优先级和依赖。
7. `07-测试计划与验收说明书.md`：确认验收场景。
8. `08` 至 `10`：确认运维、安全、质量和协作约束。
9. `11-新增智能能力需求与设计补充.md`：仅在任务明确涉及增量能力时阅读；若与前述文档冲突，停止并报告。

若文档冲突，代理不得选择“看起来更合理”的版本。必须报告冲突，并等待负责人确定后再继续。

## 3. 不可违反的规则

- 不新增未在任务卡中出现的接口、表、字段、枚举、页面或依赖。
- 不修改不在任务卡“允许改动文件”中的文件。
- 不把 AI 生成内容直接当作用户事实；未经用户确认的内容只能保存为草稿或待确认数据。
- 不绕过资源归属、AI 同意、配额、限流、私有文件下载或软删规则。
- 不打印密码、Token、完整简历、JD、面试回答、文案或 AI 原始请求体。
- 不使用 `git reset --hard`、强制覆盖他人改动或批量格式化无关文件。
- 不在测试失败、需求不清、接口不全、数据库设计缺失或权限语义未知时猜测实现。

## 4. 任务卡格式

每次只给代理一张任务卡。一个任务卡最多改动 5 个业务文件和对应测试；超过该范围必须拆分。

```text
任务名称：
目标：
当前阶段与优先级：
来源文档：
允许改动文件：
禁止改动文件：
输入契约：
输出契约：
数据读写：
权限与安全：
失败行为：
验收场景：
验证命令：
完成定义：
```

任务卡示例：

```text
任务名称：查询职业资料列表
目标：登录用户可按资料类型查看自己的职业资料。
当前阶段与优先级：第二阶段 / Priority-P0
来源文档：02 §5.5，04 §3.2，05 §3.2，07 §5.4
允许改动文件：由负责人列出 controller、service、repository、DTO、对应测试。
禁止改动文件：认证流程、简历版本模块、其他接口。
输入契约：GET /api/career-materials?materialType=...，materialType 可选。
输出契约：只返回当前用户未删除的资料，响应遵循统一响应结构。
数据读写：只读 career_material。
权限与安全：从当前认证上下文取得 userId；不得接受请求中的 userId。
失败行为：非法类型返回参数错误；未登录返回未认证错误。
验收场景：正常列表、按类型过滤、无数据、未登录、跨用户数据不可见。
验证命令：先读取项目实际测试命令，再执行受影响模块的测试。
完成定义：测试通过，接口文档无变化，任务报告完整。
```

## 5. 代理执行循环

代理必须按顺序执行，不能跳步。

### 5.1 阅读

1. 读取任务卡和来源文档的指定章节。
2. 搜索现有相似实现、DTO、实体、测试和错误码。
3. 列出将改动的文件、复用的模式和验证命令。
4. 发现缺少契约时输出 `BLOCKED`，不编辑代码。

### 5.2 计划

输出不超过 8 条的执行清单，每条必须是可验证动作：

```text
1. 阅读现有职业资料查询实现和测试。
2. 写出或更新失败测试，证明仅返回当前用户数据。
3. 实现查询服务和接口适配。
4. 运行目标测试。
5. 检查未授权、空列表和参数错误场景。
```

计划得到任务卡允许后再编辑。代理不得将“顺便重构”“优化架构”加入计划。

### 5.3 测试优先

对行为变更，先选择一种证据方式：

- 已有测试覆盖错误行为：先运行并记录失败。
- 已有测试断言旧契约：先更新测试并确认其失败。
- 没有测试：新增最小失败测试。
- 纯文档、纯配置或无法自动化的页面调整：写明不使用测试的原因，并指定替代验证。

每项功能至少覆盖：正常路径、一个边界或空值路径、一个权限或失败路径。跨模块行为至少有一个集成测试。

### 5.4 实现

1. 只编辑任务卡允许的文件。
2. 复用现有命名、统一响应和异常处理模式。
3. 每次写入前校验资源所属用户，而不是相信客户端传入的用户 ID。
4. AI 任务只创建异步任务，结果从任务查询读取；生成事实必须带来源映射或待确认状态。
5. 保存涉及多个实体时，使用一个业务事务，避免只创建版本而未保存来源引用等半成品状态。

### 5.5 验证

按顺序执行：

1. 目标单元测试。
2. 相关模块的集成测试。
3. 项目已有的格式、静态检查或类型检查命令。
4. 手工或浏览器验证（仅对有界面任务）。
5. 查看差异，确认没有超出允许文件范围。

若任一验证失败，先修复；无法修复时输出 `BLOCKED` 并附上命令、错误和已尝试操作。

## 6. 特殊任务规则

### 6.1 数据库任务

- 先更新 `04-数据库设计说明书.md`，再创建迁移。
- 新表必须有用户归属、索引、删除策略和审计/快照说明。
- 变更已有表必须说明兼容、回滚和历史数据处理。
- 不能物理删除被简历版本、评分、投递、AI 任务或面试记录引用的数据。

### 6.2 接口任务

- 先更新 `05-接口设计说明书.md`，再写 Controller。
- 每个写接口必须定义参数校验、认证、资源归属、成功响应和失败错误码。
- AI 创建接口必须定义同意、限流、配额、幂等键和异步状态。
- 文件下载必须走受控授权，不能返回永久公开存储地址。

### 6.3 AI 任务

- 只发送任务所需的最小字段，并检查用户 AI 数据同意。
- 记录提供商、模型、提示词版本、脱敏输入摘要、任务状态和用户确认状态。
- 不可映射到职业资料的事实必须标为待确认；资料不足时返回缺失项，不得编造。
- 不在日志、异常或任务消息中写入完整敏感文本。

### 6.4 前端任务

- 先明确页面入口、加载、空数据、错误、成功和无权限状态。
- 只有在接口契约已确定时才调用接口。
- 提交 AI 任务后展示可理解的进行中、成功、失败和重试状态；不得假设同步返回最终结果。
- 对用户确认、删除、导出和状态迁移等不可逆操作提供明确确认和结果反馈。

## 7. 停止条件

出现以下任一情况，代理必须停止编辑并报告：

- 来源文档相互矛盾。
- 任务需要新增未设计的数据字段或接口。
- 无法确定当前用户的资源归属规则。
- 测试失败且错误影响任务以外模块。
- 需要新依赖、外部账号、密钥、网络权限或数据库迁移策略。
- 任务范围超过任务卡定义的文件或模块。

标准报告格式：

```text
BLOCKED
原因：
冲突或缺失位置：
需要负责人决定的问题：
已完成的只读检查：
未执行的写操作：
```

## 8. 完成报告格式

每个任务结束时输出以下内容，不写泛泛总结：

```text
任务：
状态：DONE / BLOCKED
改动文件：
行为变化：
契约依据：
测试或替代验证：
结果：
未覆盖的风险：
是否需要更新文档：是 / 否，原因：
```

`DONE` 的前提是：任务卡验收场景全部通过，未超出允许改动范围，且没有未解释的测试失败。

## 9. 负责人拆任务准则

负责人给低能力代理分配任务时：

- 一次只分配一个模块的一个行为切片。
- 明确说出“不做什么”，不要只描述目标。
- 提供具体文档章节、文件路径和测试命令，不要求代理自行选择技术方案。
- 数据库、接口、权限和 AI 行为变更必须先由负责人或更高能力代理确定契约。
- 合并前由负责人检查任务报告、差异、测试结果和文档同步情况。

## 10. 最小开发顺序

低能力代理只能按以下顺序领取任务：

1. 工程骨架、统一响应、异常和认证基础。
2. 职业资料库、简历和版本管理。
3. JD 管理与规则评分。
4. 岗位定制生成的异步任务、来源映射和用户确认。
5. 私有 PDF 导出和 MVP 端到端测试。
6. 经负责人确认后，再领取 ATS、投递、AI 面试等后续任务。
