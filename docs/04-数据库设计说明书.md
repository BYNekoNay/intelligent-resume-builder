# 数据库设计说明书

## 1. 设计原则

- 面向业务主流程建模
- 优先支持结构化简历和版本管理
- 保证 AI 任务、评分结果、导出结果可追踪
- 字段设计兼顾当前 MVP 和后续扩展

数据库建议：MySQL 8.x  
字符集建议：`utf8mb4`

### 3.1.1 auth_session

用途：支持刷新令牌轮换、撤销、重放检测和按设备退出。数据库只保存刷新令牌哈希，不保存明文令牌。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | bigint PK | 会话 ID |
| user_id | bigint | 所属用户 |
| token_family_id | varchar(64) | 同一轮换链标识 |
| refresh_token_hash | varchar(255) | 当前刷新令牌哈希 |
| expires_at | datetime | 过期时间 |
| revoked_at | datetime | 撤销时间，可为空 |
| replaced_by_session_id | bigint | 轮换后的会话 ID，可为空 |
| last_used_at | datetime | 最近使用时间 |
| device_label | varchar(128) | 用户可识别的设备说明，可为空 |
| created_at | datetime | 创建时间 |

约束：`refresh_token_hash` 唯一；检测到旧令牌复用时，撤销整个 `token_family_id`。浏览器端使用 `Secure`、`HttpOnly`、`SameSite=Lax` Cookie 传输刷新令牌，不向 JavaScript 暴露。

### 3.1.2 ai_consent

用途：保存 AI 数据处理同意和撤回事件，作为能否创建新 AI 任务的唯一依据。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | bigint PK | 主键 |
| user_id | bigint | 所属用户 |
| policy_version | varchar(64) | 同意文本版本 |
| provider_code | varchar(64) | 适用提供商 |
| task_scopes_json | json | 允许的任务类型 |
| data_categories_json | json | 允许发送的数据类别 |
| notice_hash | varchar(128) | 用户看到的告知文本摘要 |
| status | varchar(16) | GRANTED / WITHDRAWN |
| occurred_at | datetime | 授权或撤回时间 |

撤回只阻止新任务，不删除历史审计；历史任务继续引用当时的同意记录。

### 3.8 ai_task

用途：保存 AI 调用任务

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | bigint PK | 主键 |
| task_type | varchar(32) | 任务类型 |
| user_id | bigint | 用户 ID |
| resume_version_id | bigint | 简历版本 ID |
| job_description_id | bigint | JD ID |
| status | varchar(32) | 状态 |
| prompt_version | varchar(64) | Prompt 版本 |
| result_json | json | AI 返回结果 |
| input_snapshot_json | json | 发起任务时的最小化输入快照 |
| provider_code | varchar(64) | 实际调用的提供商 |
| model_code | varchar(128) | 实际调用的模型 |
| consent_version | varchar(64) | 用户同意版本 |
| consent_id | bigint | 发起任务时使用的同意事件 ID |
| idempotency_key | varchar(128) | 客户端幂等键 |
| request_fingerprint | varchar(128) | 规范化请求摘要 |
| attempt_count | int | 已执行次数 |
| max_attempts | int | 最大执行次数 |
| lease_owner | varchar(128) | 当前工作器标识，可为空 |
| lease_expires_at | datetime | 任务租约到期时间，可为空 |
| next_attempt_at | datetime | 下次可重试时间 |
| provider_request_id | varchar(128) | 提供商请求标识，可为空 |
| confirmation_status | varchar(32) | NOT_REQUIRED / PENDING / CONFIRMED / REJECTED |
| confirmed_at | datetime | 用户确认时间，可为空 |
| result_resume_version_id | bigint | 确认后创建的唯一版本 ID，可为空 |
| error_message | varchar(1000) | 错误信息 |
| created_at | datetime | 创建时间 |
| updated_at | datetime | 更新时间 |

`status` 建议枚举：

- PENDING
- RUNNING
- SUCCESS
- FAILED
- CANCELLED

`task_type` 至少覆盖 `JOB_GENERATION`、`RESUME_OPTIMIZE`、`INLINE_OPTIMIZE`、`MATERIAL_IMPORT`、`ACHIEVEMENT_GUIDANCE` 和 `COMMUNICATION_GENERATE`。

约束与执行规则：

- 唯一约束：`user_id + task_type + idempotency_key`。
- 相同幂等键且请求摘要相同，返回原任务；摘要不同返回 `40901`。
- 工作器通过数据库原子抢占 PENDING 或租约过期任务；RUNNING 任务必须持有未过期租约。
- 失败按可重试/不可重试分类；达到 `max_attempts` 后进入 FAILED。
- `result_resume_version_id` 唯一，保证同一任务只能确认出一个版本。

## 4. 实体关系说明

关系如下：

- 一个用户可拥有多份简历和多条职业资料
- 一份简历可拥有多个版本
- 一个简历版本可引用多条职业资料，一条职业资料可被多个简历版本复用
- 一个用户可保存多个 JD
- 一个简历版本可对应多个评分结果
- 一个简历版本可对应多个导出任务和多个 ATS 体检结果
- 一个用户可拥有多条投递记录，每条记录关联一个岗位和一个历史简历版本
- 一条投递记录可关联多个 AI 面试会话；独立训练会话可不关联投递
- 一个面试会话可拥有多个面试轮次，答案资产可追溯到一条轮次记录
- 一个用户可将多个面试回答沉淀为可复习的答案资产

## 7. 数据安全要求

- 密码字段只保存哈希值
- 导出文件只保存私有存储标识，下载时必须校验当前用户归属
- AI 任务输入快照遵循最小化字段原则，结果中避免持久化不必要敏感中间信息
- 日志中禁止打印完整密码、Token、简历原文
- 账号和资源删除采用软删与异步清理；被历史记录引用的内容保留不可编辑快照，按保留期清理

### 7.1 生命周期基线

| 资源 | 软删恢复期 | 硬删/匿名化期限 | 例外 |
| --- | --- | --- | --- |
| 职业资料（`career_material`） | 30 天 | 恢复期结束后 7 天内：**已实施**（决策 D2 阶段 1 + 阶段 2）—— 无引用者**物理删除**；被引用者转**最小快照**（`content_json` → `{"__purged":true}`、`source_text` 一并清空），保留 `title` 等元数据 | 被历史记录引用的部分只保留最小不可编辑快照 |
| 简历版本（`resume_version`） | 30 天 | 同「职业资料」：**已实施**（阶段 1 + 阶段 2）—— 无引用者物理删除；被引用者 `resume_json` → `{"__purged":true}`、`generation_context` 与 `optimization_summary` 清空，保留 `id`/`resume_id`/`version_no`/`source_type`/`deleted_at` | 被历史记录引用的版本保留最小不可编辑快照 |
| JD、简历主记录 | 30 天 | 恢复期结束后 7 天内（**计划中，尚未实现**：阶段 2b —— 需先处理「经 `resume_version` 的间接引用」与各自的快照列） | 被历史记录引用的部分只保留最小不可编辑快照 |
| AI 任务原始输入和结果 | 不提供恢复 | 任务完成 90 天后删除非必要内容（**已实现**：`app.ai.task.retention-days=90`，压缩为元数据、不删除行） | 保留任务 ID、状态、模型、同意、耗时和脱敏错误用于审计 |
| PDF 文件 | 不提供恢复 | 生成后 24 小时自动删除（**已实现**：`app.pdf.file-ttl-hours=24`） | 仅保留任务元数据和校验摘要 |
| 投递与面试数据 | 30 天 | 恢复期结束后 7 天内（**计划中，尚未实现**） | 用户主动保留的答案资产按独立资源处理 |
| 账户 | 无撤销窗口（**与实现一致**：`DELETE /api/auth/me` 立即停用，不提供恢复，见 `docs/05` §2.7） | 立即停用 + 撤销会话/取消任务/撤回同意；行数据的匿名化清理**计划中，尚未实现** | 法律或安全审计所需内容必须匿名化和最小化 |

> **分档口径**（决策 D2）：硬删承诺分两档落地 —— **A 档「无任何引用者」** 与
> **B 档「被引用者转最小快照」** 均已对 `career_material` 与 `resume_version` 实施
> （`RetentionPurgeService` 按 `app.retention.purge.*` 周期清扫，**默认 `enabled=false` 且
> `dry-run=true`**，两条护栏都落在「不写数据」一侧；单轮每档每资源最多 `batch-size` 行）。
> **账户侧**（阶段 3）与 **`resume`/`job_description` 两资源**（阶段 2b）仍属计划中，
> 设计见 `docs/plans/2026-10-01-001-data-retention-tiered-purge.md`。方案 §1 取证：
> `resume_version` 被 **11 处**外键引用（含自引用 `restored_from_version_id`），直接硬删必撞外键
> —— 这是「必须分档」的硬理由而非偏好。
>
> 第四十九批的原结论「全仓无任何硬删清扫作业」已被本批**取代**（A/B 两档对上述两个资源均已实现）；
> 其余资源与账户侧仍无实现，按现状标注。契约由 `RetentionPolicyContractTest` 守护
> （已实施档不得再被标为「计划中」，未覆盖资源必须保留「计划中」标注）。
>
> **实施期发现并修正的一处 PII 遗漏**：方案 §4 初版的 `career_material` 快照只清 `content_json`，
> 漏了 `source_text`（MEDIUMTEXT，导入时的**原文**）—— 它与 `content_json` 一样是 PII 载体，
> 现已一并清空（第六十八批）。

备份按最长 30 天滚动过期；账户删除完成状态必须可查询。外部 AI 提供商的删除和留存行为以供应商配置为准，不能满足本表要求的提供商不得用于生产。
