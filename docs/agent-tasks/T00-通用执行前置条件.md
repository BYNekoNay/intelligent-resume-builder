## 3. 禁止越界清单(违反任一条立即输出 BLOCKED)

来源:`12 §3`、`13 §3`、`10 §12`。

### 3.1 范围类

1. **不得新增未在 Tnn「配置项」节出现的依赖**(Maven / npm);不得新建 Maven/Gradle 模块
2. **不得修改未在 Tnn「目标文件清单」节出现的文件**(包括测试、配置、文档)
3. **不得修改 `pom.xml` 中已固定的 `spring-boot-starter-parent` 版本**(3.3.2)
4. **不得修改 `docs/01..13` 与 `docs/archive/` 下的任何文件**(上游契约层)
5. **不得新建路由、Controller、表、字段、枚举、页面或接口**,除非 Tnn 明确列出
6. **不得擅自启用 Redis、MQ、RAG、向量库、微服务、Kubernetes、多租户**(13 §2 禁止)
7. **不得引入 Element Plus / Naive UI 等重型 UI 组件库**(03 §6.1 已选定 `lucide-vue-next` + 项目 CSS)

### 3.2 数据安全类

8. **不得把 AI 输出直接当作用户事实保存**(未经用户确认只能保存为草稿或待确认数据)
9. **不得绕过资源归属校验**(所有查询与写入的 `userId` 只能从认证上下文取,不得接受请求体中的 `userId`)
10. **不得绕过 AI 同意、配额、限流、私有文件下载、软删规则**(13 §3)
11. **不得打印密码、Token、完整简历、JD、面试回答、文案、AI 原始请求体到日志**
12. **不得让 AI 任务访问工具、网页、文件、任意 URL**(MVP 03 §9.6 禁止)
13. **不得让 PDF 服务接收任意 HTML、外部 URL 或 `file:` 协议**(03 §9.7)
14. **不得在文件名/存储键中包含用户 ID、邮箱、用户名、简历标题**(03 §9.7 + 08 §8)

### 3.3 工程纪律类

15. **不得使用 `git reset --hard`、强制覆盖他人改动、批量格式化无关文件**
16. **不得把调试代码长期留在主干**(10 §5.3)
17. **不得在测试失败、需求不清、接口不全、数据库设计缺失或权限语义未知时猜测实现**
18. **不得让代码代理根据缺失细节自行扩展接口、表结构、权限或产品范围**(10 §12)

## 4. 通用执行循环(每张 Tnn 都按此执行)

来自 `12 §5` 的五步循环。每步不允许跳步。

### 4.1 阅读

1. 读任务卡(`13 §5` 本卡)+ Tnn 操作手册
2. 搜索现有相似实现、DTO、实体、测试、错误码
3. 列出将改动的文件、复用的模式、验证命令
4. 发现缺少契约时输出 `BLOCKED`,不编辑代码

### 4.2 计划

输出不超过 8 条的执行清单,每条必须是可验证动作:

```text
1. 阅读现有 XXX 实现和测试
2. 写出或更新失败测试,证明 YYY
3. 实现 ZZZ
4. 运行目标测试
5. 检查场景 A、B、C
```

计划得到 Tnn 允许后再编辑。**不得将"顺便重构""优化架构"加入计划**。

### 4.3 测试优先

对行为变更,先选择一种证据方式:

- 已有测试覆盖错误行为:先运行并记录失败
- 已有测试断言旧契约:先更新测试并确认其失败
- 没有测试:新增最小失败测试
- 纯文档/纯配置/无法自动化的页面调整:写明不使用测试的原因,并指定替代验证

每项功能至少覆盖:正常路径、一个边界或空值路径、一个权限或失败路径。跨模块行为至少有一个集成测试。

### 4.4 实现

1. 只编辑 Tnn「目标文件清单」节列出的文件
2. 复用既有命名、统一响应、异常处理模式(见 §2)
3. 每次写入前校验资源所属用户,不信任客户端传入的 `userId`
4. AI 任务只创建异步任务,结果从任务查询接口读取;生成事实必须带来源映射或待确认状态
5. 保存涉及多个实体时使用一个业务事务,避免半成品状态

### 4.5 验证

按顺序执行:

1. 目标单元测试
2. 相关模块的集成测试
3. 项目已有的格式、静态检查或类型检查命令
4. 手工或浏览器验证(仅对有界面任务)
5. 查看差异,确认没有超出允许文件范围

若任一验证失败,先修复;无法修复时输出 `BLOCKED` 并附命令、错误、已尝试操作。

代理每完成一张 Tnn,必须**逐项填写**以下内容,**缺任何一项不得报告 DONE**。来源:`12 §8` + `13 §7`。

```text

验证命令与结果: <按 Tnn §10 顺序执行,逐条贴命令与结果摘要>
权限/归属/幂等/失败场景证据: <针对 Tnn §9 的每个必测场景,贴一个证据行>
```

`DONE` 的前提:

1. Tnn「必测场景」全部通过
2. 未超出 Tnn「目标文件清单」节的范围
3. 没有未解释的测试失败
4. 完成报告无空字段

## 6. 停止条件与标准报告

来源:`12 §7`。出现以下任一情况,代理必须停止编辑并按以下模板报告:

- 来源文档相互矛盾
- 任务需要新增未设计的数据字段或接口
- 无法确定当前用户的资源归属规则
- 测试失败且错误影响任务以外模块
- 需要新依赖、外部账号、密钥、网络权限或数据库迁移策略
- 任务范围超过 Tnn 定义的文件或模块

```text
BLOCKED
原因: <一句话>
冲突或缺失位置: <文件:行 或 章节号>
需要负责人决定的问题: <列出具体问题>
已完成的只读检查: <列出已读的文件和搜索的命令>
未执行的写操作: <确认尚未修改任何文件>
```

## 7. 提交规范(10 §4)

每次完成一个最小可验证步骤即可提交一次。提交前缀:

- `feat:` 新功能
- `fix:` 问题修复
- `refactor:` 重构
- `docs:` 文档更新
- `test:` 测试相关
- `chore:` 杂项调整

提交消息示例:

```text
feat(t01): 完成 Flyway V1 迁移与 11 张表结构
test(t01): 添加迁移失败阻止启动的集成测试
```

每张 Tnn 至少包含 1 个 `feat:` 提交 + 1 个 `test:` 提交。不得把整张 Tnn 的所有改动放在一个提交中。

## 8. 文档维护触发条件(10 §10)

出现以下情况,**必须先更新上游文档(02/04/05/13)**,再修改 Tnn 和代码:

- 新增模块
- 修改数据库结构(表/字段/索引/约束)
- 修改接口字段(路径/请求/响应/状态码)
- 修改部署方式
- 修改验收标准
- 修改 AI 可引用资料范围、资料选择规则或岗位定制生成行为
- 修改 ATS 规则、成果量化确认规则、投递状态或面试答案资产行为
- 修改 AI 数据出站字段、同意、配额、删除保留或私有文件访问规则

**Tnn 与上游文档冲突时,以 Tnn「来源」节引用的上游章节为准**。
